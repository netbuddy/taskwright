# 功能用例的写法

本文是功能用例的领域规矩。执行者按它写，评审者按它评。

## 什么是一个用例

一个用例写的是：某个参与者为了达到一个目的，与系统之间完成的一次完整交互，做完之后参与者得到了一个对他有意义的结果。

评审者按下面这几条规则逐条核对（规则的正本是 `docs/review-rules/use-case.json`，这里的列表由它生成，不要手改）。必选规则违反了，条目就评审不通过；可选规则只给建议。

<!-- 规则生成区 开始：docs/review-rules/use-case.json UC-R1 UC-R2 UC-R3 -->
1. **UC-R1（必选）** 用例粒度以参与者的一个目的为准；一个步骤不是用例，一堆用例的总称也不是。
   - 反例：用例名称「点击续借按钮」；用例名称「借阅管理」。
   - 正例：用例名称「续借图书」。
2. **UC-R2（可选）** 一个用例只写一件事；材料里并列的、各有结果的两件事拆成两个用例。
   - 反例：用例功能「读者借阅图书并预约已借出的图书」。
   - 正例：拆成「借阅图书」与「预约图书」两个用例。
3. **UC-R3（可选）** 两个用例的基本流程大部分相同时，应合并为同一用例的基本流程与扩展流程。
   - 反例：「归还图书」与「逾期归还图书」各写一个用例，前五步完全相同。
   - 正例：一个用例「归还图书」，扩展流程「3a. 图书已逾期：系统计算逾期费用……」。
<!-- 规则生成区 结束 -->

系统内部自己做的一段处理（例如自动计算逾期费用），如果材料把它当作一件独立的、有自己规则的事来讲，可以单独成为一个用例，参与者写触发它的那一方。

## 九项各写什么

下面的例子取自一个图书馆借阅系统，只用来说明写法，与你手上的材料无关。

| 项 | 写法 |
|---|---|
| 用例名称 | 用「动词加对象」的短语，从参与者的角度命名，例如「续借图书」。不用「管理」「处理」这类说不清做什么的词（UC-R4）。 |
| 用例 ID | 由系统生成，不用填写。 |
| 用例功能 | 用一两句话说明这个用例让谁达到什么目的。 |
| 参与者 | 列出与系统交互的人的角色或外部系统，一项一个。用角色名，不用人名。发起用例的那个参与者排第一个（UC-R5）。 |
| 前置条件 | 用例开始之前必须已经成立的状态，一项一条，写成可以判断真假的陈述，例如「图书处于借出状态」。不写「用户已登录」这类所有用例都有的条件，除非材料特别强调（UC-R6）。 |
| 后置条件 | 用例成功结束之后系统所处的状态，一项一条，例如「图书的应还日期已顺延」（UC-R6）。 |
| 约束规则 | 这个用例执行时必须遵守的业务规则，一项一条。材料里的数值、期限、判定条件原样写出，例如「每本图书最多续借 2 次」（UC-R14、UC-R12）。 |
| 基本流程 | 一切顺利时的步骤，一项一步，按先后排列。每一步写明是谁做了什么，主语是参与者或者系统，例如「读者选择要续借的图书并提交」「系统校验这本图书是否已被他人预约」。一般三到九步（UC-R7、UC-R13）。 |
| 扩展流程 | 基本流程某一步出现别的情况时怎样走，一项一条，开头标明它从基本流程的第几步分出来，例如「3a. 图书已被他人预约：系统拒绝续借并说明原因，用例结束。」（UC-R8） |

## 写法规则

其余的写法规则如下，同样由 `docs/review-rules/use-case.json` 生成。

<!-- 规则生成区 开始：docs/review-rules/use-case.json 其余 -->
1. **UC-R4（可选）** 用例名称是从参与者角度写的「动词加对象」短语，不用「管理」「处理」这类词。
   - 反例：「借阅处理」。
   - 正例：「借阅图书」。
2. **UC-R5（必选）** 参与者一项一个角色名，发起者排第一，不用人名。
   - 反例：参与者「张老师、系统管理员」；参与者「读者和管理员」写在一项里。
   - 正例：参与者「读者」「管理员」两项，读者在前。
3. **UC-R6（必选）** 前置条件与后置条件写成可以判断真假的状态陈述，一项一条。
   - 反例：前置条件「读者想续借」；后置条件「续借成功」。
   - 正例：前置条件「图书处于借出状态」；后置条件「图书的应还日期已顺延 15 天」。
4. **UC-R7（必选）** 基本流程每一步写明谁做了什么，主语是参与者或系统，按先后排列。
   - 反例：步骤「校验预约情况」（没有主语）；步骤「续借完成」放在校验之前。
   - 正例：「读者选择要续借的图书并提交」「系统校验这本图书是否已被他人预约」。
5. **UC-R8（可选）** 扩展流程每一条开头标明从基本流程的第几步分出。
   - 反例：扩展流程「图书已被预约时拒绝续借」。
   - 正例：「3a. 图书已被他人预约：系统拒绝续借并说明原因，用例结束。」
6. **UC-R9（可选）** 不写界面细节与实现手段，除非材料明确把它当作约束提出。
   - 反例：步骤「读者点击右上角蓝色的续借按钮」；约束规则「续借记录写入 renew 表」。
   - 正例：步骤「读者提交续借请求」。
7. **UC-R10（必选）** 不把材料里没有的功能写进去；按常识补的步骤，来源必须标为助手补充。
   - 反例：材料只说「可以续借一次」，用例里写了「系统向读者发送续借成功的短信」且来源标为文档原文。
   - 正例：不写短信步骤；确需补的步骤来源标「助手补充」。
8. **UC-R11（必选）** 不把含糊之处自己定下来；材料说不清、前后矛盾或明说还没想好的，记为问题条目。
   - 反例：材料写「寒暑假借期另定」，用例约束规则写成「寒暑假借期为 60 天」。
   - 正例：约束规则不写寒暑假借期，另记问题条目「寒暑假借期的规则待澄清」。
9. **UC-R12（可选）** 约束规则与流程里不举例。
   - 反例：约束规则「逾期按每天 0.5 元计费，例如逾期 3 天收 1.5 元」。
   - 正例：约束规则「逾期按每天 0.5 元计费」。
10. **UC-R13（可选）** 步骤里不用「等」「相关」「必要的」这类无法验证的词。
    - 反例：步骤「系统核对借阅记录等」。
    - 正例：步骤「系统核对该读者名下是否有逾期未还图书」。
11. **UC-R14（必选）** 材料里的数值、期限、判定条件在约束规则里原样写出。
    - 反例：材料写「学生一次最多借 5 本」，约束规则写「学生一次最多借几本」或「约 5 本」。
    - 正例：约束规则「学生一次最多借 5 本」。
