# 功能用例的写法

本文是功能用例的领域规矩。执行者按它写，评审者按它评。

## 什么是一个用例

一个用例写的是：某个参与者为了达到一个目的，与系统之间完成的一次完整交互，做完之后参与者得到了一个对他有意义的结果。

1. 粒度以「参与者的一个目的」为准。「读者续借图书」是一个用例；「读者点击续借按钮」不是，它只是一个步骤；「借阅管理」也不是，它是一堆用例的总称。
2. 系统内部自己做的一段处理（例如自动计算逾期费用），如果材料把它当作一件独立的、有自己规则的事来讲，可以单独成为一个用例，参与者写触发它的那一方。
3. 一个用例只写一件事。材料里用「并且」「同时」连起来的两件有各自结果的事，拆成两个用例。
4. 两个用例的基本流程大部分相同时，检查它们是不是同一个用例的基本流程与扩展流程。

## 九项各写什么

下面的例子取自一个图书馆借阅系统，只用来说明写法，与你手上的材料无关。

| 项 | 写法 |
|---|---|
| 用例名称 | 用「动词加对象」的短语，从参与者的角度命名，例如「续借图书」。不用「管理」「处理」这类说不清做什么的词。 |
| 用例 ID | 由系统生成，不用填写。 |
| 用例功能 | 用一两句话说明这个用例让谁达到什么目的。 |
| 参与者 | 列出与系统交互的人的角色或外部系统，一项一个。用角色名，不用人名。发起用例的那个参与者排第一个。 |
| 前置条件 | 用例开始之前必须已经成立的状态，一项一条，写成可以判断真假的陈述，例如「图书处于借出状态」。不写「用户已登录」这类所有用例都有的条件，除非材料特别强调。 |
| 后置条件 | 用例成功结束之后系统所处的状态，一项一条，例如「图书的应还日期已顺延」。 |
| 约束规则 | 这个用例执行时必须遵守的业务规则，一项一条。材料里的数值、期限、判定条件原样写出，例如「每本图书最多续借 2 次」。 |
| 基本流程 | 一切顺利时的步骤，一项一步，按先后排列。每一步写明是谁做了什么，主语是参与者或者系统，例如「读者选择要续借的图书并提交」「系统校验这本图书是否已被他人预约」。一般三到九步。 |
| 扩展流程 | 基本流程某一步出现别的情况时怎样走，一项一条，开头标明它从基本流程的第几步分出来，例如「3a. 图书已被他人预约：系统拒绝续借并说明原因，用例结束。」 |

## 不允许的写法

1. 不写界面细节（按钮、页面、颜色）与实现手段（数据库表、接口名、算法），除非材料把它当作约束明确提出。
2. 不把材料里没有的功能写进去。按常识必须补的步骤可以补，但来源要标为执行者补充。
3. 不把含糊的地方自己定下来。材料里说不清、前后矛盾或者明说还没想好的，记成问题条目（写进「问题」集合），不写进用例。
4. 不在约束规则与流程里举例。要写的是规则本身，不是「例如某某情况」。
5. 步骤里不用「等」「相关」「必要的」这类让人无法验证的词。
