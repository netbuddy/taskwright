# 软件需求规格说明编制

这类任务的交付物是一份软件需求规格说明，由四个条目集合组成：功能用例、非功能需求、约束、问题。「问题」集合里的条目叫问题条目，编号前缀是 TBD。完成条件要求功能用例至少有一个、非功能需求与约束可以没有；这是完成任务时的最低要求，不是写到一个就可以停：材料里的内容都要整理进条目。每个条目都要注明来源。

怎样调用工具、填来源、回复、看用户有没有看过与完成任务，按 taskwright-executor 做。这份 skill 只写这类任务特有的做法。

下面写的路径都相对任务目录，也就是你当前的工作目录，不是相对这份 skill 所在的目录。任务定义文件是 `docs/task-definitions/srs-authoring.json`，里面写明了四个集合各有哪些字段。两份领域规矩文档必须先读完再动手写条目：

- `docs/domain-knowledge/use-case-writing.md`：功能用例怎样写。
- `docs/domain-knowledge/ears-writing.md`：非功能需求与约束怎样写。

## 怎样做

1. **材料没读完不要动笔。** 材料要逐个读完全文，再开始分拣。引材料作来源（文档原文）时，摘录逐字抄材料里连续的一段，不要改字、漏字；条目出自材料里几处不相邻的地方，就写几条来源，或者在一条来源的摘录里用空行把这几段隔开，每段各自逐字照抄。
2. **把材料分拣成四类。**
   - 系统要让某个人或某个外部系统完成的一件事，是功能用例。
   - 对系统做得多快、多稳、多安全之类的要求，是非功能需求。
   - 材料里已经定死、设计时不能改的条件（时限、必须用哪个外部系统、必须遵守的业务规则），是约束。
   - 材料里含糊的、前后对不上的、说了要做却没说清楚怎样算做到的、明确说以后再做或本期不管的，是问题条目，记进「问题」集合。

   只约束某一个用例的规则，写进这个用例的「约束规则」字段；对整个系统都成立的规则，单列为约束集合的条目。
3. **一批最多写 4 个条目，问题条目放最后一批。** 一次保存最多写 4 个条目。材料里的内容多于 4 个条目时，看到这一批保存成功之后，接着保存下一批，直到材料里的用例、需求、约束与问题都写成了条目；中间不要停下来回复用户。问题条目的关联条目只能填已经保存、拿到编号的条目。同一批里新增的条目还没有编号，不能被引用；要先保存牵涉的条目，拿到编号后再在下一批写问题条目。所以先把功能用例、非功能需求与约束都保存完，再把问题条目单独放在最后一批保存，不和别的条目放在同一批。对话中途新增了一个条目、又要写一个牵涉它的问题时也一样：先保存这个条目，看到它的编号，再在下一批写问题条目。
4. **含糊的地方不要自己定。** 材料没说清楚的，不要替用户编一个答案写进用例或需求里。把它记成一条问题条目（种类填待澄清，状态填未解决），需要时在「建议的处理」里写你建议怎么办，然后去问用户。这条问题条目写下之后，事项、种类、关联条目、建议的处理都不再改，只改状态与处理结果。
   - 一条问题条目只装用户要做的一个决定。「事项」只写要决定的那件事，不重复背景。
   - 每条问题条目都要带来源，说明这份不确定从哪来：材料里的一段（来源种类填文档原文）、用户的一句话（用户的话）、你自己的发现（执行者补充，摘录写你发现了什么）、用户在界面上的一次修改（你填不了「用户直接修改」这一种，填执行者补充，摘录写明是用户哪次修改、改成了什么）。
   - 同一个来源引出几件要分别决定的事，就记几条问题条目，各自在「关联条目」里写各自牵涉的条目；一个决定牵涉多个条目，仍是一条问题条目，把这几个条目都写进它的「关联条目」。
5. **问用户与记下答复。** 来源相同的几条问题条目聚成一组，问一次：在 `items` 里点名这几条，把几件要决定的事逐件列出来。用户在一句话里答了几件都可以，按用户答的逐条了结，没答的留着下次再问。来源不同的分组分开问，先问最影响其他条目的那一组。这一条优先于平台 skill 里「一次只问一条未决事项」。
   - 用户就某条问题条目要你给建议时，给出对它牵涉的条目（关联条目里列的那些）的具体改法：改哪个条目、哪个字段、改成什么，并说明这是你推导出来的候选，等用户采纳；判断这件事该留到以后的，直接建议按「用户决定保留」了结。建议不要写回这条问题条目的「建议的处理」。
   - 用户采纳或答复之后，先把改动写进牵涉的条目（来源加一条「用户的话」）。改完之后，你判断牵涉的条目还缺信息的，不要问这个问题是否已解决，直接说还缺什么，接着问用户。
   - 不缺了，就在同一轮回复的末尾用请选择问用户这个问题是否已解决，在 `items` 里点名这条问题条目，选项固定三个：「已解决」「还没解决，继续改」「先不管，保留」。不要用请确认问：请确认只用于请用户看几条条目，它的按钮是「这几条都看过了」，答不了是非题。
   - 用户选「已解决」，就把这条问题条目的状态改为已解决，并在「处理结果」里写明采纳的内容；选「先不管，保留」，就把状态改为「用户决定保留」，并在「处理结果」里写明用户决定先保留。这两种都只改状态与处理结果两个字段。选「还没解决，继续改」，就问用户还要怎么改。问题了结之后再问下一条。
6. **「用户决定保留」只认对话里的用户。** 只有对话里的用户亲口说了这件事以后再说、先不管，状态才能填「用户决定保留」，「处理结果」才能写用户的决定；材料里的说法不算用户的决定。材料里写着「以后再做」「本期忽略」的内容，种类填后续迭代或范围外，状态仍填未解决，并向用户确认一次；材料的作者不等于正在与你对话的用户。
7. **用户的说法与材料原文对不上时**，先把原文那句话摆出来问清以哪个为准，不要直接改条目，也不要删掉有来源的内容。例如用户说「材料里没写续借次数，别写进去」，而材料里写着「每本书可以续借一次」，就先回一句：材料原文是「每本书可以续借一次」，是要按这句写，还是改掉？用户说清以后再改，并把这句话记成「用户的话」来源。

## 对用户说话

材料全部整理成条目之后（不是每保存一批就说一次），用几句话告诉用户你整理出了什么：功能用例、非功能需求、约束、问题各有几条，列出编号与名称即可，不要把全部内容贴出来。之后每次修改了条目，照样说明改了哪几条。
