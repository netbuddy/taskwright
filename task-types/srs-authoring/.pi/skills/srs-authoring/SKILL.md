# 软件需求规格说明编制

这类任务的交付物是一份软件需求规格说明，由五个条目集合组成：功能用例、非功能需求、约束、问题、总体分析。「问题」集合里的条目叫问题条目，编号前缀是 TBD；「总体分析」收这件事里的概念、角色、流程、场景、目标、假设与决定，一条是一页主题，编号前缀是 OA；用例、需求与约束依据它来写。完成条件要求功能用例至少有一个、非功能需求与约束可以没有。每个条目都要注明来源。

怎样调用工具、填来源、回复、看用户有没有看过与完成任务，按 taskwright-executor 做。这份 skill 只写这类任务在每个阶段都要照做的；这类任务在某一个阶段另外要做的事，写在「现在这个阶段」里。

下面写的路径都相对任务目录，也就是你当前的工作目录，不是相对这份 skill 所在的目录。任务定义文件是 `docs/task-definitions/srs-authoring.json`，里面写明了五个集合各有哪些字段。两份领域规矩文档在动手写功能用例、非功能需求与约束之前必须读完：

- `docs/domain-knowledge/use-case-writing.md`：功能用例怎样写。
- `docs/domain-knowledge/ears-writing.md`：非功能需求与约束怎样写。

## 怎样做

1. **材料没按块读完不要动笔。** 按 taskwright-executor 第二节的三步读材料：先看分段清单，再一次读连续几块，把读到的这几块按现在这个阶段该写的东西整理并保存之后，再读后面的块；整份材料一次读得下时，就一次读完再整理。引材料作来源（文档原文）时，摘录逐字抄材料里连续的一段，不要改字、漏字；条目出自材料里几处不相邻的地方，引了几处就写几条来源，每条各抄一段、各写段落号。Word 材料（.docx）读它的文字版，就是它旁边由它生成的同名 .md：每段一行，# 表示标题级别，方括号里的 p 加数字（例如 [p12]）是段落号，它右边是这一段的正文，左边的编号是 Word 自动编号。引用时出处写 Word 文件加段落号（例如 inputs/材料.docx#p12），摘录逐字抄段落号右边的正文，不带编号、段落号和 #、- 这些标记。表格按行写，一格里每段的段落号写在那段前面，（同左）（同上）是合并单元格。文字版里的 ![图 k](...) 是文件里的图片：能读图就用 read 读那个图片文件；读不了图，就在回复里告诉用户这里有一张图没看。以「> （文本框）」开头的行是文本框里的字，没有段落号，不能作出处。
2. **含糊的地方不要自己定。** 材料没说清楚的，不要替用户编一个答案写进用例或需求里。把它记成一条问题条目（种类填待澄清，状态填未解决，「是否阻断下游」照 taskwright-executor 第十节第 9 条填），需要时在「建议的处理」里写你建议怎么办，然后去问用户。这条问题条目写下之后，事项、种类、关联条目、建议的处理都不再改，只改状态与处理结果。
   - 一条问题条目只装用户要做的一个决定。「事项」只写要决定的那件事，不重复背景。
   - 每条问题条目都要带来源，说明这份不确定从哪来：材料里的一段（来源种类填文档原文）、用户的一句话（用户的话）、你自己的发现（助手补充，摘录写你发现了什么）、用户在界面上的一次修改（你填不了「用户直接修改」这一种，填助手补充，摘录写明是用户哪次修改、改成了什么）。
   - 同一个来源引出几件要分别决定的事，就记几条问题条目，各自在「关联条目」里写各自牵涉的条目；一个决定牵涉多个条目，仍是一条问题条目，把这几个条目都写进它的「关联条目」。
3. **问用户与记下答复。** 来源相同的几条问题条目聚成一组，问一次：在 `items` 里点名这几条，把几件要决定的事逐件列出来。用户在一句话里答了几件都可以，按用户答的逐条了结，没答的留着下次再问。来源不同的分组分开问，先问最影响其他条目的那一组。这一条优先于平台 skill 里「一次只问一条未决事项」；用户要你给建议、用户答复之后怎样改条目、怎样问这个问题是否已解决，都照平台 skill 第五节第 8 条做。你给用户的建议不要写回这条问题条目的「建议的处理」。
4. **「用户决定保留」只认对话里的用户。** 只有对话里的用户亲口说了这件事以后再说、先不管，状态才能填「用户决定保留」，「处理结果」才能写用户的决定；材料里的说法不算用户的决定。材料里写着「以后再做」「本期忽略」的内容，种类填后续迭代或范围外，状态仍填未解决，并向用户确认一次；材料的作者不等于正在与你对话的用户。
5. **用户的说法与材料原文对不上时**，先把原文那句话摆出来问清以哪个为准，不要直接改条目，也不要删掉有来源的内容。例如用户说「材料里没写续借次数，别写进去」，而材料里写着「每本书可以续借一次」，就先回一句：材料原文是「每本书可以续借一次」，是要按这句写，还是改掉？用户说清以后再改，并把这句话记成「用户的话」来源。
6. **总体分析的每一页怎样填。** 这类任务先把主题想清楚，再写用例、需求与约束。什么时候立页、问什么，看「现在这个阶段」；这里只写每一页怎样填。
   - 一页一个主题：一个词、一个角色、一段流程、一个场景、一个目标、一条假设或一个决定各立一页，不要把几件事堆在一页里。
   - 「标题」写短，就写这件事在这里的叫法，例如「预约取书」「借还台管理员」；别的叫法写进「别名」，别名不要用太短的常用词。
   - 「它是什么」用这件事自己的话写一两段：概念写它指什么、与相近的词差在哪里；流程写怎么走；角色写是谁、做什么；目标写要达到什么。不要写成需求的句式。
   - 「例子」每项一段话，要具体：有名字的人、具体的东西、具体的日子，例如「小王周六预约了《算法导论》，周一馆员把书放到预留架，小王周二来取」。这种不算的例子以「反例：」开头；流程走不通、要另行处理的情形以「例外：」开头，每一页流程至少写一条。
   - 「已经定下的」一句一条，写规则与用户定下的事，例如「保留期是 3 天」；每一条都要有自己的出处：材料里的原话、用户的话，或者你补的并写理由。还没定的不写在这里，记成问题条目，在它的「关联条目」里写这一页的编号。
   - 「标签」从概念、角色、流程、场景、目标、范围、假设、决定里选，可以选几个，拿不准就先不贴。解释一个词的贴「概念」，它会进文档的「术语与定义」；谁在用系统贴「角色」；一件事怎么走贴「流程」；一个具体情形贴「场景」；为什么做贴「目标」；做什么、不做什么贴「范围」；先这样认定的贴「假设」；用户拍板的贴「决定」。
   - 「上级主题」写它在哪一页之下讨论，例如「保留期」的上级主题是「预约取书」；最多写一页，没有就不写。
   - 「状态」新立的页写「在用」。
