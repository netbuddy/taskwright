### Upgrading

- **Only task databases of format 8 or later are opened.** Format 8 is the format of the development builds of this version. Tasks created by 0.5.0 (formats 1 to 7) and by 0.4 (no format number) are no longer upgraded: the task list shows them as 旧格式 ("old format") with a sentence that names their format, they cannot be opened, and neither the start of the service, `taskwright data upgrade` nor importing a data pack changes them. To go on with such a task, read it with 0.5.0 and carry over what is needed into a new task.
- The task database goes to format 9. A task of format 8 is upgraded like before (when the service starts, with `taskwright data upgrade`, or when a data pack is imported), and the upgrade does four things: the table of tool rejections gains two columns for the reason codes of each rejection, and rejections recorded before keep empty reason codes (see **Texts out of the code** below); the task type 软件需求规格说明编制 (`srs-authoring`) becomes 需求工程 (`requirements-engineering`) in the task directory, the task database and `task.json`; the collection 总体分析 becomes 业务说明 in the task definition, the items, the event payloads and the files that came with the task type (the materials are not touched), and reviews keep counting as done under the current rules although the wording of the review rules changed; and the side panel tab setting is dropped from the task definition (see **Task types** below). The upgrade report names the renames.
- The data directory goes to format 2: the service database gets the table of task type revisions. `taskwright data upgrade` (or the button on the page in the desktop package) upgrades it with the tasks.
- **Log files and the product settings follow the data directory.** The daily log `backend-<date>.log` goes to `logs/` and the product settings to `settings.json` in the data directory, also when the task service is started from the command line with `--data` (before, both stayed in the user data directory and only the desktop launcher moved them). `TASKWRIGHT_LOG_DIR` and `TASKWRIGHT_SETTINGS_FILE` still win, and without `--data`, `TASKWRIGHT_DATA_DIR` or `--tasks` nothing moves. On the first start, when the data directory has no `settings.json` and the user data directory has one, it is copied over once (the original is kept) and the log says 产品设置从 … 复制到 …；以后只读新的一份 ("product settings copied from … to …; only the new one is read from now on"). Log files are not moved. `scripts/dev.sh` uses the repository root as its data directory, so its `logs/` and `settings.json` are there (and ignored by git).
- Clients of the API: the event `stage_changed` is replaced by `activity_started` and `node_entered`, there is a new event `work_item_deleted`, the stage of work is now a property of a session, not of the task, and the key of the flow is `analysis` (see **Interface** below).

- **Desktop packages keep everything under one directory**, the data directory (`~/.local/share/taskwright` on Linux), so deleting it uninstalls them. pi's configuration (registered model services, keys, pi's settings) now lives in `pi/` there, and the package no longer reads or writes `~/.pi/agent`: on the first start of this version, when `pi/` has neither `models.json` nor `auth.json` and `~/.pi/agent` has one of them, `models.json`, `auth.json` and `settings.json` are copied once (a copy, not a link; the model chosen in the settings is carried over), the log says so, and the models section of the settings page says 已从本机 pi 的配置复制 ("copied from this computer's pi configuration"). After that, changes to `~/.pi/agent` no longer reach the package. The program's cache moved from `~/.cache/taskwright` to `cache/` in the data directory, and the cache of older builds is removed once a new build has started; the old `~/.cache/taskwright` can be deleted by hand. `TASKWRIGHT_DATA_DIR` or `--data` moves the whole tree; `TASKWRIGHT_CACHE_DIR` and `PI_CODING_AGENT_DIR` still move `cache/` and `pi/` on their own. Running from the repository is unchanged.
- The early domain notes collection (领域说明), the forerunner of the business description, is gone: the pages no longer show it, the hint about domain notes linked to no item is gone, and the side panel tab that a task definition could add for a collection is removed (the task definition check now reports 右侧栏页签 as an extra entry). The early source kind names 执行者补充 and 领域说明 are no longer accepted when saving; they are refused like any other unknown kind. Tasks made before revisions replaced item versions are listed as an older format like any other database before format 8, and the error `old_format` is gone.

### Versions

- **Version records.** A task keeps a record of every version published: the version number (from 1), when it was published and by whom, the revision of the deliverable at that moment, a note, and the documents generated then, a Markdown and a Word file archived in the task directory under `versions/v{N}/`, so that the version can be downloaded as it was later, whatever changes in templates and rendering. Whether the figures were archived in the Word file is recorded too.
- **Publishing a version replaces completing the task.** The conditions are the same as for completing a task in 0.5.0: every completion condition met, the user's agreement, and no new revision since the agreement; there is no forced publishing. What changes is the result: publishing writes a version record and archives the documents of that version, and nothing else. The task does not become read-only: you go on talking and changing items after a version is published, and publish version 2 later.
- **On the page**, the green bar above the items now reads 可以发布第 N 版了 ("version N can be published") with one button, **发布版本** ("publish a version"); it opens a small confirmation that says which revision becomes which version, with a box for a note on the version (optional), and **发布** ("publish"). The page renders the diagrams of the document first, as for **下载 Word**, so that the Word archive has them as pictures. Once a version is published, the bar stays away until the deliverable changes again. On the assistant's card the agreeing option reads 已完成，发布版本 ("done, publish a version").
- **The versions** are listed in the 文档与版本 ("documents and versions") tab of the work view, newest first: the version number, when and by whom it was published, the revision it published (a click selects that revision in the 修订 tab of the reference panel), the note, and the archived Word and Markdown files; a download that has no archive is greyed out and says why.
- **Changed since version N.** Once a version has been published, an item or a page of the business description changed after it carries a blue tag 第 N 版后有改动 ("changed after version N"), a section in the outline of the business description a small mark, and a line above the items says how many items, pages and diagrams changed after the latest version; 列出来 ("list them") lists them and a click opens one.
- **A task has no status any more.** The words 进行中 ("in progress") and 已完成 ("completed") are gone from the pages, and nothing is read-only because a version was published: a task can always be changed, worked on and published again. The task list is sorted by the latest activity (the latest message in any session, or the latest start or end of a work item), newest first; its status column is replaced by 进展 ("progress"), which says where the requirements analysis flow is, how many work items the task has and how many blocking questions are unresolved, for example 需求分析 · 第 4 站写条目 · 2 个工作项 · 2 条阻断 ("requirements analysis · stage 4 writing items · 2 work items · 2 blocking"), or 未启动流程 ("no flow started"); the published versions are shown on the task start page and in the work view, not in the list.
- **Deleting a task.** Each row of the task list has a menu (⋯) with **删除任务** ("delete task"). The confirmation says how many materials, items and published versions the task has and that deleting cannot be undone, and offers **先导出存档** ("export an archive first", which downloads the task as a data pack) next to **删除** ("delete"); exporting is not required. Deleting removes the task folder and the task's session archive for good; there is no recycle bin. It is refused while the assistant is working (stop it first). The service log gets a line with the time, the task number and name, and where the request came from. Interface: `POST /api/v1/tasks/{task_id}/delete`.
- **Redacted diagnostic packs.** The diagnostic pack confirmation offers 完整 ("full", the default) or 脱敏 ("redacted"), each with one sentence on what it holds; the redacted one is `GET …/export?diagnostic=1&redact=1` (`--diagnostic --redact`) and is named `diag-<task>-<time>-redacted.taskwright.zip`, with `diagnostic.purpose` `redacted`. Writing it rewrites the event streams and session files line by line (only the lines that change; line counts and times stay): results of `read` on files under the materials or knowledge folders (their derived files included), of `grep` reaching the materials folder and of `search_knowledge` become a placeholder JSON (tool, path, line range, byte count, first 16 hex digits of the SHA-256); source excerpts in `save_revision` and `save_diagram` arguments become `[已脱敏] 摘要值 … 长度 …`, and the streamed argument fragments of those two calls are emptied. The task database copy gets the same excerpt rewrite (and is vacuumed), and the settings excerpt's service addresses become `[已脱敏]`. Business description, items, problems, understanding, cards, rejection texts and the conversation are kept, so `说明.txt` says the pack is not clean and only serves flow problems. Redacted packs cannot be imported or upgraded (脱敏诊断包只供排查，不能导入).
- **Replenishing materials after an import.** Importing a pack without materials writes the pack's material list and projection section to `inputs/.expected.json` (machine state: not in the task database, never exported, not listed as a material). A missing material's row on the material card has 补齐 ("supply"): the chosen file is stored at the material's path, its text version, segment list and location table are regenerated, and everything is compared with the fingerprints taken at export (`POST …/materials/replenish?path=`). A file whose SHA-256 differs from the export is refused (`replenish_mismatch`: 不是导出时那份文件（校验值不同），没有导入) and nothing is written. Otherwise the material is restored ("已恢复到导出时的状态"), or, when the pack recorded no fingerprints, supplied without a check ("已补齐（没有导出时的校验值可比）"). When the regenerated text version, segment list or location table differs from the export (different parsing rules or segment parameters on this machine), the user is not told; the regenerated files are kept and one line goes to the backend log with the task, the material, what differs and both sides' rule versions and segment parameters. Knowledge library documents missing after an import are marked on the knowledge page and can be supplied too; only a file with the recorded SHA-256 is accepted.
- **Diagnostic packs.** A task's row menu in the task list has 导出诊断包 ("export diagnostic pack") above 删除任务; its confirmation says the pack bundles the task's run records, conversations and items for troubleshooting, without material originals or keys, and that it holds the full conversations. It downloads `diag-<task>-<yyyyMMdd-HHmm>.taskwright.zip` from `GET …/export?diagnostic=1` (`data export --task <task> --diagnostic` on the command line). A diagnostic pack is a task-scope data pack that always carries the event archive and never the material originals, plus the backend log files written since the task was created (`logs/`, whole files: a file's date is the day its process started, so a file is taken when its date is not after the export day and it was last modified after the task was created) and a settings excerpt (`settings.redacted.json`: settings version, selected models, and each model service's kind, purpose, name, address and model list, picked field by field). The list file has a `diagnostic` section (`purpose`, `granularity`, `session_id`, `product_version`, `task_db_version`, `model` — the language model selected in the settings —, `launch_model` — the model the service actually hands to the assistant, with where it came from; null on the command line —, `log_range`), and `说明.txt` says it is for troubleshooting, not for restoring. Diagnostic packs import like data packs; the two attachments are not extracted. `data upgrade --pack` on a diagnostic pack says 这是诊断包，升级后只保留数据包部分 ("this is a diagnostic pack; only the data pack part is kept") and writes a plain data pack.
- **Data packs leave out the materials.** `data export` and `GET …/export` no longer take the originals of the materials, their text versions, segment lists and location tables (`tasks/<task>/inputs`), nor the documents of knowledge libraries with their derived files and embeddings (`knowledge/<library>/files`); the two directories go in as empty directories. Instead the list file carries a material list for each task (path, slot, role, when it was added, size and SHA-256 of the original and of each derived file, number of segments) and a document list for each library (copied from `documents.json`), plus a `projection` section with the PDF location rules and format versions, the pdf.js version and the segment parameters. `--with-materials` (`?with_materials=1`) takes the files as before; the list file records `with_materials`, and both lists are written either way. A pack without materials imports as usual: the material card lists every material the task database records but whose file is not there with 文件缺失，请补齐 ("file missing, please supply it") in the size column and a greyed-out 查看 ("view"), without replace or delete; the two material read endpoints answer the new error `material_missing` with 文件缺失，请补齐：<name>; and the assistant's `read` of such a material (or of its text version) is blocked with a sentence that asks the user to supply it. Interface: `materials` items in the task page and the snapshot carry `missing`. `说明.txt` in the pack, the summary printed by `data export` and the note under **先导出存档** in the delete confirmation say what the pack holds and that it is not clean (it has verbatim excerpts, paraphrases and the conversations).
- **Smaller data packs.** `data export` and `GET …/export` leave out the event archive of each task (`runs/<task>/pi-events`, the raw record of every step of the assistant and the run logs) and take only the conversation records; `--with-events` (`?with_events=1`) takes the event archive too, and the list file records which. A pack without event archives imports as usual, and the observatory lists such sessions as 没有事件归档 ("no event archive") instead of leaving them out. Every pack has a `说明.txt` at its root that says in plain words what the pack holds, what it does not hold and how to import it; it is not in the list file and is not extracted on import. Upgrading an old pack keeps its event archives. In the delete confirmation, the note under **先导出存档** now says the export holds the task's materials, requirement assets and conversation records, not the run logs.
- On the task start page, the card of a flow whose prerequisite is met but which this version does not offer yet (the change flow, once a version is published) is labelled 此版本尚未提供 ("not offered in this version") instead of 前置条件未满足 ("prerequisite not met").
- Interface: tasks, the task list and the event `task_changed` no longer have `status` (nor `ended_at`, nor `status_before` and `status_after`); the error `task_closed` is gone. A task list row that cannot be opened says why in `unavailable` (占用中, 旧格式, 需要升级, 需要处理, 需要更新的程序), which is `null` for a task that opens; each row has `flow`, `work_item_count` and `blocking_count` (what the progress column shows), and `version_count` and `latest_published_at`. The assistant's task status and the board no longer state a status. The database keeps its `status` column unread; it is dropped the next time the tables are reorganised.
- **Pictures in the Word archive.** A version records how many diagrams its document has and how many of them are pictures in the Word archive (the rest are Mermaid text: always so when the assistant publishes); a document without diagrams records neither. The versions list says, for example, Word 里 3 张图有 1 张是 Mermaid 文本 ("in the Word file 1 of 3 diagrams is Mermaid text").
- The assistant's tool `complete_task` is now `publish_version`, with an optional `note`; it asks the task service to archive the documents of the version (the diagrams are written as Mermaid text, since the assistant has no rendered pictures) and then records the version. Its instructions and the refusals speak of publishing a version. The direct operation `submit_deliverable` is gone; the page publishes through `POST …/versions`.
- Interface: `GET /api/v1/tasks/{task_id}/versions` lists the versions (`version_no`, `published_at`, `actor`, `revision_no`, `note`, `figure_count`, `figure_pictures`, `has_markdown`, `has_docx`), and the task status's `versions` is the same list. `GET /api/v1/tasks/{task_id}/versions/{n}/document?format=md|docx` downloads the archived document of a version; a version without that archive answers 404 and says why. `POST /api/v1/tasks/{task_id}/versions?session=…` publishes a version from the page: body `{ revision_no, note, images }` (`images` as for downloading the Word document); the service archives the documents under `versions/v{N}/` and then records the version through the direct operation `publish_version`, which `POST …/actions` no longer accepts on its own. `POST /api/v1/tasks/{task_id}/versions/archive` (`{ version_no, revision_no }`) is what the assistant's tool calls to have the documents archived before recording the version. A new library event `version_published` (`version_no`, `revision_no`, `actor`, `note`); the snapshot's task has `versions`. The cell 文档与版本 of the requirement assets counts the versions.

### The task start page

The task page is replaced by the task start page, the home of a task. It keeps the frame of the work view (top bar and rail) and has no conversation.

- **What it shows.** The task type and times, the task name with one line of state (尚无需求资产, or the number of work items and whether a version is published, such as 3 个工作项 · 未发布), a paragraph on what the task is for; the work items of the task; the state of the six kinds of requirement assets, one cell each with what produces it; the two flows and the seven activities as cards with their purpose, example, input and output kinds and prerequisites; then the session list, the materials and the knowledge bases in use as before.
- **Things to deal with.** When the task holds requirement assets, a section 待处理事项 above the work items gathers what is still open on them, in four cards: open questions of the kind 待澄清 (those that block downstream work listed and counted, the others counted with when to come back to them); decisions to make (pages tagged 决定 without a 目标 page, and pages, diagrams or items still marked 待定) with items to verify; analysis models not viewed; and review findings not dealt with. Each line has an action: 启动澄清 opens the input page of clarifying with that entry ticked (启动澄清（选择 N 条） takes all the blocking questions), 打开写条目的会话 or 启动写条目 for an item to verify, 查看 for a model, 打开评审确认的会话 or 启动评审确认 for a finding. While the task has a work item of a flow, a last line 推进建议 says what to deal with first and which station can follow, or what the current station still lacks. Everything is computed from the items, diagrams, reviews and the checks of each stage that the task already returns; the interface has no new fields.
- **Work items.** When the task has work items, a section 工作项 above the six cells shows one card each, the most recently active first: the name and whether it is a flow or a single activity, the day it was launched, the station of a flow, the note on scope, and how many sessions it has with the most recent one. Each card has three buttons: 打开最新会话, 换一条干净的会话接着 (a new session of the same work item; nothing is said in it for you) and 删除这个工作项, which first asks for confirmation and says how many sessions will be archived. A completed or abandoned task keeps only the first button.
- **The three-step guide is the entry to the requirements analysis.** It shows whenever the task has no work item of a flow: an empty task, a task that only ran single activities, a task whose flow work item was deleted; once there is a flow work item it is gone, and the flow is carried on from its card. In an empty task it sits under the head, titled 三步开始 with the three steps; in a task that holds assets it is a section of its own after the work items and before the six cells, titled 启动需求分析 with the three steps on one grey line. Its main button 启动需求分析 and the three common starting points open the input page of the flow. When the task has materials, each starting point adds 已上传 N 份材料，启动后一并核读 ("N materials uploaded, read when the flow starts"): materials belong to the task and need not be uploaded again.
- **A catalogue, not a launcher.** A flow card or an activity card that can be started is clickable as a whole and opens its activity input page; so do the main button of the guide and the three common starting points. A card whose prerequisites are not met is dimmed, cannot be clicked and says what is missing on hover. While the task has a work item of a flow, that flow's card reads 已在进行 and the station it is at, cannot start another, and has a button 打开它的会话; the other flow says why it cannot be started. An activity that already has work items shows how many; it can still be started, which adds another. The arrow on startable cards reads 启动 →. 自由讨论, on a row of its own below the activity cards, opens a new session without starting anything; it is the only entry that skips the input page.
- **The activity input page** (`#/tasks/{task_id}/start/{key}`) has no conversation. It shows a summary of the flow or activity, the input blocks it needs (project materials and domain knowledge bases for flows and for reading the material; the description of the target system while the business description is empty, for flows and for clarifying; a note on scope for single activities), and what happens after starting. There is no choice of session: a launch always creates a work item and a session of its own. The main button 启动… launches it, sends the first message for the user and opens the workbench in the new session. The first message is the description of the target system when one was written, otherwise one fixed sentence per activity, such as 请开始整理建模。; the persona draft export leaves these sentences out. The note on scope goes with the start request, not into the message. The input page of clarifying has a block 待澄清问题 above the note on scope, with a tick box for each open question (those that block first) and each decision to make; the ticked numbers are written at the start of the note on scope (只澄清这几项：…。), and coming from 待处理事项 they are ticked already (`?pick=` in the address). The block that says what happens next is titled 启动后; launching never ends another work item, so it no longer says that the current activity ends. While the task has a work item of a flow, the input page of a flow says why it cannot be launched and offers 打开它的会话.
- **Opening a task from the list** leads to the workbench (the most recently active session) when the business description already has content, and to the start page otherwise. The task name in the top bar of the work view and the task icon in its rail lead to the start page.
- Gone from this page: the completion bar, the cards per collection, and the buttons 生成文档 and 新建会话. Documents are generated from the work view as before; a new session comes from 进入工作台 here or from the 会话 menu in the work view.
- **The top bar of the work view names the current activity of the session.** Where it used to read 任务进行中 it now reads either 当前活动：… ▾ while the session is carrying out a work item, or 自由讨论 · 不绑定活动 with a dark chip 启动工作 (to the task start page) in a session for free discussion; the first two open the panel 切换工作. A completed or abandoned task still reads 任务已完成 or 任务已放弃, and a task without stages 任务进行中.
- **The sessions of a task** are listed on the start page and in the 会话 menu of the top bar with the work item each belongs to: the flow and its station (需求分析 · 写条目), the activity (整理建模), or 自由讨论. A switch at the bottom, 显示已归档的会话, also lists the archived sessions, marked 已归档; they can still be opened. The 新建会话 entry of the menu says that it creates a session for free discussion.
- **The panel 切换工作** shows which work item the session belongs to (the station of a flow and how many other work items the task has), the six kinds of requirement assets, and three groups. The work item of this session: continue it, carry it on in a fresh session, or delete it (after confirmation); a session for free discussion has nothing here. Helper actions done in this session without changing its work item: answer the open questions (puts a sentence in the input box), ask for a retelling, request a review of the items waiting for one, add a project material, and show the work progress card. Other activities: the catalogue of single activities and flows; one that can be started opens a confirmation that says what happens to this session and to the new one, which items a redrawn model would mark for checking, and which work items of the same activity exist already, with a box for the note on scope. Starting creates a work item and a session, sends the activity's first sentence for you and opens the new session. While the task has a work item of a flow, that flow reads 已在进行 with a button 打开它的会话.

### The workbench

The middle column of the work view is split by the six kinds of requirement assets, and the right-hand column becomes a reference panel. The look of the tab row is unchanged.

- **Six tabs**, each followed by its count: 材料与证据 (materials and evidence; materials, not counting the text versions made from Word or PDF), 业务说明 (business description; sections, not counting deprecated pages), 分析模型 (analysis models; diagrams), 需求条目 (requirement items; not counting questions), 评审与确认 (review and confirmation) and 文档与版本 (documents and versions; versions published). A line under the tabs gives the summary (items, waiting for review, failed review, unread, open questions); a click shows the completion conditions, on every tab. The page remembers the tab last used for each task.
- **材料与证据**: a table of the task's materials with type, size, upload time and how many sections and places cite each, with 查看 (opens it in the reference panel), 替换 and 删除 under the same rules as on the start page, and **上传材料**; a table of the knowledge bases in use with how many places cite each, 取消选用, and **选用别的知识库**.
- **业务说明**: the outline and the sections, as before.
- **分析模型**: an index of all diagrams, grouped by kind, with the section or chapter head each sits in, its revision (marked 刚改 "just changed", on a light amber row, when it was changed after it was drawn and you have not seen it since), whether you have seen it, and the items that cite it; 打开所在章节 opens the business description at the diagram. A count line sits above the table. An address with `?tab=diagrams` opens this tab.
- **需求条目**: a row of sub-tabs, one per collection, with **导出 Word**; a row of filters (筛选：); the unread notice, the bulk mark-as-read, and the list and the detail as before.
- **评审与确认**: **评审 N 条待评审的条目** at its head; one line on open findings (the findings themselves are in the 评审 tab of the reference panel, linked to the item in view); a table of review rounds (round, time, how many items, how many findings, how they were handled); a table of confirmations for requirement items, analysis models, the assistant's additions to verify and open clarification questions; and a line on what publishing needs.
- **文档与版本**: the latest version at its head with **生成文档** (the document dialog) and **发布第 N 版** (the same conditions as the green bar; when it cannot be used, hovering says why). A preview of the latest revision opens inline, and the whole document downloads as Word or Markdown. A table covers the document chapter by chapter (sections, items, diagrams, whether it has an introduction; empty chapters marked). A pre-publish check lists the completion conditions, ticks those met, says what each of the others lacks and links to where it can be fixed, and collapses to one line when all are met; non-blocking notes below it point at empty chapters, items without a basis, diagrams not seen, items whose section has an open clarification question and untagged topics. Then the versions table with how the assets differ from the latest version, and one line on traceability: how many requirement items trace to a section or a diagram, naming the exceptions.
- **The reference panel** has four tabs: 原文定位 (source text; one material at a time, opened from 查看 in 材料与证据 or from a cited source; it no longer lists the materials), 修订 (revisions), 评审 (review) and 调试 (debug, in debug mode only).
- **Retired**: the 文档 ("document") tab of the side panel, the versions block at the top of the 修订 tab, the 生成文档 button above the items, the standalone 图表 ("diagrams") tab of tasks without a business description, and the side panel tab for the business description outline.
- **Items to verify are requirement items only.** The check 没有待核实的条目 of the writing stage, the 待核实条目 card on the start page and the list of items to verify given to the assistant no longer count question items: a question records something undecided, and an assistant's source on it does not make it a requirement to verify.

### Work items, sessions, activities and the flow

Reading the material, clarifying, modeling, writing items, reviewing and writing the document are now six activities. In that order they form the flow of the requirements analysis (需求分析), which is what 0.5.0 called the six stages; an activity can also be carried out on its own.

- **A work item is one launch.** Every time you start work, a flow or a single activity, the service creates a work item (工作项) and a session that belongs to it. The work item records what was launched, the station a flow is at, the note on scope, and who launched it and when. A task can have several work items at once, of different activities or of the same one; they do not disturb one another, and the task no longer has one "current activity".
- **A work item has no end.** It is a lasting line of work in the task. When the assistant reports a single activity done, that is a line under its reply and nothing more: the work item stays, and you can go on in the same session. The flow does not end either: it can go back to any station and run again. A work item you no longer want is deleted.
- **At most one flow per task.** While a task has a work item of a flow, no flow can be launched (whatever the flow); open its session, or carry it on in a fresh session. To start the flow over, delete its work item first; the station it had reached is not kept. Single activities have no such limit.
- **A session belongs to one work item, or to none.** This is fixed when the session is created. What the assistant may write in a session, which part of the instructions it gets and which proposal is open depend on the work item of that session. A session that belongs to no work item is a session for free discussion: the assistant answers, writes topic pages and records questions, as in the clarifying stage, but writes no requirement items and proposes no stage. To do something else, launch another work item; the session you were in stays as it is.
- **A fresh session for the same work.** A work item can have several sessions one after another. When a session has grown long, a new one can carry on the same work item: the station of the flow and the note on scope are kept, and the earlier session remains. A new session in which nothing is said before you leave it is not kept, and is not counted.
- **Deleting a work item archives its sessions.** The sessions are not deleted (they are the record of the work, and revisions point to them): they are archived, left out of the session list unless archived sessions are asked for, and in them the assistant works as in a session for free discussion. Revisions and events stay as they are.
- **Moving within a flow.** The cards that enter the next stage or go back, and the direct move, change the station of the work item; they do not open another one. They count only in a session whose work item is a flow. A proposal of the assistant belongs to its work item and lapses when that work item moves to another station, not when some other work item is launched or deleted.
- **Sessions are named after their work item** when they are created: the name of the activity, or the name of the flow and the station, followed by the first characters of the note on scope when there is one. A session for free discussion is still named after the first sentence you say.
- Only you launch work. The assistant has no tool for it; writing items in particular starts only by your choice. The card 开始核读材料 that the assistant used to send in an idle task is gone from its instructions, and a click on such a card no longer starts anything.
- **Whether a single activity can be launched depends on the data only.** Reading needs a material; modeling needs something in the business description; writing items needs that and every diagram viewed; reviewing needs items; writing the document needs at least one item you have read that is not pending verification. Which activity ran before, and which work items exist, play no part: an activity that already has a work item can be launched again.
- The line a launch adds to the conversation of the new session names the activity or the flow in quotes: 用户启动活动「整理建模」。 or 用户启动工作流程「需求分析」，从「核读材料」开始。 A refused launch reads 现在还不能启动「…」：… and says what is missing. A move reads 用户把工作项从…移到…。 A deletion reads 用户删除工作项「…」，它的 N 条会话已归档。
- **A note on scope.** A launch can carry a short note on its scope. It is kept with the work item, appended to that line in the conversation (范围说明：…), and given to the assistant in the system prompt, as a part of its own, in every session of the work item.
- **The conversation of a session begins with a line saying what it is**: 新会话 · 属于工作项「整理建模」（10-13 09:02） with the time the work item was launched, or 新会话 · 自由讨论（不绑定活动）. An archived session has no such line.
- **The task status card is now the work progress card (工作进展)**, and so is the button beside the input box. Its title is 工作进展 · time. Its first row says what the session is doing: the flow, its station and when it was entered, the activity and when it was launched, or free discussion; then come the version (已发布第 N 版 or 未发布), the work items of the task, and the business description, the models and the requirement items each with its number and one line on its state. The section 开展一项活动 of the card is gone. Its buttons are now: the open proposal, as before; 启动需求分析 or 启动需求变更 while the recommended flow can be launched, which opens its input page, with a line saying that it creates a session of its own; 请助手汇报当前状况 (it was 请助手说明下一步; the sentence sent is the same); and 其他工作…, which opens the panel 切换工作. The card reads the status of the session it is shown in, and a new session of a task that holds nothing yet does not open with it.
- When the business description is still empty, the work view no longer offers 通读材料起草 and 逐项澄清; a line says that reading the material and clarifying fill it, and that the requirements analysis is launched from the task start page. A session cannot change its work item, so these two buttons, which moved the task to a stage, no longer fit.
- The conversation no longer has a line above a reply for a stage move made by the assistant. The assistant has not been able to move the stage since before 0.5.0; a session recorded during the development of 0.5 that contains such a move no longer shows that line.
- For those who tune the instructions: the six stage files under `agent/prompts/stages/` now describe the activity only, and the parts on leaving a stage are in `agent/prompts/flows/analysis.md`, one section per node of the requirements analysis. For a task in the flow the assembled system prompt is the same text as in 0.5.0, apart from one new item in the shared part. Each activity file, and each flow file under `agent/prompts/flows/`, now opens with a head between two `---` lines (key, name, mode, purpose, the asset kinds read and written, prerequisites, an example; for a flow its stations and inputs as well). The head is what the activity catalog and the prerequisites are computed from; it is dropped when the system prompt is composed, so the prompt text is unchanged. `stages/publish.md` and `flows/change.md` have a head only for now. The debug prompt directory recognizes `flows/analysis.md` as a sixteenth file name.

### Texts out of the code

- **One place for the platform texts.** The sentences the assistant or the user reads now live in Markdown templates under `agent/prompts/` instead of the code: the descriptions of the eight tools (`tools/`), and in `runtime/` the notes appended after the user acts on the page, the task status message, the text that 查看条目 and 查询任务状态 return, the rejections of every tool (`rejections_*.md`), what the tools hand back when they succeed (`results.md`, `results_search_knowledge.md`), the fixed sections of the system prompt, and the texts of the task start page. A template has one key per section and `{{name}}` placeholders only; which sentence to use is still decided in the code. `agent/prompts/README.md` lists every file: where it is assembled, who reads it, its parameters and the tests that pin it. Tests check that every key the code uses has a template, that no template is unused and that the values given match the placeholders. The code that recognised a rejection or a status message by its words now takes the words from the same templates, or reads the reason codes. What the assistant and the user read is unchanged, except one sentence of the knowledge base section, which pointed at the retired platform skill, and a rejection of 保存图 whose sources failed a check, which carried a stray control character between the reason and what to do.
- **The platform skill is retired.** Every task now gets its system prompt from the stage prompt files (`agent/prompts/stages/`); `agent/prompts/skills/taskwright-executor/` and `backend/prompts/executor_system_prompt.md` are removed, and the launch profiles no longer name a platform skill. The texts the assistant reads say 平台说明 ("platform text") where they said 平台 skill.
- **Reason codes.** Every rejection carries reason codes: the key of its template without the variant, such as `save_revision.collection_unknown`, `source.material_excerpt_not_found` or `gate.understanding_missing`; a rejection with several reasons (a save with several faulty operations, a reply with several faults) has one per reason, in order. The table of tool rejections of a task (format 9) stores the first in `reason_code` and all of them in `reason_codes` (a JSON array). Whether a rejection counts as a missing earlier step or as faulty input now follows its first reason code: the 18 codes of the gates (understanding not written, wrong stage, the user's agreement missing, completion conditions unmet) count as a missing earlier step; a save stopped by the stage of work, recorded as faulty input before, now counts as a missing earlier step. 查看条目 and 查找知识库 record their rejections too. A rejection that is not about the input (the task database cannot be opened, the archive was not written) is still not recorded.
- **The observatory's health page** has a second table under the gate statistics, 每百次调用被拒次数，按原因码 ("rejections per hundred calls, by reason code"): one row per tool and reason code, with how many calls of that tool the archives in scope hold, how many of them were refused with that code, the rate, and how many of those counted as a missing earlier step. Rejections recorded before format 9 have no code and share one row; refused calls without a record share another. Sessions without an event archive are left out of both counts.

### Task types

- **The bundled task type is now 需求工程 (requirements engineering)**, key `requirements-engineering`, formerly 软件需求规格说明编制 (`srs-authoring`). It covers the work of requirements engineering on a project; publishing the requirements specification is one of its activities. Its collection of topic pages is now called 业务说明 (business description), the name the page already used; the id prefix OA does not change.
- **Task types live in the data directory.** `task-types/` in the data directory holds the current version of each task type, and new tasks are copied from there. When the service starts, every task type the product ships that is not there yet is copied over, and `task-types/manifest.json` records the version it was seeded from, when, and by which product version. A type already there is never overwritten: a newer version in a later package does not replace it (restoring the shipped one and updating to it come with the task type page in a later batch).
- **Task types have revisions.** Every revision is kept as a whole directory under `task-types/.revisions/<key>/<number>/`; the seeded copy is revision 1. A change, or going back to a revision, is made in a scratch directory, checked to still have a readable task definition, and then kept as a new revision; going back never deletes a revision. The service database records each revision: when, by whom, a note, and the files added, changed or removed with their digests. There is no page for this yet.
- `task.json` records `task_type_revision`, the revision of the task type a task was copied from; tasks upgraded from format 8 count as revision 1. The list of task types, the version recorded for a new task and the current version shown next to the version a task was created with are read from the data directory.

### Interface

- Task types: `GET /api/v1/task-types` lists the task types in the data directory; the key of the bundled one is `requirements-engineering`. A collection's `display` no longer has `side_tab`. Completion `hints` no longer have the kind `unlinked_domain_notes`. The error code `old_format` is gone.
- Events: in place of `stage_changed` there are two. `activity_started` is the launch of a work item (`record_id`, `to`, `actor`, `reason`, `run_id`, `flow`, `node`, `scope`, `op_id`; `from` is always null, and `flow` and `node` are null for a single activity). `node_entered` is a move of the work item of a flow to another station (`record_id`, `flow`, `node`, `from`, `direction`, `actor`, `reason`, `run_id`, `op_id`). A new event `work_item_deleted` is the deletion of a work item (`record_id`, `activity`, `node`, `flow`, `scope`, `archived_sessions`, `actor`, `reason`, `op_id`). A client that listened for `stage_changed` must listen for `node_entered`.
- The key of the flow is `analysis`, its name 需求分析. Events recorded before the upgrade keep the earlier key `initial`, and the service passes them on with `analysis`.
- The stage of work belongs to a session. `task.stage` in a snapshot is that of the session the snapshot was read for; it has `work_item`, the work item the session belongs to, and `current` is `idle` for a session for free discussion or an archived session. The `stage` carried by the last library event of a batch is computed for the session given when subscribing. Data read without a session, such as the task detail, reports `idle`.
- Direct operation `start_activity` with `fields` `{ activity, in_flow, scope }`: launches the flow of the requirements analysis from a station, or a single activity. It always creates a work item and a session, and answers with `session_id` and `activity_record_id`; launching a flow while the task has a work item of a flow is refused with the existing one in `data.existing`. New direct operation `delete_work_item` with `fields` `{ activity_record_id }`, answering with `archived_sessions`. `move_stage` moves the work item of the session and is refused in a session that is not carrying out a flow.
- `POST …/sessions` accepts `{ "activity_record_id": … }` to create a session that carries on a work item. The session list has `work_item` on every session, leaves out archived sessions, and lists them with `archived` and `archived_at` when `?archived=1` is given.
- Task status: `GET …/status` accepts `?session=…`; `activity`, `missing` and `proposal` describe that session. New entry `work_items`, all work items latest activity first, each with its sessions (archived sessions and sessions never written out left out) and the most recently active one. `activity.kind` may be `activity` (a single activity) or `idle`, with `ordinal` null.
- Task status and `task.stage` also have `assets`, the current state of the six kinds of requirement assets (materials and evidence, business description, analysis models, requirement items, review and confirmation, documents and versions), and `catalog`, the two flows and the seven activities with the wording from their definitions, whether each can be launched now, a one-line state and `active_count`, the number of its work items; a flow carries its stations, the station to start from (`start`) and `work_item`, the work item of a flow the task already has. `task.stage.scope` is the note on scope of the work item of the session. `launch` stays for the pages that still read it.
- The system prompt shown in the debug tab may have one more part, `scope`.
- Task status: `start_page`, the texts of the task start page and the activity input page (`lead`, `guide_note`, `cases` each with the block to look at first, `intake`).
- The assistant's reply accepts `activity_done`; a reply message then carries `activity_done` with the activity that was done, and nothing else changes. A user message sent from a card carries `how` in `stage_move`, and `why` in `stage_unmoved` when the click did not count because the session was not carrying out a flow.
- See sections 4, 5, 6 and 13 of the API reference.

## [0.5.0] - 2026-10-12

0.5.0 changes how a requirements task is worked. The assistant no longer writes items straight from the materials: work goes through six stages, each entered by your click on a card the assistant proposes. What you and the assistant come to understand is kept as a business description in seven chapters, with five standard models drawn from it; items are written from that description. A point that is unclear is recorded as a question where it arises and settled later, without going back a stage. The generated document follows the chapters of the business description and can be downloaded as a Word file. Tasks now keep working across upgrades, and tasks and knowledge libraries can be exported and imported as data packs.

### Upgrading from 0.4.3

- Tasks keep working across upgrades from this version on. Tasks created by 0.4.0 or later are upgraded in place (the task database goes to format 4); their content does not change. Tasks older than 0.4.0 still cannot be opened and are marked 旧格式 ("old format").
- **Desktop packages and `--mode desktop`:** the first start after the upgrade shows **数据升级** ("data upgrade") in place of everything else, with the number of tasks, where the backup goes and a button **开始升级** ("start the upgrade"). It usually takes less than a minute.
- **Servers (`--mode server`):** a service that finds tasks left by an earlier version does not start; the log and standard error say so and the exit code is 1. Run the command the message gives, then start the service: `node backend/src/main.mts data upgrade --data <data directory>`, with `--tasks` and `--knowledge` added when the service is started with them. The command refuses to work while a service is using the data directory, and its report says which task directory was scanned.
- Before anything is changed, the files about to be changed are copied to `backups/<date and time>-<earlier version>/` in the data directory; if that copy fails, nothing is upgraded. Backups are not removed automatically. Data upgraded by this version must not be opened with 0.4.3 or earlier: those versions do not check and would write to it. To go back, install the earlier version and copy the backup back (see **Upgrading to a new version** in section 8 of the deployment guide).
- The data directory now holds `service.sqlite` (the task register) and, in every task directory, `task.json`; include them in backups. The task service takes `--data <dir>` and `TASKWRIGHT_DATA_DIR` for the data directory.
- **Tasks created by 0.4 work as before.** They keep their domain notes (领域说明), are not divided into stages, have no business description, and their documents are generated from their own template as before. The stages, the business description and the new document are for tasks created with 0.5.0.
- The interface looks different after the upgrade: the new style **暖纸** ("warm paper") is the default. Choose **素白** ("plain white") under **外观** on the settings page to get the earlier look; the choice is kept per browser.
- If you ran a development build between 0.4.3 and 0.5.0 from the repository: tasks created with it are upgraded by the same command. They keep the copy of the task type definition they were created with, so in them the assistant writes no chapter introductions, questions carry no blocking label, and the checks about these show as not applicable; their documents are generated with the template the product ships now.

### Work in six stages

- In a new requirements task, work goes through six stages: reading the material (核读材料), clarifying (澄清), putting the topics in order (整理建模), writing items (写条目), review and confirmation (评审确认) and writing the document (编写文档). A task starts in the reading stage when it has materials and in the clarifying stage when it has none.
- **You move the stage, on a card.** When the assistant has finished a stage it sends a card that says how far the stage got and what the next one will do; the task moves when you choose the entering option (进入澄清, 进入整理建模, 开始写条目, 进入评审确认, 进入编写文档). The other option, **继续本阶段**, only marks the card and does not make the assistant work. In the clarifying stage the assistant proposes the next stage when nothing is left to ask. Only when most of the earlier results can no longer be used does the assistant propose going back, on a card with **退回…** and **留在本段**. The assistant cannot move a task itself; every move is recorded with who made it, when and why.
- **A proposal stays open.** After a proposal card, a line **待决定** above the input box carries the card's acting button in every session of the task, until the stage moves, a new proposal is sent or the task ends.
- What the assistant may write depends on the stage and is enforced by its tools: pages of the business description and questions always; diagrams from the modeling stage to the review stage; use cases, requirements, constraints and review requests in the writing and review stages; completing the task in the review and document stages. A refusal says which stage the task is in and what has to happen first. What you do in the interface is not restricted.
- When you ask for something that belongs to another stage, the assistant says which stage the task is in and where that can be done, and sends the card; a change to a page of the business description is made directly in any stage.
- Seven things can be done in any stage without changing it: asking and settling questions, revising, confirming, recording a decision, retelling, reviewing, and looking at the task status.
- Twenty-one checks say what each stage still lacks, for example that every material is cited, every flow has a flowchart with a decision, and you have looked at every page an item is based on. They never block an operation.
- The assistant's instructions are given by stage: before every run the system prompt is put together from what every stage needs and one section for the current stage.

### The business description and its models

- A new requirements task has the collection **总体分析** (overall analysis, ids starting with OA), shown on the page as **业务说明** (business description). One page is one topic in the matter's own words: what it is, examples, what is settled, labels, sources. It replaces the domain notes of 0.4.
- The business description has a table of contents with seven fixed chapters: overview and scope, roles, business flows, business objects, business rules, business goals, and decisions and open questions. A page is a section of the chapter its label points to, numbered as on the page (3.1, 3.2). Every chapter has a chapter page; chapters 5 and 7 are computed (the rules table, decisions and open questions by time).
- A section has a fixed order of blocks: description, flow steps, state diagram, relations to other objects, exceptions, examples, applicable rules, open questions, other diagrams, related roles and objects, the requirement items written from it, and a trace line from the materials to the items and the section's number in the document.
- **Five models.** In the modeling stage the assistant draws, in a fixed order, a system boundary diagram (a new kind, `context`), a use case diagram, an object relation diagram, a flowchart with decisions for every flow and a state diagram for every concept that has states, and records rules that contradict each other as questions. Diagrams are shown in the section or on the chapter page they describe; the Diagrams tab is gone in such tasks. The use case diagram is shown as a table of roles and use cases.
- **Items are written from pages you have looked at.** An item can cite a page or a diagram as a source. An item based on a page or diagram you have not looked at, or on content the assistant added that you have not confirmed, is marked as waiting to be verified. The page records that you looked at a diagram when it has been drawn in the visible part of the page.
- **Waiting to be verified.** Whatever the assistant adds without a source in the materials or your words is marked; a page shows how many places wait, and you confirm them on the page.
- **Retelling.** The assistant can tell its understanding of a topic as a story for you to check, on a card titled **复述 · 请核对** with the options **采纳为例子**, **有误，需修改** and **换一个例子重述**.
- While the business description is empty its tab offers two ways to start: **通读材料起草** (the assistant reads all the materials first) and **逐项澄清** (it asks you one thing at a time).
- The requirements task type maps the models to items: a use case of the diagram becomes a use case item, the main path of its flowchart the basic flow, the branches the extensions.

### Questions recorded in place

- When one point is unclear in any stage, the assistant records a question, writes 待定 on the page, diagram or item concerned and carries on, instead of going back. The report at the end of a stage and the card for the next one list the questions still open.
- A question says whether it **blocks the next stage** (阻断下游) or not (不阻断, with when to come back to it). Blocking ones come first. A section of the business description lists its open questions with the label, and its settled questions with where the answer was written.
- In the clarifying stage the assistant asks one thing at a time, also about rules the business needs but the material does not state; it records an answer directly and asks once at the end, on one card, whether the answered questions are settled.

### Generated document

- The generated document has the structure of the business description: the task name and contents, the seven chapters with the page's chapter and section numbers and the diagrams where they belong, then the requirement items (chapters 8 to 11), and an appendix that traces every requirement item to the sections and diagrams it is based on. Open questions are marked 【待澄清】 and undecided sentences 【待定】.
- **The document stage.** After review the assistant proposes 进入编写文档, adds an introduction for every chapter that has content, and asks you to read them on a card with **看过了，生成文档** and **需要修改**.
- The preview in the document dialog is laid out, with headings, tables and the diagrams drawn. **下载 Word** saves the whole document as a Word file with the same content; **导出 Word** for ticked items works as before.
- Document templates: `{{业务说明}}`, `{{追溯附录}}`, `{{目录}}` and `{{任务名}}`; grouping by each value of a list field; writing a list field item by item; a part written only when a field has content.

### Task status, cards and the work view

- **Task status.** **任务状况** beside the input box, or `/状况`, inserts a card computed by the program without the assistant: the stage, the sections per chapter, the diagrams, the items and how many you have looked at, what the stage still lacks, and the open proposal. A new session in a task that already has pages starts with this card.
- **Stop a piece of work.** While the assistant works, the send key becomes a stop key. What was already saved stays, and a line under the summary says which revisions, how many items and how many diagrams that work saved.
- The card that asks you to look at items is titled **请过目** instead of 请确认. The buttons that set a question aside read **暂不处理**.
- **A card can wait.** Words typed in the input box at the bottom no longer close an open card: the card stays usable until you click one of its options or write in its own text box, or until the assistant, judging from the context, takes what you said as the answer to it. Before it proposes the next stage the assistant asks the question and choice cards still unanswered in the stage again, one at a time, and records those you still leave open as questions.
- **Two styles.** **暖纸** and **素白**, chosen on the settings page; a style changes colours and the typeface of titles only.
- A reply that asks a yes-or-no question as an open question is refused, so that such questions come as a choice with buttons.

### Upgrades, export and import

- Every task database records its format version and changes only through one table of upgrade steps. A task that fails to upgrade is left as it was, marked **需要处理** in the task list with the reason, and retried by `data upgrade`. Every upgrade writes a report to `logs/` in the data directory.
- Tasks and knowledge libraries can be exported into a **data pack** (`.taskwright.zip`) and imported into another data directory: everything, one task, or one knowledge library. A pack holds copies of materials and conversation records, is not encrypted, and does not hold settings, model configuration or keys. Commands: `data export`, `data import` (`--renumber` for a task whose id is in use) and `data upgrade --pack`. The page has no buttons for this yet.
- Task type definitions carry a version. A task keeps the instructions, review rules and definition copied when it was created; when they differ from what the product ships, the task page says so.

### Interface

- Task data: `task.stage` (the current stage, the checks, the open proposal, the flow), `task.overall_views` (rules table, goal tree, decisions and open questions), `pending_verification` and related fields on items, `viewed` on diagrams, `task_type_versions`.
- Conversation: a reply carries `answers_card` and `resends_card`, an act may carry `resends`, and a sentence typed in the text box of a card is sent with `card.choice` `typed`; section 5.3 says when a card counts as answered.
- New events: `stage_changed`, `stage_proposed`, `diagram_viewed`. New direct operations: `move_stage`, `continue_stage`, `mark_diagram_viewed`. `GET …/status` returns the task status.
- `POST …/documents/download` with `"format": "docx", "whole": true` returns the whole document as a Word file; the client sends a PNG for each diagram in `images`.
- Upgrades and data packs: `GET` and `POST /api/v1/service/upgrade`, `GET …/export`, `POST …/import`; while an upgrade is pending every other endpoint answers `upgrade_pending` (503), and a task whose format does not match answers `task_unavailable` (409).
- See the API reference for the fields; sections 4, 5, 6, 9, 12 and 13 changed most.

### Evaluation, debug mode and development

- **Evaluations.** `python3 -m sim.evals run` plays one persona several times against a set of materials and records, for each pass, the twenty-one checks, an expectation list for the materials and the version of the instructions; the observatory lists evaluations and compares two of them. The simulated user looks at pages and diagrams, clicks the cards and answers blocking questions first.
- **Debug mode** (`--debug`, off unless given): a prompt directory whose files replace the instruction files without a restart, the system prompt of the last run part by part, the stage moves and checks in a 调试 tab of the side panel, and a draft persona exported from what the user said in a task. It has no access control of its own; use it on your own machine.
- The instruction files for tasks with stages are in `agent/prompts/stages/`; a task type keeps one file per stage beside its `SKILL.md`. The fake model endpoint for tests moved to `tools/fake-model/` and writes its configuration only into an empty directory. The agent and backend tests remove their temporary directories.

## [0.4.3] - 2026-10-08

0.4.3 takes PDF files as materials and as knowledge base documents. The assistant cites a PDF by page and block; the page shows the file page by page, scrolls to the page a source points to, frames the block and marks the excerpt. A material that has not entered the conversation can be replaced with another file. The task status note at the top of a conversation is folded into one line. The page now names the browsers it supports and says so in a browser that is too old.

### Upgrading from 0.4.2

- Existing tasks are not migrated and are not affected: the task databases are as they were, and a task created with 0.4.2 takes PDF materials like a new one. As before, back up the task directories before upgrading.
- The desktop packages are larger by 2 to 3 MB (the AppImage by about 2.2 MB, the plain executable by about 3 MB): they now carry the files of pdfjs-dist that the task service reads PDF files with (about 3.8 MB uncompressed) and those the page shows them with (about 3 MB uncompressed).
- If you run Taskwright from a clone of the repository, install the dependencies again as usual (`make install`, or `npm ci`). The pages now use pdfjs-dist, the package the task service has declared since 0.4.2; a clone whose dependencies were installed for 0.4.2 already has it, and installing again changes nothing. A startup profile of your own needs no change: the new section **PDF 解析** has a default for every value.
- Upgrade the page and the task service together. The page of 0.4.3 relies on what the task service of 0.4.3 sends with a system note; with a task service of 0.4.2 the reminder sentence is still shown in the conversation, and the folded line has no key facts.

### PDF materials and knowledge base documents

- PDF files are accepted as materials and as knowledge base documents (up to 5 MB and 20 MB, as for other files). A PDF is parsed when it is uploaded, which takes under a second for most files. Meanwhile the page says so (**正在上传……PDF 要先读出各页的文字，页数多的要多等一会儿。**), and the line turns into the result when the upload is done. The upload box of the knowledge base page no longer says that PDF files are not accepted yet.
- A PDF without any readable text, most likely a scan, is refused with **这份 PDF 没有可读的文字（可能是扫描件），本版不支持。** ("this PDF has no readable text (it may be a scan); not supported in this version"); there is no text recognition. A PDF in which only some pages have no text is accepted, and the assistant is told which pages could not be read. Also refused: a PDF that needs a password, one over 1000 pages or 3 million characters, and one whose parsing is not finished after 60 seconds, with a message that says how long it took and which page it reached, such as **解析用了 60 秒仍没有完成（已读到第 420 页，共 1000 页），这份文件太复杂，本版不支持。** A refused upload leaves nothing behind.
- The assistant reads a text made from the PDF, in which every block of text is one line marked with its page and block, such as `[p3-2]`. Running heads and feet are kept apart, and a table is read row by row, not cell by cell. The task status message and `get_task_status` give, for every PDF material, its number of pages and blocks and the pages without text, and count the blocks no item cites yet. The assistant's instructions say how to read a PDF material and how to cite it.
- A source that cites a PDF names the page and the block: `inputs/a.pdf#p3-2`, or `knowledge/<library id>/a.pdf#p3-2` for a knowledge base document. The excerpt is checked verbatim against that block, or from that block into at most five following blocks of the same page; an excerpt cannot cross a page. Before the comparison both sides are normalised, because the text layer of a PDF often writes ordinary characters as look-alikes: radical characters become ordinary Han characters, full-width and half-width forms are unified, and whitespace and hyphens are dropped. This applies to PDF sources only.
- A knowledge base search returns PDF passages with their page and blocks, such as 第 3 页第 2 到 4 块 ("page 3, blocks 2 to 4"); PDF documents are split into chunks page by page.
- Generated documents and the Word export write a PDF source as the file name and the page, such as inputs/a.pdf（第 3 页）. The work summary names a PDF material by its own name, as it does for Word materials.
- Interface: the upload extensions in `GET /api/v1/service` include `.pdf`; a PDF in the list of materials carries `pdf: {pages, units, no_text_pages}`, and the files generated from it carry `derived_from`; `GET …/materials/raw` answers a PDF with `application/pdf` and `GET …/materials/content` with its text; a search hit in a PDF document has `first_unit`, `last_unit` and `units`. See **PDF materials** in section 5.1 of the API reference. The limits on pages, characters and seconds are in a new section **PDF 解析** of the startup profiles, each with a default.
- The desktop packages carry the files of [pdfjs-dist](https://github.com/mozilla/pdf.js) 6.4.299 (Apache-2.0) that the task service uses, in `backend/vendor/pdfjs-dist/`, with their licence files; the build checks them by reading a PDF.

### PDF materials in the page

- A PDF material is shown in the Materials tab page by page, as it is, with a text layer for selecting. Only the pages in view are drawn, so a long file opens quickly. The bar above the pages shows the current page and the page count, with **缩小**, **放大** and **适应宽度** ("fit the width"); a file opens fitted to the width of the tab. **查看** ("view") on the task page shows a PDF page by page too.
- Clicking a source that comes from a PDF scrolls to its page, frames the block the source points to and marks the excerpt character by character. The page works out which block it is, and whether the excerpt runs on into the following blocks, by the same rule that checks the source when it is saved. When the excerpt cannot be marked, the block is still framed and a line above says why.
- A source from a PDF is labelled with the file name and 第 N 页 ("page N"), the page of the PDF itself. The chapter follows when the file has bookmarks and the page can be told to belong to one of them; when more than one bookmark points to the page, the label stops at the page.
- The file's bookmarks are listed under **目录** ("contents") below the file name; a file without bookmarks says so and lists its pages instead.
- Pages with no readable text (usually scanned images) carry a note, and the file name line and the task page's list of materials say how many such pages a file has. A line of small print says that tables in a PDF are read row by row, not cell by cell.
- Sentences cited by an item are underlined in the PDF and open the item when clicked; selecting a passage brings up the same action bar as in other materials.
- A source that comes from a PDF document of a knowledge base is labelled with the library, the document and 第 N 页. Opening it still shows the text of the document; knowledge base documents are not shown page by page yet.
- When the page cannot open a PDF or cannot draw one of its pages, it shows the file in the browser's own PDF viewer instead, with the line **这个浏览器里只能按页显示，不能标出摘录。** above it; clicking a source or an entry of the contents then only jumps to the page.
- The page draws a PDF with the legacy build of pdf.js 6.4.299, the version the task service uses, loaded only when a PDF material is opened. Its character maps, standard fonts, colour profile and image decoders are part of the built page (about 3 MB).

### Replacing a material

- A material that has not entered the conversation can be replaced with another file: on the task page such a material has **替换** ("replace") beside **删除**. You choose a file, confirm, and the material is the new file; the old file and the files generated from it are gone, and a Word or PDF file gets its generated files anew. The new file may have another name and another type, and is taken in by the rules of an upload. When the new file cannot be stored, the old material stays as it was.
- Once the material has entered the conversation, **替换** is grey and the request is refused with 这份材料已经进入了对话，不能替换；请上传一份新材料，并告诉助手以新的为准。 ("this material has entered the conversation and cannot be replaced; upload a new material and tell the assistant to go by the new one").
- After a material is deleted or replaced on the task page, **查看** shows the file that is there now, for Word and PDF materials alike. Before, a Word file uploaded under the name of a deleted one was still shown with the old content until the page was reloaded. An open work view drops what it had read of a PDF material when the material is removed or replaced.
- Interface: `POST …/materials/replace?path=…`; a refusal answers `rejected`; open work views are updated by `material_removed` with `replaced_by` followed by `material_added` with `replaces`.

### Work view and conversation

- The task status message at the top of a conversation is folded into one line. The message is written for the assistant (the state of the task, the list of materials and knowledge bases, how to cite them) and used to fill the top of the conversation. The line gives the gist, for example **助手开始这条会话时看到的任务状况：2 份材料 · 2 个知识库 6 份文档 · 完成条件 1/3 · 问题 0 条未解决** ("the task as the assistant saw it when it started this session: 2 materials, 2 knowledge bases with 6 documents, completion conditions 1/3, 0 open issues"); for a resumed session it reads **助手续接这条会话时看到的变化：新增 2 条、修改 1 条、新材料 1 份** ("what had changed when the assistant resumed this session"). Click the line to see the full text, click again to fold it. The notes about what you did on the page are shown as before.

- In the interface, `system_note` now carries `kind` (`task_status` or `reply_fallback`), which the documentation already listed but the service did not send, and a task status message carries `details`, the facts the line is written from.

### Sources

- A source now says which element of the task an item rests on. An item can cite any other item of the task, not only a domain note: the kind is **条目** ("item"), the locator is the cited item's id, and the excerpt is checked verbatim against the cited item's current content. The cited item must exist, must not be deleted and cannot be the item itself; an item added or changed earlier in the same save can be cited.
- When an item is cited, the revision it had at that moment is recorded. If the cited item is changed later, the source is marked **依据已变：DN-002 在这之后改过（引用时是修订 2，现在是修订 5）** ("the basis has changed: DN-002 was changed after this; revision 2 when cited, revision 5 now"); if it is deleted, the source says **DN-002 已经删除** ("DN-002 has been deleted"). The mark goes away when the assistant writes the source again. Carrying a source over while other fields change, editing a field on the page and undoing do not count as citing again.
- The details of an item that other items rest on have a line **被谁依据** ("cited by") listing them. Domain notes keep their fuller section **被哪些条目引用** ("which items cite it").
- **助手补充** ("added by the assistant") must carry a reason: the assistant writes it in the excerpt, a source of this kind without one is refused, and the page shows it after **理由：** ("reason:"). The assistant no longer writes a locator for this kind.
- Two kinds were renamed in the database and the interface: `执行者补充` is now `助手补充`, and `领域说明` is now part of `条目`. The assistant's tools still accept the two old names and store the current ones, so the instructions copied into existing task directories keep working. A kind `图` ("diagram") is reserved for an item that rests on a diagram; it cannot be used yet, and the assistant's tools refuse it.
- Task data from the interface: a source of kind `条目` carries `depends_revision`, `current_revision` and `stale` (`"changed"`, `"deleted"` or `null`), and each item carries `depended_by`. The last three are worked out when the data is read and are not stored.
- Generated documents and the Word export write a source that cites an item as the collection name, the item id and the excerpt, so documents of existing tasks read as before.
- The observatory and the simulation judge read sources under the current kind names; the simulation summary key `执行者补充累计` is now `助手补充累计` (old result files are still read).

Five kinds: use case, class, state, sequence and flowchart, written as Mermaid text; a use case diagram is written as a flowchart. In the conversation a diagram shows up as a step such as **保存了图 D-001（用例图：读者用例）**. A diagram is not reviewed, does not count towards the completion conditions, and is not part of generated documents or the Word export.
- Before a diagram is saved the task service checks the Mermaid text. A text with a syntax error is not saved; the assistant is told the line and corrects it. After three failed checks in a row it stops and tells you. If the check itself cannot be made, nothing is saved and the assistant says so.

When a node stands for an item, the assistant writes the item id into the node's text and cites the item as a source of the diagram. The revision and the note are on one line above it; the Mermaid text, the sources and **图里画了谁** ("the items drawn in it") are in a column on the right with the tabs **文本** and **来源**, which can be hidden to give the drawing more room. ## [0.4.1] - 2026-10-08

### Upgrading from 0.4.0

- **Sign in to the Codex subscription again.** pi 1.0.4 has a new sign-in entry, and a login made through the earlier one counts as not signed in. Open **设置** ("settings"), add or open the Codex subscription and follow the two steps shown there: run `pi`, type `/login`, choose OpenAI and sign in with the ChatGPT subscription.
- **Choose the language model in the settings once.** The desktop package no longer ships with a default model; until a language model is chosen the assistant is not started and the pages say so.

Model services saved by such a build are given a purpose when the task service starts; one that provided both language and embedding models is split in two.

### Knowledge base

- A knowledge base for reference documents, kept apart from a task's materials: materials are what a task organises into items, the knowledge base holds standards, glossaries, templates and earlier deliverables consulted while doing so. It is divided into libraries; each task uses some of them, and every task uses the library **通用知识库** ("general knowledge base"), which cannot be renamed or deleted. Documents are `.md`, `.txt` or Word `.docx` files of at most 20 MB (the 5 MB limit for materials is unchanged), each labelled with a kind: 规范, 术语表, 模板, 以往的成果 or 其他 ("standard", "glossary", "template", "earlier deliverable", "other"). Documents have no versions: a changed document is uploaded as a new file. The same bytes or the same name in one library are refused, as for materials. Word documents get the same projection files as Word materials.
- The sidebar has a **知识库** ("knowledge base") entry under **任务** ("tasks"). The knowledge base page lists the libraries on the left (new, rename, delete) and the chosen library's documents on the right, with their kind, size and upload time, an upload box and a **删除** ("delete") link for each document. Deleting a library asks first and says that its documents go with it and that tasks using it stop using it. The pages and messages say 知识库 in full, never the short 库.
- On the task page a new card **选用的知识库** ("knowledge bases in use") lists the task's knowledge bases and changes them with **选用别的知识库** ("use other knowledge bases"). An upload on the task page is always a material; reference documents are uploaded on the knowledge base page.
- Documents in the knowledge base are embedded with the chosen embedding model, so that they can be searched by meaning. A document is split into chunks of at most 800 characters (a Word document by the blocks of its segment list, then paragraph by paragraph and table row by table row, Markdown by heading and blank line, plain text by blank line); a table row of a Word document is one line, written `| first cell | second cell |`, is never split between two chunks, and a chunk that starts in the middle of a table repeats the table's header row. Each chunk becomes one array of numbers and records where it is in the source text, and the result is kept in two files beside the document, written only when the whole document is done and removed with it. The task service embeds in the background, one document and one request at a time: an uploaded document is queued at once when an embedding model is chosen, `POST /api/v1/knowledge/embed` starts the rest, and nothing is embedded on startup. `GET /api/v1/knowledge` gives every document a status (not embedded, waiting, embedding with chunks done and total, embedded, failed with the reason), every library a count and the whole knowledge base a summary with `ready`; `GET /api/v1/tasks/{task_id}/knowledge` gives the same summary for the libraries the task uses. A failure that concerns one document (for example text longer than the model accepts) marks that document and goes on; one that does not (the service cannot be reached, no answer in time, the key is refused) stops the whole run with the reason. See **Embedding the documents** in section 11 of the API reference.
- The knowledge base page shows this: a column **换算** ("embedding") with each document's status, a line above the table with 已换算 N / M ("embedded N of M"), a progress bar and the model in use, a **开始换算** ("start embedding") button when documents are left, **重试** ("retry") and the reason under a document that failed, and the reason when the whole run stopped. The page updates itself every two seconds while documents are waiting or being embedded.
- Changing the embedding model, or choosing one for the first time, asks first when the knowledge base already has documents: they have to be embedded with the new model, until then they are searched by keyword only, and a commercial service may charge for it. After confirmation the choice is saved and embedding starts. Changing only the query prefix does not ask.
- Embedding requests to Ollama now carry `truncate: false`, so text longer than the model accepts is an error instead of being cut silently.
- The knowledge base is searched in two ways at once, by meaning and by keyword. By meaning, the sentence is embedded as a query and compared with every chunk, so a passage is found even when the material and the rules use different words. By keyword, the sentence is cut into tokens (one per two adjacent Chinese characters; 第 N 条 is one token, so the number of a rule is found however it is spaced) and every chunk is scored with BM25. The first chunks by meaning are the candidates and the first two by keyword replace the last of them; the first chunk by meaning is never replaced. Three chunks are returned by default and at most five. When the search by meaning cannot be done (no embedding model is chosen, documents are not yet embedded, or the model service fails), the search is not refused: it falls back to keyword only and says so. The task service does the search, `POST /api/v1/knowledge/search`; the response says how the search was done (`mode`, `reason`), which documents were searched by keyword only or not at all (`uncovered_semantic`, `uncovered`), and gives every hit with its rank in each way and its verbatim source text, read at the chunk's position: Markdown and plain text byte for byte including blank lines, a Word document paragraph by paragraph with paragraph numbers, a table cell by cell with its row structure. A caller that disconnects ends the search. See **Searching** in section 11 of the API reference.
- The knowledge base page has **试一试按意思查找** ("try searching by meaning") under the document table: write a sentence, and the most relevant chunks of the chosen knowledge base are listed with their score, document, heading, position and text.
- The assistant uses the knowledge base. The task status message at the start of each conversation lists the libraries the task uses and, on one line each, their documents with name, kind, size and how to cite them; it gives no path and no text of a document, whatever its size. `get_task_status` lists the same, and a resumed conversation gets the list again when the choice or the documents changed. Three rules in the assistant's system prompt and its instructions say how to use it: when the material hands the specifics to another document (按公司规范执行, 见术语表 and the like), the assistant must look the rule up, write the rule itself into the item and add a knowledge base source, whether or not the user mentioned the knowledge base; it searches with a new tool, `search_knowledge`, one thing per search; and what the tool returns is the verbatim source text, within 8192 bytes, from which the assistant copies its excerpts without reading the file again (when not everything fits, the tool says how many chunks are not listed and the assistant narrows the question). When nothing is found, public common knowledge or law is written into the item as the assistant's own addition, with the reason, and anything else keeps the material's wording with a problem item added. Every knowledge base source names the field it supports, and the excerpt of a numbered rule starts at its number. Knowledge base documents are not organised into items. These are instructions to the model; the program checks only the excerpts.
- A source can cite a knowledge base document: the kind stays 文档原文 and the locator is `knowledge/<library id>/<document name>` (plus `#pN` for a Word document). The excerpt is checked verbatim as for materials, and only documents in the libraries the task uses can be cited; a source the item already had is kept unchecked when its document or library is gone. In the work view such a source has the magenta label **知识库** and reads "library name / document name"; clicking it opens the document in a read-only dialog with the excerpt highlighted, and when the document is no longer in the knowledge base the locator cannot be clicked and **这份文档已经不在知识库里** ("this document is no longer in the knowledge base") is written beside it. Review counts these sources when deciding whether two items cite the same place, and generated documents write them as 知识库，出处 library name / document name.
- The task service keeps the knowledge base under a new option, `--knowledge <dir>`, by default `knowledge/` in the user data directory next to `tasks/` and `runs/`. `scripts/dev.sh` passes `TASKWRIGHT_KNOWLEDGE_DIR` (default `./knowledge`), and the desktop package puts it under `TASKWRIGHT_DATA_DIR` when that is set. New endpoints under `/api/v1/knowledge` list, create, rename and delete libraries and upload, read and delete documents; `GET` and `POST /api/v1/tasks/{task_id}/knowledge` read and change the libraries a task uses, and `GET /api/v1/tasks/{task_id}` returns them as `knowledge_libraries`. A task's choice is kept in `knowledge.json` in its task directory; tasks created before this version count as using the general library only. `GET /api/v1/service` has `capabilities.knowledge` and `knowledge_upload`. The task service hands the knowledge root to the assistant in the environment variable `TASKWRIGHT_KNOWLEDGE_ROOT`. See section 11 of the API reference.
- `agent/eval/knowledge/` holds tools that measure how a conversation used the knowledge base (for every expected rule: was it a candidate, was it returned, did the assistant adopt it, cite it correctly and save it) and that compare ranking methods offline. They are not part of the package.

### Task page

### Materials and sources

- A material that has not entered the conversation can be deleted: on the task page such a material has **删除** ("delete"), which asks first. A material has entered the conversation once any session of the task was active after it was uploaded; from then on it cannot be deleted, the delete request is refused with `rejected` and 这份材料已经进入了对话，不能删除。 ("this material has entered the conversation and cannot be deleted"), and the task page no longer shows **删除**. ### Model configuration

- Model services and the models the assistant uses are set up on the new settings page (**设置**) and through the API (section 10 of the API reference): add, change and remove a model service (ollama, llama.cpp, vLLM, DeepSeek, Alibaba Cloud Model Studio with pay-as-you-go billing, another OpenAI-compatible service, or the Codex subscription), fetch its models, find a model's context length, and choose the language model and the embedding model. The task service writes only its own entries, named `taskwright-…`, into pi's `models.json` and `auth.json`; it backs each file up before writing, keeps the five most recent copies, takes the same lock as pi, and does not rewrite a file that contains comments. Model services written into `models.json` by hand are listed read-only, and their language models can be chosen. Keys are never returned, only whether one is set and its last four characters. The configuration can be read and changed from any computer that opens the pages; the service information reports this as `capabilities.model_config`, which is always `true`. A chosen language model is used from the next session opened or created, including a session opened again, because the task service switches pi to it after each start, new session and switched session. The choices are kept in the product's settings file (`settings.json` in the user data directory, or the file named by `TASKWRIGHT_SETTINGS_FILE`); while no language model is chosen, the model in the assistant program's own settings is used, and when there is none the assistant is not started (see below).
- Every model service now has one purpose: it provides language models or embedding models. Adding a model service starts with choosing its purpose, then its kind (the Codex subscription is not offered for embedding models), and the request `POST /api/v1/model-config/providers` requires `purpose`. The list of model services on the settings page is grouped into 语言模型 ("language models") and 嵌入模型 ("embedding models"), a service's details name its purpose under 用途, and the model list no longer has a type column or a type choice when a model is added by hand: a model's type is its service's purpose, so models in the API no longer have `type`. Fetching the model list keeps only the models of the service's purpose for ollama and 阿里云百炼, which can tell the type of a model; the other kinds list all their models. Changing the language model or the embedding model offers only the services of that purpose. An address that provides both types is added twice.
- The language model can be tested. On the settings page the row 助手用的语言模型 has a **测试** ("test") button: a dialog names the model and says that one real request will be sent and that a commercial service may charge a very small amount; after **开始测试** the button reads 正在测试…… and the model cannot be changed until the test ends. The result is written below the row, 这一次测试通过，用时 N 秒。 or 这一次测试没有通过： with the reason, followed by the sentence the model was asked (问模型：…) and what it answered (模型回答：…, or 模型没有回答), and is cleared when the model is changed or the page is reloaded. The new endpoint `POST /api/v1/model-config/test` `{type: "language"}` starts the assistant once outside any task, with the same startup profile and model as for a task but in a temporary directory, with only the tool that reads files and without the task system prompt, has the model read a small file that says how many boxes a shipment has (a number picked at random each time) and say how many there are, and stops the assistant; it answers `{ok, result, model, seconds, tool_calls, question, reply, reason}`, waits at most 90 seconds, runs one test at a time (a second request gets the new error `busy`, 409) and stores nothing. `GET /api/v1/service` has `capabilities.model_test`.
- The embedding model can be tested. On the settings page the row 查找用的嵌入模型 has a **测试** ("test") button too: a dialog names the model and says that one real request will be sent and that a commercial service may charge a very small amount; after **开始测试** the service has the chosen embedding model turn one sentence into an array of numbers. A test that passed reads 这一次测试通过，用时 N 秒。 and shows the sentence that was sent, with the query prefix in front (送去换算的话), and the length of the array (算出来的数字串长度); a test that did not pass reads 这一次测试没有通过： with the reason. Only one test runs at a time: while either model is tested, **测试** and **更换** are disabled on both rows. `POST /api/v1/model-config/test` accepts `type: "embedding"` and answers `{ok, result, model, seconds, question, dimensions, reason}`. The task service now calls the embedding model itself (`backend/src/embedding.ts`): `/api/embed` for ollama, the OpenAI-compatible `…/embeddings` for the other kinds, one request of at most 32 texts (10 for Alibaba Cloud Model Studio), with the query prefix put in front of queries only, not documents.
- The Codex subscription now uses pi's current sign-in entry only. The settings page shows signing in as two steps: the command `pi`, which **复制** ("copy") copies, and the instruction `/login` to type once it has started, with the note 输入后在列表里选 OpenAI，按提示用 ChatGPT 订阅登录。 ("then choose OpenAI in the list and sign in with the ChatGPT subscription as prompted"); the login is read from the `openai` entry of `auth.json`, the model list is pi's list for `openai`, and a model chosen from the Codex subscription is passed to pi as `openai/<model>`. Before, such a model was passed under the product's own name for the model service, which pi does not know, so a Codex model chosen on the settings page could not be used. **After upgrading, sign in once through the new entry**: a login made through the earlier entry (OpenAI Codex (legacy)) counts as not signed in, and the Codex subscription's details say 这一版改用新的登录入口，请重新登录一次。 The development profile's model is now `openai/gpt-6-luna`.
- The Codex subscription's details have a button **更新模型目录** ("update the model catalog"). It asks first, then lets pi fetch its catalog of models from the network once (`POST /api/v1/model-config/providers/{id}/refresh-catalog`) and fetches the model list again; when the update fails, the reason is shown under the button.
- The desktop package no longer ships with a default model. With no language model chosen, and none in pi's own settings, the assistant is not started: the pages show 还没有选定语言模型，助手现在不能工作。 with a button to the settings, and opening a session returns `executor_unavailable` with 还没有选定语言模型，请先到设置里添加模型服务并选定。 **After upgrading, choose the language model in the settings once.**
- Wording of the model configuration. The source of the model that is used while no language model is chosen is given as 助手程序的设置 ("the assistant program's settings"); the API returns it in `fallback.from`, and the settings page, the startup record and the sentence of the model check use the same words. The two `in_use` errors say 查找用的嵌入模型, as the page does. When fetching the model list fails for a Codex subscription that is not signed in, the message ends 请先在命令行里登录，再回到这里点「获取模型列表」。 ("sign in on the command line first, then press 获取模型列表 here"); for its other failures it ends 可以稍后再试。 ("try again later"), and for the other kinds of model service 可以稍后再试，或者手工添加。 ("try again later, or add models by hand"). Without an embedding model the pages say 助手查知识库只按字面找，用词不同的找不到。 ("the assistant searches the knowledge base by keyword only and does not find a passage worded differently").

### Assistant runtime

- Taskwright is now tested with pi 1.0.4, and the release build packages pi 1.0.4 (it was 0.85.1). pi 1.0.4 writes one system message at the start of every session, into the session file and the event archive, and leaves a Node compile cache directory (`node-compile-cache`) in the system temporary directory; neither changes what the task service does. The tests and the expected observatory output follow both.
- The release build installs pi from a lock file kept in the repository (`release/pi/`) instead of packing the globally installed one. pi's own package stopped shipping a lock file with 1.0.1, so two builds could pack different dependencies; now every build packs the same ones, each checked against its checksum. The build stops when the installed pi is not the pinned version or differs from the lock file, and `manifest.json` in a package lists the pi dependencies that were packed (`pi_packages`). A globally installed pi is no longer needed for building; `--pi-dir` still packs an installed one, which must be the pinned version.
- The assistant no longer goes to the network by itself: all startup profiles start pi with `--offline`, so pi does not refresh its catalog of models, check for a new version or download the search tools rg and fd. Requests to the model service are not affected. The desktop package brings rg and fd; on a machine set up by hand, run `pi` once without `--offline` to let it download them, otherwise the assistant's `grep` and `find` tools do not work.
- A turn in which the assistant keeps being refused now stops instead of going on without end. When the assistant has been refused five times in a row since the user's last message, the tool refused for the fifth time ends the run, the page says 助手这一轮一直没有按规矩回答，已经停下。你可以再说一句，让它重新来。 ("the assistant kept failing to answer by the rules and has been stopped; say something more"), and the turn ends as `stopped_by_limit` (a new value of `outcome` and a new `problem` code). What counts is every refusal of `reply`, and the refusals of `save_revision` and `complete_task` for lack of a valid understanding; refusals for invalid input do not count, and the rule that lets a malformed reply through at the fifth attempt is unchanged. Before, a refusal for a missing understanding had no limit at all: a model that never wrote one was asked again and again, one model request per round.
- The output of the assistant's built-in tools is capped, so that one call cannot fill the context. `grep` output above 40 lines or 6144 bytes is cut to its first lines, with a sentence asking for more specific words or several searches, for the materials and the knowledge base alike; one status line (`taskwright-grep-capped`) stays in the archive, where the observatory shows it. `read` of a file under the knowledge base directory without a number of lines reads 120 lines. No call is stopped.

### Task service

- The task service splits what the assistant's program writes into lines at line feeds only. Before, a line whose JSON held the character U+2028 or U+2029, which can come from a material or the conversation, was split into pieces that could not be read, so the event was lost. The program's error output is split the same way, so a lone carriage return there no longer starts a new line either. Inside the task service, starting the program and sending and receiving its lines is now an interface with one implementation, a child process.

### Known issues

- In a knowledge base search the first two chunks by keyword always come into the result, whatever their score, so now and then a chunk that merely shares a few characters with the question takes the place of a closer one.
- The keyword scores are computed anew at every search. With more than about ten thousand chunks in the knowledge bases a task uses, one search takes more than a second.
- **试一试按意思查找** on the knowledge base page shows only the score by meaning and does not say when a chunk came in by keyword; it cannot be used while no embedding model is chosen or documents are still to be embedded, although the assistant can then still search by keyword.
- The limit of five refusals in a row covers refused replies and refusals for a missing or invalid understanding. A revision refused for its content is not counted, and the number of rounds in one run has no limit.
- Nothing is done about large materials: the assistant does not get through a material of several MB.
- When one cell of a Word table is longer than 800 characters, a search returns the whole cell for each piece of it.
- Without the programs rg and fd the assistant's `grep` and `find` tools do not work. The desktop package brings both; on a machine set up by hand they have to be installed, or downloaded by running `pi` once without `--offline`.
- PDF files are not accepted, as materials or in the knowledge base (planned for 0.4.3).
- The assistant may still miss content in the materials, even in short ones. Statements in the materials that contradict each other may be written down as a settled rule, and the same rule may be written as two.
- The review rules have not been verified one by one, so a review verdict is for reference only, and you can overrule it with **保留这种写法** ("keep this wording"). A task created earlier uses the review rules copied when it was created, and an upgrade does not update them.
- When the package (AppImage) runs on a computer without FUSE, it leaves the files it unpacked in the system's temporary directory.
- While a review is running, the progress note in the top right corner covers the top line of the Review tab.
- The screenshots in the tutorial were taken from an earlier version. The task page, the Review tab and the item details look different now; where they differ, follow the text.
- The Windows executable can be built with the same scripts but has not been verified.
- Upgrades do not yet promise that existing tasks keep working. Back up the task directories before upgrading.

### Issue items and sources

- Marking an issue resolved or kept by the user's decision needs a click from the user. `save_revision` refuses to set an issue item's status to 已解决 ("resolved") or 用户决定保留 ("kept by the user's decision") until the user has clicked 已解决 or 先不管，保留 ("leave it for now") on a Choose card that names the issue item, and the issue item and its related items have not changed since that click, whoever changed them; the latest click counts, and typed words do not count. The refusal says to send the card first. A new issue item can no longer be written with either status. Keeping an issue pending from the page is not affected.
- When the assistant updates an item, the item's existing sources are kept. Before, giving a source for a field replaced every source of that field, so adding an entry to a list such as 约束规则 ("constraint rules") dropped the material source of an entry that had not changed. Entries of a list are now recognised by their content, so a source follows its entry when entries are inserted, removed or reordered; before, it stayed at the same position and silently pointed at another entry, or the save was refused when the list became shorter. A source on an entry that was removed goes with it. A source on content the assistant rewrote stays, and the save result reminds the assistant to check it. To remove a source, the assistant relabels the item with sources only, and the save result lists what was removed.
- Your own edits on the page no longer add a source, and they keep the sources of what you did not touch. Before, changing a field replaced every source of that field with one 用户直接修改 ("your direct edit") source quoting the whole new value, so adding an entry to a list dropped the sources of the entries you had left alone. List entries are now recognised by their content in the same way as for the assistant: the sources of untouched entries stay and follow their entries when entries are inserted, removed or reordered, a source on a removed entry goes with it, and a source on a whole list stays. A sentence you rewrote, a plain field or one entry of a list, loses its earlier sources and gets no new one: what an item says counts as your own, its sources only mark which original passages it cites, and who changed what is shown by the revisions. An item may be left with no sources; its details then leave out the 来源 (sources) section, and the generated document writes （无） ("none") for its sources. The 用户直接修改 kind of source is gone: records of it from earlier revisions stay in the database, but they are not carried into new revisions and are left out of the page, the generated document, what the reviewer sees and what the assistant reads. When the assistant changes an item that has no other sources, it must give sources, as before.
- In the review rules, UC-R10 ("do not write in what the material does not have") is removed, since you may add content the material does not have; its number is not reused. The new rules UC-R15 (use cases) and EARS-R10 (non-functional requirements and constraints) check that a cited quote really supports the content it is cited for; content without a source is not checked by them. Both are optional rules, and the bundled task definition switches them off by default, since in a first trial with a real model they failed items that should have passed; you can switch them on for a task in the Review tab. UC-R14 now reads 用例里写到的数值、期限、判定条件要与材料原样一致，不四舍五入，不改比较方向；材料里有而这个用例没有写到的，不算违反这一条。 ("the numbers, periods and conditions a use case states match the material exactly, not rounded and with the comparison unchanged; a value the material has and the use case does not state is not a violation"). Before, it read 材料里的数值、期限、判定条件在约束规则里原样写出。 ("the numbers, periods and conditions of the material are written as they are in the constraint rules"), and the reviewer, which then saw one item at a time, failed use cases for not repeating numbers that other items already state. Tasks created earlier keep the rule files and the task definition copied when they were created.
- The reviewer's instructions say that content the material does not mention is not a violation of rules such as UC-R11, and that a point whose source is the user's words or a domain note was settled or confirmed by the user, so it does not break such rules even where the material leaves the matter open.
- The reviewer sees the task's other items as background, after the item's sources: related items in full (a document source in the same material paragraph, the same user message or domain note, the domain note the item cites, an issue item that refers to the item or that it refers to) and every other item as a one-line summary, with a cap of 10,000 characters. Its instructions say that content of the material already written in another item does not count against the item under review. Before, it saw one item at a time: when a fine was written as two constraints, one for the daily rate and one for the upper limit, the one with the daily rate failed for leaving out the upper limit, and when the two were merged again, the merged one failed for saying two things. A verdict does not follow the other items: when another item changes or is deleted later, earlier verdicts stay. This applies to tasks created earlier too, since the reviewer's program and instructions are shared.
- An item's details list only the unresolved issues that concern it. Resolved issues and issues kept by your decision are no longer shown there as dimmed cards with their outcome; they remain in the 问题 (issues) tab, and the revisions show how each was settled. The heading reads 挂在这条上的问题 N 个 ("N questions on this item") and counts only those; when none is left, the part is not shown, and a card you keep pending disappears once the change is saved. Opening an item from a resolved or kept issue in the 问题 tab still shows ‹ 回到问题列表 ("back to the question list") at the top, but no longer that issue's card, and the other unresolved issues are listed without folding.

### The earlier Python task service is removed

- The earlier Python task service (`server/`, `taskwright_server`) is removed from the repository; the TypeScript task service in `backend/` replaced it in 0.3. Installing, testing and building no longer need it: `make install`, the CI and the worktree setup install only the observatory, and `scripts/test-all.sh` no longer runs its tests. The side-by-side comparison with it (`backend/compare/` and its saved outputs) is removed too; what it checked is covered by the backend's own tests, among them new end-to-end cases with a real assistant.
- Direct operations no longer accept `unconfirm` (withdrawing a confirmation), which had no entry on the page; it is answered with 400 `bad_request`, like the earlier retired `confirm`. Withdrawals already in a task database are still read and shown.
- A review request no longer carries a force-review field; the task service no longer passes on `force`, which had no effect.
- The task service can be started with `--port 0`, which lets the system pick a free port; the log, the service info and the task locks carry the port actually used.
- The packages carry only the desktop launch profile; the development and test profiles are left out. The notes in the launch profiles no longer use internal program names.
- The AppImage build uses pinned releases of appimagetool and of the AppImage runtime, checked against their checksums, and hands the checked runtime to appimagetool, which no longer downloads it by itself.

### Known issues

- The assistant may still miss content in the materials, even in short ones. Statements in the materials that contradict each other may be written down as a settled rule, and the same rule may be written as two.
- The review rules have not been verified one by one, so a review verdict is for reference only, and you can overrule it with **保留这种写法** ("keep this wording"). No rule checks for now that a source the assistant gives matches the content it is given for: the two rules that do this are switched off by default and can be switched on in the Review tab.
- When you add a value by hand that the materials do not have, the review points it out once; click **保留这种写法** to keep it.
- A task created earlier uses the review rules copied when it was created, and an upgrade does not update them. After an upgrade, earlier review verdicts are not reviewed again automatically; an item is reviewed in the new way only after the item or the review rules change.
- The assistant's program goes online to look up its model catalog when it starts, and on a computer without internet access the default model is not recognised. The next version will let you configure the model in the interface and will not go online by default.
- When the package (AppImage) runs on a computer without FUSE, it leaves the files it unpacked in the system's temporary directory.
- While a review is running, the progress note in the top right corner covers the top line of the Review tab.
- The screenshots in the tutorial were taken from an earlier version. The Review tab and the item details look different now; where they differ, follow the text.
- The Windows executable can be built with the same scripts but has not been verified.
- Upgrades do not yet promise that existing tasks keep working. Back up the task directories before upgrading.

## [0.3.0-alpha] - 2026-09-28

In 0.3 the task service is rewritten in TypeScript, so the task service, the web pages and the assistant need only Node, and the product can be started from a single executable; the observatory and the simulator are still Python programs. Word materials are read by the assistant as Markdown, with a segment list and a location table beside them. Reviews, uploads and completing a task follow stricter rules.

### Completing a task

- Completing a task needs a click from the user; typed words such as 完成吧 ("finish it") do not count. When every completion condition is met at the end of the assistant's turn, the assistant asks with a Choose card that states the facts and what submitting means, with the options 已完成，提交交付物 ("finished, submit the deliverable") and 还没完成，继续修改 ("not finished, keep editing"). When the conditions become met through what the user does on the page while the assistant is not working, the work view shows a green bar above the items with the same question and one button, 已完成，提交交付物; it asks for confirmation and then completes the task without starting the assistant. The bar is hidden while the assistant works or while its card asking the same question is unanswered.
- The agreement holds as long as the deliverable has no new revision; reading items, reviews and kept wordings create no revision. The latest click counts. `complete_task` checks the completion conditions first and the agreement second, and a refusal says which is missing. From the page the task is completed through a new direct operation, `submit_deliverable` (`fields.revision_no`, the revision the page showed), with the user as the actor and a note in the conversation; a revision that is no longer the latest is refused. In the conversation a refused `complete_task` step reads 完成任务没有做成 ("completing the task did not succeed") instead of 完成任务被拒，完成条件还没满足 ("completing the task was refused, the completion conditions are not met yet"), since the call can now be refused although every condition is met.
- The hint 还有 N 条未读 ("N items unread") under a reply card appears only when unread items are the only condition left before the task can be completed; before, it also appeared while items still awaited review.

### Reviews

- An item is reviewed once per revision and rule set. The 仍要重评 ("review again") link and its confirmation are gone, and `force` no longer has any effect. An item is reviewed again after it changes or after the rules change. The greyed-out **Review this item** (评审这条) says why, and for an item that failed and was not kept it adds that the item can be changed and reviewed again, or its wording kept.
- One shared rule decides the review result everywhere: the item badge, the filters, the completion conditions, the Review tab, the task page, the generated document and what the assistant reads. For tasks that hold several reviews of one revision from 0.2, the latest review under the current rules counts, and a kept wording counts only if it was kept after that review. Stored reviews are not changed.
- A failed review whose wording you kept is no longer shown as failed, and it is not counted among the passed items either; for the completion conditions it still counts as passed, as in 0.2. The summary line above the item list counts it as 已保留写法 N ("wording kept"), the 评审不通过 filter lists only failed items that were not kept, a new filter 已保留写法 lists the kept ones, and the deliverable board on the task page shows 评审通过 N/M · 已保留写法 K.
- After the review rules change, a finding made under the earlier rules reads 按改之前的规则评出，不再算数 ("made under the earlier rules, no longer counts") in the Review tab, has no action links, and is left out of the tab's badge and of **Only open**. The generated document writes 未评审 for an item that has no review under the current rules.
- Reviews and kept wordings in the task data (`items[].reviews[]`, `items[].waivers[]` and the reviews in an item's revisions) carry `seq`, the number of the event they were recorded at. Reviews made now are recorded with `forced` false, and the `forced` list of `review_batch` is empty.
- Clicking **Review** (评审 N 条待评审的条目, "review the N items waiting for review") right after the assistant had replied often showed nothing until the first item had been reviewed, and a second click was refused. The button now greys out and 评审中 0/1 ("reviewing 0/1") appears as soon as the review starts.
- **Let the assistant fix this** (让助手照这条改) names the reviewer's suggestion first and the problem after it when the finding has a suggestion; before, it prefilled only the problem, which could read as the opposite of the suggested change.

### Word materials

- The text written beside each uploaded `.docx` for the assistant is now Markdown (`<name>.docx.md`) instead of plain text. Headings keep their level and Word's automatic numbering is written in front of them; list items use `-` or `1.`; tables are Markdown tables with one row per Word row, merged cells marked `（同左）` and `（同上）`, nested tables flattened into the outer cell; pictures are extracted to `<name>.docx.media/` and linked where they appear, on a line of their own when they stand in a heading; text-box text is written as a quote without a paragraph number and cannot be cited; the text inside equations is written in order as plain text. Every paragraph keeps its number, written `[pN]` in front of its text. The counting rule, the source form `inputs/a.docx#pN` and the verbatim check are unchanged.
- Word files in tasks created with 0.2 are still read: when a Word file has only the old `<name>.docx.txt`, the assistant, the excerpt check and the Materials tab read that file. Such files have no segment list on disk and no location table, so the Materials tab shows no sections for them and their source labels leave the chapter out. File names ending in `.docx.md` or `.docx.txt` are reserved.
- A segment list is written beside each Word material on upload (`<name>.docx.segments.json`): blocks at headings, each with its paragraph and line range. The list is recomputed when the `材料分段` parameters of the launch profile change. The assistant's skill tells it to read the list first, read long materials a few blocks at a time and save before reading on. The task status message states each Word material's paragraph and block count and, on a resumed session, how many paragraphs no item cites; `get_task_status` lists every block with the number of items citing it. The Materials tab shows the same per section under **按章节看引用** (sections and citations), greys sections no item cites, and scrolls to a section when it is clicked.
- The assistant's tool allowlist adds the built-in `grep` and `find`, so it can find paragraphs by words instead of reading from the top.
- A location table is written beside each Word material on upload (`<name>.docx.locations.json`): the headings by paragraph number, with the level and the heading text, the automatic number written as Word shows it (for example 第一章 总则). The chapter in a Word source label comes from this table; the chapter of a cited paragraph is the nearest heading at or before it, and a paragraph in a table cell that uses a heading style is not a chapter. The projection and the table take the heading text from the same code.
- Word headings that declare their level only through the style name are recognized. A paragraph's heading level comes from, in order: its own outline level; its style's outline level, looked up through the styles it is based on; the style name `heading N` or `标题 N`. Before, a file whose level-1 heading style carries no outline level (as LibreOffice writes it) lost all its level-1 headings, and the Materials tab put sources and citation counts under the wrong section.
- Derived files (projections, segment lists, location tables) are marked with `derived_from` in the materials API and are not listed or counted as materials in the pages. **View** on a Word file on the task page shows the file page by page in its original layout.
- When the Materials tab or **View** cannot draw a Word file, the page shows a fixed note instead of the rendering library's English error, and the hint about the original layout above the file is left out: 这份 Word 文件在这里显示不出来，但文件已经上传好了：助手仍然能读到它的内容，条目的来源仍然有效，不需要重新上传。 The library's error goes to the browser console. The source labels of such a file keep the file name and the chapter and leave out the page and the position on the page.
- Word files that could not be shown at all are now shown: a file with an equation whose brackets, bar or group character carried no properties, and a file whose automatic numbering is set in a paragraph style without a level.

### Uploading materials

- **Not backward compatible:** an upload whose name is taken by a material with other content is refused with `name_taken` (409) instead of being stored as `<name>-2.<ext>`. Names count as the same when they differ only in case, in Unicode normalization (NFC) or in white space at either end. Materials already stored under such names are left as they are.
- An upload whose bytes are the same as those of a material already in the task, whatever its name, is refused with `duplicate_content` (409). Both refusals give the existing material's path in `data.path`.
- `GET /api/v1/service` gives the upload rules: the size limit and its message (`upload.max_bytes`, `upload.too_large_text`), the extensions (`upload.extensions`), and the accepted types and the refusal written out for people (`upload.types_text`, `upload.unsupported_type_text`). The pages take the hints from there and refuse a file that is too large or of another type before sending it. Before, a file over 5 MB sent through the web development server showed 请求没有成功（HTTP 502）.

### Conversation and work view

- A turn the user stopped, or one that failed, says so. Under the summary line of such a turn an amber line reads 这一轮是你让助手停下的。 ("you stopped the assistant in this turn") with the revisions the turn saved and a tag that opens them, or 这一轮因为出错停下了，助手没有做完。 ("this turn stopped because of an error and the assistant did not finish"). The line stays after a reload; before, a stopped turn looked like a finished one and a failed turn disappeared from the conversation after a reload. A failed turn has its own notice, with the new `problem` code `failed`. `work_summary` carries `outcome` with the values of `work_ended`. The `outcome` of `work_ended` is decided by the turn's last assistant message, so a turn whose model call failed and was then retried successfully reports `replied` or `no_reply` instead of `failed`.
- The work summary no longer says a tool call finished when it has no result: a stopped save was shown as 写好并保存了修订 None：. A save or a completion that did not happen reads 保存修订没有做成 or 完成任务没有做成.
- Texts shown to people no longer write a missing value as None, in notices, in the generated document and in the revision log.
- Prefilled text is added after a draft already typed into the conversation input, on a new line, instead of replacing it.
- **Generate a document from this revision** (按此修订生成文档) on a revision card shows the revision it was clicked on; before, it showed the latest revision the first time it was used.
- The session menu in the work view reads the session list again when the assistant finishes a turn and when the menu is opened; before, it kept the last activity and message count from when the page was opened.
- The task page no longer shows **New session** (新建会话) once the task is completed or abandoned.
- When a message cannot be sent, its text goes back into the input box it came from if that box is still empty.

### When the assistant or the service is not available

- A direct operation on the page (saving or deleting an item, marking items read, undo, review and rule changes, keeping a wording) starts the assistant on demand and resumes the session first, as a message does. The work view no longer turns read-only when the assistant has exited: a note above the input box says it will restart on the next message. The page stays read-only only when the assistant cannot be started.
- Opening or reloading a session page while the assistant cannot be started shows its conversation, items and materials read-only, with the reason above the input box, instead of an error page. The snapshot is then answered with `executor.state` `failed_to_start` and the reason in `executor.text`, worded as in the `executor_state` event, instead of failing with `executor_unavailable`. Every reload tries to start the assistant again.
- Notices about the assistant's program no longer mention processes, commands or standard error, and they name pi only when the program cannot be found: 找不到助手的程序（pi），请检查安装。 ("the assistant's program (pi) cannot be found, check the installation"). When the system refuses to start it, the notice gives only the system's error code, for example 助手没有启动起来，系统原因：EACCES. The command and the system's own message go to the backend log and to the `detail` of the error.
- The note above the input box wraps long text inside the box. While the input box cannot be used, its placeholder says 现在不能在这里输入，原因见上方。 instead of repeating the note.
- The reconnecting notice says changes cannot be sent until the connection is back. After about a minute without a connection it becomes a lasting message that the service may have stopped, and the page retries every 30 seconds. A failed request says the service cannot be reached instead of mentioning the backend.
- The service tells open pages that it is stopping (`service_exiting`, with the run mode in `mode`) before it closes the event streams. Open work views then show that the service has exited or stopped, and stop reconnecting.
- Going back to an earlier session, or resuming one after the task service restarted, could put the assistant into a new, empty session without any error when the service was started with relative `--tasks` and `--runs` paths. The service now uses absolute paths, and after resuming or switching it checks that the assistant reports the requested session; if not, it sends nothing and answers `session_resume_failed`.

### Source checks

- A document source holds one continuous passage: for a Word file the excerpt must start in the cited paragraph and may run on into at most the next five. An excerpt that puts separate passages into one source is refused with a note to write one source per passage. Blank lines in an excerpt count as white space; before, passages separated by a blank line were saved as several sources, and such an excerpt is now refused.
- When an excerpt is not in the paragraph named by the source and occurs in several other paragraphs, the refusal lists the nearest ones with their table positions and asks the assistant to choose by context, instead of pointing to a single one. Pointing to one paragraph led the assistant to save sources that matched word for word but pointed to the wrong place.
- An excerpt taken from a text box in a Word file is refused with a note that text-box text cannot be cited.

### Task service in TypeScript

- `backend/`: the task service is rewritten in TypeScript and run directly by Node 24 with no third-party dependencies. `scripts/dev.sh` and `make dev` start it (`node backend/src/main.mts`). `--mode desktop|server` picks the default bind address; `GET /api/v1/service` reports the running mode, port and capabilities; a taken port falls back to the next free one.
- The earlier Python task service stays in `server/` for comparison and is no longer started by the scripts. Backend tests and `backend/compare/` compare with saved outputs of the Python service (`--against fixtures`). The launch profiles and the assistant's system prompt moved to `backend/profiles/` and `backend/prompts/`. The fake model endpoint used by tests has a TypeScript version in `backend/fake_model/`, and `observatory/archive-format.md` states the format of the archive files.
- `--web <directory>`: the task service serves the built web pages from that directory.
- When starting the assistant's program fails at once, the service closes the archive files of that start and leaves no empty ones behind.

### Packages

- `release/`: build scripts for a single executable (Linux and Windows) and a Linux AppImage. The packages carry the task service, the built web pages, the assistant's program and its extension, and the `rg` and `fd` programs that `grep` and `find` need. Starting a package opens the browser on the task list; starting it again while it runs only opens the browser. Data goes to `~/.local/share/taskwright/` on Linux and to `%LOCALAPPDATA%\Taskwright` on Windows, or to `TASKWRIGHT_DATA_DIR`.
- Desktop profile `desktop.json` for the packages. In desktop mode the task service uses the default provider and model from the assistant program's `settings.json` when both are set, checks at startup whether the model is registered or logged in, and reports the result in `GET /api/v1/service`. When no model service is set up the pages show a notice with a link to the deployment guide.
- In desktop mode the local-user menu has **Exit service** (退出服务), which asks for confirmation and then shows a service-stopped screen (`POST /api/v1/service/exit`; `capabilities.exit` in `GET /api/v1/service` is `true` only in desktop mode and for requests from this computer). This endpoint is meant for the 0.3 packages and may not stay.

### Observatory, simulator, scripts and documentation

- The observatory reads a `--runs` directory that holds the task archive directories again on every read, so tasks created after it started appear without a restart. Without `--workspaces` it picks the `tasks/` directory next to `runs/`, even while `runs/` holds no task yet.
- The simulator (`sim/`) no longer uses the Python task service. `python3 -m sim.run` starts the TypeScript task service, and the simulated user is started and driven by a Node driver (`sim/user_agent_driver.mts`) that uses the task service's session class. The judge checks the completion conditions through the observatory. Running the simulator needs Node.js, the assistant's program and a `python3` that can import the observatory package, but not the `server` package. When the simulated user cannot be started or its driver stops, `record.json` gives the stop reason 模拟用户不可用：<reason>.
- `scripts/tui.sh` opens the assistant program's own terminal interface for a task and replaces the Python `tui` client; the `chat` terminal client is no longer documented.
- `web/mock/`, the web mock server, is removed. The web development server proxies to the local task service, and `scripts/dev.sh --demo` starts the task service on the fake model with a demo task.
- `scripts/check-public.sh` also catches home paths written with a tilde and looks inside gzip-compressed files. `examples/library-lending/run.sh` runs from start to end again, and a backend test runs it.
- Documentation now matches the code in four places: withdrawing a confirmation does not make an item unread again; **Answer** (回答) on a question card stays available while the assistant works as long as its box is empty; a rule made required for the task can be switched off directly; the observatory's `--runs` takes the task service's `runs/` directory.

### Known issues

- Until the assistant's skill is updated, the assistant may try to complete the task without asking, or ask with a card that lacks the right option, and be refused once before it asks with the right card. Completing through the assistant can take an extra round; the green bar on the page is not affected.
- The Windows executable can be built with the same scripts but has not been verified.

After it gets an answer for a provider it does not ask again for that provider for four hours. When the site cannot be reached, it asks again at the next start. The requests carry no task content. - Open questions follow the items they concern: list rows show how many unresolved questions point at an item, the item detail lists those questions with an answer box and a keep-pending button, and following a question's link to an item offers a way back to the question list.

## [0.1.0-alpha] - 2026-09-24

First public release.

### Added

- Task type for writing a software requirements specification (`task-types/srs-authoring`).
- Agent built on pi, limited to eight tools; it changes the deliverable only through `save_revision`.
- A platform skill shared by all task types, separate from each task type's own skill.
- Direct operations in the interface: edit, delete, confirm, withdraw a confirmation, keep pending, undo a revision.
- One revision sequence per task; every item is identified by its id and a revision number.
- Web interface with a Revisions tab, field-level change marks since the last confirmation, and adjustable font size.
- One writer at a time and strict turn-taking between the user and the agent.
- Markdown documents generated from a chosen revision, with readable sources.
- HTTP/SSE task service, terminal client, read-only observatory, and a simulated user for test runs.
- Documentation in English and Chinese, and a GitHub Actions workflow for checks and tests.
