# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Task page

- The task page is rebuilt as an overview with six parts: breadcrumb, header (name, status, task type, **生成文档** and **新建会话**, creation time and last activity), a completion bar, the deliverable, the session list, and the materials and knowledge base cards side by side.
- The completion bar shows a score such as 完成条件 1/3 and one line per condition: a green tick for a condition that is met, an amber ring for one that is not, with the items still missing; the conditions of collections that have no items yet are gathered into one grey line and do not count in the score. When every condition is met the bar becomes one sentence.
- The deliverable shows one card per collection, each in its own colour, with the number of items and 评审通过 N/M · 已读 N/M; the longer explanation moved into the card's tooltip, and a collection without items has a grey card. Clicking a card opens the work view of the most recently active session with the items area on that collection's tab; the work view address takes an optional `?collection=<name>` for this.
- The task page now lists the task's sessions: the first sentence, the last activity and the number of revisions each session produced, most recently active first. The task detail and the session list give `revision_count` for every session.
- The materials card is a table with name, size, upload time, **查看** ("view") and, for a material that has not entered the conversation, **删除** ("delete"). The dialog that asked what an uploaded file was for is gone.

### Knowledge base

- A knowledge base for reference documents, kept apart from a task's materials: materials are what a task organises into items, the knowledge base holds standards, glossaries, templates and earlier deliverables consulted while doing so. It is divided into libraries; each task uses some of them, and every task uses the library **通用知识库** ("general knowledge base"), which cannot be renamed or deleted. Documents are `.md`, `.txt` or Word `.docx` files of at most 20 MB (the 5 MB limit for materials is unchanged), each labelled with a kind: 规范, 术语表, 模板, 以往的成果 or 其他 ("standard", "glossary", "template", "earlier deliverable", "other"). Documents have no versions: a changed document is uploaded as a new file. The same bytes or the same name in one library are refused, as for materials. Word documents get the same projection files as Word materials.
- The task service keeps the knowledge base under a new option, `--knowledge <dir>`, by default `knowledge/` in the user data directory next to `tasks/` and `runs/`. `scripts/dev.sh` passes `TASKWRIGHT_KNOWLEDGE_DIR` (default `./knowledge`), and the desktop package puts it under `TASKWRIGHT_DATA_DIR` when that is set. New endpoints under `/api/v1/knowledge` list, create, rename and delete libraries and upload, read and delete documents; `GET` and `POST /api/v1/tasks/{task_id}/knowledge` read and change the libraries a task uses, and `GET /api/v1/tasks/{task_id}` returns them as `knowledge_libraries`. A task's choice is kept in `knowledge.json` in its task directory; tasks created before this version count as using the general library only. `GET /api/v1/service` has `capabilities.knowledge` and `knowledge_upload`. See section 11 of the API description.
- The sidebar has a **知识库** ("knowledge base") entry under **任务** ("tasks"). The knowledge base page lists the libraries on the left (new, rename, delete) and the chosen library's documents on the right, with their kind, size and upload time, an upload box and a **删除** ("delete") link for each document. Deleting a library asks first and says that its documents go with it and that tasks using it stop using it.
- On the task page a new card **选用的知识库** ("knowledge bases in use") lists the task's knowledge bases and changes them with **选用别的知识库** ("use other knowledge bases"). An upload on the task page is always a material; reference documents are uploaded on the knowledge base page.
- The assistant now uses the knowledge base. The task status message at the start of each conversation lists the libraries the task uses and their documents (name, kind, size, the path to read and how to cite it), and `get_task_status` lists them too; a resumed conversation gets the list again when the choice or the documents changed. The assistant looks documents up with its existing `grep` and `read` tools, searching literally (when it must look and how is in the next entry); knowledge base documents are not organised into items. The task service hands the knowledge root to the assistant in the environment variable `TASKWRIGHT_KNOWLEDGE_ROOT`.
- The assistant's instructions now say when the knowledge base must be consulted and how. When the material hands the specifics to another document (按公司规范执行, 见术语表 and the like), the assistant must look the rule up, write the rule itself into the item and add a knowledge base source, whether or not the user mentioned the knowledge base; when nothing is found the item keeps the material's wording and a problem item is added. A document of at most 4 KB may be read whole; a larger one is searched with `grep` first, with words from the material or their synonyms and never a pattern that matches everything, and then read a few lines at a time, at most 120. Every knowledge base source names the field it supports, and when an item has two or more sources each of them does; the excerpt of a numbered rule starts at its number. The knowledge base section of the task status message now says that the rule must be looked up when the material points to it. These are instructions to the model; the program does not enforce them.
- A source can cite a knowledge base document: the kind stays 文档原文 and the locator is `knowledge/<library id>/<document name>` (plus `#pN` for a Word document). The excerpt is checked verbatim as for materials, and only documents in the libraries the task uses can be cited; a source the item already had is kept unchecked when its document or library is gone. In the work view such a source has the magenta label **知识库** and reads "library name / document name"; clicking it opens the document in a read-only dialog with the excerpt highlighted, and when the document is no longer in the knowledge base the locator cannot be clicked and **这份文档已经不在知识库里** ("this document is no longer in the knowledge base") is written beside it. Review counts these sources when deciding whether two items cite the same place, and generated documents write them as 知识库，出处 library name / document name.
- A locator that is not a knowledge base source must now stay inside the task directory. Before, an absolute path outside it or a relative path leaving it through `..` was read and accepted when the excerpt matched.
- The pages and messages say 知识库 in full instead of the short 库, for example **新建一个知识库**, **删除这个知识库**, **选用别的知识库** and "N 个知识库" in the sidebar. The general library is now called **通用知识库**; a stored library list that still has the old name 通用库 is corrected when the service starts.
- A long path in a system note in the conversation now wraps instead of pushing the note out of the column.
- Documents in the knowledge base are embedded with the chosen embedding model, as the groundwork for searching by meaning. A document is split into chunks of at most 800 characters (a Word document by the blocks of its segment list, then paragraph by paragraph and table row by table row, Markdown by heading and blank line, plain text by blank line), each chunk becomes one array of numbers, and the result is kept in two files beside the document, written only when the whole document is done and removed with it. The task service embeds in the background, one document and one request at a time: an uploaded document is queued at once when an embedding model is chosen, `POST /api/v1/knowledge/embed` starts the rest, and nothing is embedded on startup. `GET /api/v1/knowledge` gives every document a status (not embedded, waiting, embedding with chunks done and total, embedded, failed with the reason), every library a count and the whole knowledge base a summary with `ready`; `GET /api/v1/tasks/{task_id}/knowledge` gives the same summary for the libraries the task uses. A failure that concerns one document (for example text longer than the model accepts) marks that document and goes on; one that does not (the service cannot be reached, no answer in time, the key is refused) stops the whole run with the reason. See **Embedding the documents** in section 11 of the API reference.
- The knowledge base page shows this: a column **换算** ("embedding") with each document's status, a line above the table with 已换算 N / M ("embedded N of M"), a progress bar and the model in use, a **开始换算** ("start embedding") button when documents are left, **重试** ("retry") and the reason under a document that failed, and the reason when the whole run stopped. The page updates itself every two seconds while documents are waiting or being embedded.
- Changing the embedding model, or choosing one for the first time, asks first when the knowledge base already has documents: they have to be embedded with the new model, searching by meaning is unavailable until then, and a commercial service may charge for it. After confirmation the choice is saved and embedding starts. Changing only the query prefix does not ask.
- Embedding requests to Ollama now carry `truncate: false`, so text longer than the model accepts is an error instead of being cut silently.
- The assistant can search the knowledge base by meaning. A new tool, `search_knowledge`, takes one sentence and returns the chunks of the task's knowledge bases closest to it in meaning, each with its score, the document, where to read the original and how to write the locator; it finds a passage even when the material and the rules use different words. The assistant's instructions say when to search literally (the number of a rule or its wording is known) and when by meaning, and that a chunk found by meaning is read in the original before it is cited; the way a source is written does not change. The comparison is done by the task service, `POST /api/v1/knowledge/search`, which embeds the sentence as a query and compares it with every chunk; while documents are still to be embedded it answers `ready: false` and the tool tells the assistant to search literally. A new error, `embedding_failed` (502), reports trouble at the model service while the sentence is embedded. See **Searching by meaning** in section 11 of the API reference.
- A table in a Word document now stays in rows inside a chunk. Before, every cell was a paragraph of its own, so a chunk listed the cells one per line and a found chunk no longer showed which value belonged to which row and column. Now a table row is one line, written `| first cell | second cell |`, a row is never split between two chunks, and a chunk that starts in the middle of a table repeats the table's header row. The version of the chunking rules is now kept per kind of document, so only Word documents embedded before this change go back to 未换算 ("not embedded") and are embedded again with **开始换算**; Markdown and plain text documents are untouched.
- The knowledge base page has **试一试按意思查找** ("try searching by meaning") under the document table: write a sentence, and the closest chunks of the chosen knowledge base are listed with their score, document, heading, position and text.
- The assistant now reaches the knowledge base through `search_knowledge` only. Its system prompt gains three rules: when the material hands the specifics to another document (按公司规范执行, 见术语表 and the like) the rule must be looked up in the knowledge base and written into the item with its source; the knowledge base is searched with `search_knowledge` only; a large file is never read whole in one go. The task status message lists each knowledge base document on one line with its name, kind, size and locator; it no longer gives a path to read and carries no text of the document, whatever the document's size. `grep`, `find` and `ls` are stopped when their scope includes the knowledge base directory (the scope is inside it, or it is inside the scope; symbolic links are resolved first): the call is not carried out, the assistant is told to use `search_knowledge`, and one status line (`taskwright-knowledge-blocked`) stays in the archive, where the observatory shows it. `read` is not stopped: the assistant still reads the original at the place a search gives before it cites anything. When the documents are not all embedded or no embedding model is chosen, `search_knowledge` now asks the assistant to tell the user to embed them or to choose a model, instead of falling back to `grep`; when a search fails it asks for one more try and then for a problem item. The assistant's instructions (section 2, item 4) are rewritten to match, and searching the knowledge base literally is gone from them. Known limitation: without an embedding model the assistant cannot search the knowledge base at all, while three places on the pages still say 只能按字面查找 ("can only be searched literally").

### Materials and sources

- A material that has not entered the conversation can be deleted: on the task page such a material has **删除** ("delete"), which asks first. A material has entered the conversation once any session of the task was active after it was uploaded; from then on it cannot be deleted, the delete request is refused with `rejected` and 这份材料已经进入了对话，不能删除。 ("this material has entered the conversation and cannot be deleted"), and the task page no longer shows **删除**. The task detail marks every material with `deletable`. The file goes together with the files generated from a Word material, the event `material_removed` updates open work views, and the request is refused while the assistant is working. A material an item cites is therefore always there, and a deletion leaves no trace.
- The source tags under each field in the item detail (材料原文, 用户的话, 助手补充 and the domain-note tag) are gone; an item's sources are listed only in its **来源** ("sources") section. A source label for knowledge-base documents gets its own colour, ready for when the assistant cites them.

### Task service

- The task service splits what the assistant's program writes into lines at line feeds only. Before, a line whose JSON held the character U+2028 or U+2029, which can come from a material or the conversation, was split into pieces that could not be read, so the event was lost. The program's error output is split the same way, so a lone carriage return there no longer starts a new line either. Inside the task service, starting the program and sending and receiving its lines is now an interface with one implementation, a child process.

### Model configuration

- Model services and the models the assistant uses can be set up through the API (section 10 of the API reference): add, change and remove a model service (ollama, llama.cpp, vLLM, DeepSeek, Alibaba Cloud Model Studio with pay-as-you-go billing, another OpenAI-compatible service, or the Codex subscription), fetch its models, find a model's context length, and choose the language model and the embedding model. The task service writes only its own entries, named `taskwright-…`, into pi's `models.json` and `auth.json`; it backs each file up before writing, keeps the five most recent copies, takes the same lock as pi, and does not rewrite a file that contains comments. Model services written into `models.json` by hand are listed read-only, and their language models can be chosen. Keys are never returned, only whether one is set and its last four characters. The configuration can be read and changed from any computer that opens the pages; the service information reports this as `capabilities.model_config`, which is always `true`. A chosen language model is used from the next session opened or created, including a session opened again, because the task service switches pi to it after each start, new session and switched session. The choices are kept in the product's settings file (`settings.json` in the user data directory, or the file named by `TASKWRIGHT_SETTINGS_FILE`); while no language model is chosen, the rules of 0.3 apply.
- Wording of the model configuration. The source of the model that is used while no language model is chosen is now given as 助手程序的设置 ("the assistant program's settings") instead of a name that contained the program's name; the API returns it in `fallback.from`, the settings page shows it as given, and the startup record and the sentence of the model check use the same words. The two `in_use` errors say 查找用的嵌入模型, as the page does. When fetching the model list fails for a Codex subscription, the message no longer suggests adding models by hand, which the page does not offer for it: when the subscription is not signed in it ends 请先在命令行里登录，再回到这里点「获取模型列表」。 ("sign in on the command line first, then press 获取模型列表 here"), and for the other reasons it ends 可以稍后再试。 ("try again later"); for the other kinds of model service it still ends 可以稍后再试，或者手工添加。 On the settings page, signing in to a Codex subscription is shown as the two real steps: the command `pi`, which **复制** ("copy") copies, and the instruction `/login` to type once it has started, with the note 输入后在列表里选 ChatGPT Plus/Pro (Codex). The note below no longer points to a **测试** ("test") button the page does not have; it now ends 要确认能用，请选定模型后到任务里试着让助手说一句话。 The tooltip of the search icon in the work view reads 全局查找（还没有做）.
- The language model can be tested. On the settings page the row 助手用的语言模型 has a **测试** ("test") button: a dialog names the model and says that one real request will be sent and that a commercial service may charge a very small amount; after **开始测试** the button reads 正在测试…… and the model cannot be changed until the test ends. The result is written below the row, 这一次测试通过，用时 N 秒。 or 这一次测试没有通过： with the reason, followed by the sentence the model was asked (问模型：…) and what it answered (模型回答：…, or 模型没有回答), and is cleared when the model is changed or the page is reloaded. The new endpoint `POST /api/v1/model-config/test` `{type: "language"}` starts the assistant once outside any task, with the same startup profile and model as for a task but in a temporary directory, with only the tool that reads files and without the task system prompt, has the model read a small file that says how many boxes a shipment has (a number picked at random each time) and say how many there are, and stops the assistant; it answers `{ok, result, model, seconds, tool_calls, question, reply, reason}`, waits at most 90 seconds, runs one test at a time (a second request gets the new error `busy`, 409) and stores nothing. `GET /api/v1/service` has `capabilities.model_test`.
- The embedding model can be tested. On the settings page the row 查找用的嵌入模型 has a **测试** ("test") button too: a dialog names the model and says that one real request will be sent and that a commercial service may charge a very small amount; after **开始测试** the service has the chosen embedding model turn one sentence into an array of numbers. A test that passed reads 这一次测试通过，用时 N 秒。 and shows the sentence that was sent, with the query prefix in front (送去换算的话), and the length of the array (算出来的数字串长度); a test that did not pass reads 这一次测试没有通过： with the reason. Only one test runs at a time: while either model is tested, **测试** and **更换** are disabled on both rows. `POST /api/v1/model-config/test` accepts `type: "embedding"` and answers `{ok, result, model, seconds, question, dimensions, reason}`. The task service now calls the embedding model itself (`backend/src/embedding.ts`): `/api/embed` for ollama, the OpenAI-compatible `…/embeddings` for the other kinds, one request of at most 32 texts (10 for Alibaba Cloud Model Studio), with the query prefix put in front of queries only, not documents.
- Every model service now has one purpose: it provides language models or embedding models. Adding a model service starts with choosing its purpose, then its kind (the Codex subscription is not offered for embedding models), and the request `POST /api/v1/model-config/providers` requires `purpose`. The list of model services on the settings page is grouped into 语言模型 ("language models") and 嵌入模型 ("embedding models"), a service's details name its purpose under 用途, and the model list no longer has a type column or a type choice when a model is added by hand: a model's type is its service's purpose, so models in the API no longer have `type`. Fetching the model list keeps only the models of the service's purpose for ollama and 阿里云百炼, which can tell the type of a model; the other kinds list all their models. Changing the language model or the embedding model offers only the services of that purpose. An address that provides both types is added twice. **Settings from earlier versions are migrated when the task service starts**: a model service with only language models, only embedding models or no models gets its purpose and keeps its name; one with both types is split in two, the embedding models moving to a new service named after the original followed by （嵌入模型）, with the same address and key, and a chosen embedding model follows them. The settings file's `version` becomes 2.
- The Codex subscription now uses pi's current sign-in entry only. Sign in with `pi`, `/login`, choose OpenAI and sign in with the ChatGPT subscription; the login is read from the `openai` entry of `auth.json`, the model list is pi's list for `openai`, and a model chosen from the Codex subscription is passed to pi as `openai/<model>`. Before, such a model was passed under the product's own name for the model service, which pi does not know, so a Codex model chosen on the settings page could not be used. **After upgrading, sign in once through the new entry**: a login made through the earlier entry (OpenAI Codex (legacy)) counts as not signed in, and the Codex subscription's details say 这一版改用新的登录入口，请重新登录一次。 The development profile's model is now `openai/gpt-6-luna`.
- The desktop package no longer ships with a default model. With no language model chosen, and none in pi's own settings, the assistant is not started: the pages show 还没有选定语言模型，助手现在不能工作。 with a button to the settings, and opening a session returns `executor_unavailable` with 还没有选定语言模型，请先到设置里添加模型服务并选定。 **After upgrading, choose the language model in the settings once.**
- The Codex subscription's details have a button **更新模型目录** ("update the model catalog"). It asks first, then lets pi fetch its catalog of models from the network once (`POST /api/v1/model-config/providers/{id}/refresh-catalog`) and fetches the model list again; when the update fails, the reason is shown under the button.

### Agent runtime

- A turn in which the assistant keeps being refused now stops instead of going on without end. When the assistant has been refused five times in a row since the user's last message, the tool refused for the fifth time ends the run, the page says 助手这一轮一直没有按规矩回答，已经停下。你可以再说一句，让它重新来。 ("the assistant kept failing to answer by the rules and has been stopped; say something more"), and the turn ends as `stopped_by_limit` (a new value of `outcome` and a new `problem` code). What counts is every refusal of `reply`, and the refusals of `save_revision` and `complete_task` for lack of a valid understanding; refusals for invalid input do not count, and the rule that lets a malformed reply through at the fifth attempt is unchanged. Before, a refusal for a missing understanding had no limit at all: a model that never wrote one was asked again and again, one model request per round. The work summary now says why a reply was refused (no understanding yet, an invalid understanding, or a malformed reply) instead of always saying its form was wrong.
- Taskwright is now tested with pi 1.0.4, and the release build packages pi 1.0.4 (it was 0.85.1). pi 1.0.4 writes one system message at the start of every session, into the session file and the event archive, and leaves a Node compile cache directory (`node-compile-cache`) in the system temporary directory; neither changes what the task service does. The tests and the expected observatory output follow both.
- The release build installs pi from a lock file kept in the repository (`release/pi/`) instead of packing the globally installed one. pi's own package stopped shipping a lock file with 1.0.1, so two builds could pack different dependencies; now every build packs the same ones, each checked against its checksum. The build stops when the installed pi is not the pinned version or differs from the lock file, and `manifest.json` in a package lists the pi dependencies that were packed (`pi_packages`). A globally installed pi is no longer needed for building; `--pi-dir` still packs an installed one, which must be the pinned version.
- The assistant no longer goes to the network by itself: all startup profiles start pi with `--offline`, so pi does not refresh its catalog of models, check for a new version or download the search tools rg and fd. Requests to the model service are not affected. The desktop package brings rg and fd; on a machine set up by hand, run `pi` once without `--offline` to let it download them, otherwise the assistant's `grep` and `find` tools do not work.

## [0.4.0] - 2026-09-29

0.4.0 finishes the work that 0.3 left open, removes the earlier Python task service, and improves reviews. The Review tab is laid out by what needs your attention, the reviewer sees the task's other items, and two review rules are switched off by default. An item's sources now only mark the original passages it cites, and your own edits no longer add a source.

### Web pages

- The Review tab is laid out by what needs your attention instead of review by review. A top line says how many items have not been reviewed (or must be reviewed again after a rule change), with one button **评审这 N 个条目** ("review these N items"), how far a running review has got, with a thin progress line, and how many problems wait for you, or that every item has passed. Below it, **要处理的** ("to handle") groups the problems by item, one card per item; each problem gives its place, text and fix with **让助手照这条改**, **保留这种写法** and the rule it rests on. With more than three items, the others fold into one line each. Advice, the items that are fine now (passed or wording kept, with **撤销保留**) and the review log (one line per review) are folded below. Problems found on earlier revisions or under earlier rules are no longer shown, and an item changed after its review counts as not yet reviewed. The words 合规, 不合规, 第 N 次评审, 未处理, 已在修订 N 改 and the item revisions are gone from the tab, and so is **只看未处理** ("only open"). The review rules moved from the bottom of the tab into a panel that slides in from the right from the tab's last line. Keeping a wording from a problem keeps the whole item, and when the item has several problems the reason box now says so.
- The deliverable board on the task page no longer shows 评审通过 0/0 and 已读 0/0 in amber for a collection without items; it shows only 0 个条目 ("0 items") and 这个集合还没有条目。 ("this collection has no items yet"). Its grey lines address you throughout; before, one sentence switched to 用户 ("the user") halfway.
- The task page opens an event stream without a session and listens only to `executor_state`: when the assistant finishes a turn it reloads the task, so the last activity and each session's message count and last activity no longer stay as they were when the page was opened. The stream is not opened for a completed or abandoned task and is closed when you leave the page.
- A 502, 503 or 504 without an explanation, which a forwarding layer such as the development server's proxy returns while the task service is stopped or restarting, now reads 连不上任务服务，可能正在重启。请稍后再试；一直不行，请告诉管理员。 ("cannot reach the task service, it may be restarting; try again later, and tell your administrator if it keeps failing") instead of 请求没有成功（HTTP 502）。 ("the request failed (HTTP 502)"). This applies to ordinary requests, to reading a Word file for the original-layout view and to downloading a document; an explanation from the task service itself is still shown as it is.
- Error notes in the material pane, the document preview and the Word original-layout view wrap inside their box; a long string without spaces could run past the right edge before.
- When the input box is disabled or you have unsaved item edits, the send button's hover text is 现在不能发送，原因见上方。 ("you cannot send now; the reason is shown above") instead of repeating the notice above the input box.
- 被 N 个条目引用过 ("cited by N items") on the Materials tab counts every item whose excerpt is found in the material. It used to miss an item whose excerpt overlapped another item's, and dropped further while a passage was highlighted.
- The question on the green submit bar names the collections you must have read that are not reviewed, such as the domain notes, with their count, and says the issues are all resolved or kept pending only when there are issue items; before, it left the domain notes out and always said 没有未解决的问题 ("no unresolved issues").
- After a page reload the conversation stays at the bottom when the revision tags appear; before, it could stop at the top with the last line half hidden behind the input box when the conversation was just over one screen long. It does not scroll if you have scrolled up.
- The review rules, in the panel that slides in from the Review tab, show only a switch, the rule number and the text: the labels 必选, 可选 ▾, 已关闭 and 升为必选 ▾ are gone, and with them the way to make a rule required on the page (`set_review_rules` still accepts it). The panel's top line reads 带锁的不能关；其余的可以关掉，只对这个任务生效。改动只影响之后的评审。 ("rules with a lock cannot be switched off; the others can, for this task only; a change affects only later reviews"). A required rule's switch is green, since the rule is on, with a white lock drawn opposite the knob, and the pointer shows it cannot be clicked; screen readers hear 必选，不能关 ("required, cannot be switched off"), and for the other switches the rule number and whether it is on. Before, a required rule's switch was grey and faded like a switched-off rule. A rule made required earlier shows as on, and its hover text says 这条规则已经升为必选，违反它算问题。 ("this rule has been made required; breaking it counts as a problem").
- An item that passed review shows the sentence the review recorded, for example 评审通过：按 14 条规则逐条核对，没有发现问题。, in a green note where a failed review shows its red banner, with the time and revision of the review. 看这 14 条规则 ("see these 14 rules") lists the rules it checked, each by number and text, and says how many were switched off. When the rules changed after the review, the note says the rules it checked cannot be listed. On the Review tab a passed item is listed among the items that are fine now, and 核对了哪些规则 ("which rules were checked") next to it opens the same sentence and list of rules. Passed items used to show only 合规 ("passed").
- The rule text opened from 违反 UC-R7 ("violates UC-R7") in a review finding shows the rule number and text without the level in brackets; the finding already begins with 问题 ("problem") or 建议 ("advice").
- Selecting a passage in a material shows its three actions in a bar just above the selection, with an icon over each label, instead of in a strip at the bottom of the material pane. The bar has no 不用了 ("not now") button: a click elsewhere or Escape closes it. The note that the actions go to the assistant is in each button's hover text, and 补到当前条目 ("add to the open item") names the item there.
- Opening a session that no longer exists, usually a new session left without a word, shows 找不到这条会话。还没有说过话的会话，在你打开别的会话之后不会保留。 ("this session cannot be found; a session in which nothing was said is not kept once you open another one") with the top bar and a link back to the task page, instead of one line with the session id.
- Choosing **New session** while the assistant is working in the session you are in says 助手正在这条会话里工作，等它做完这一轮再新建会话。 ("the assistant is working in this session; wait for this turn to finish") instead of saying it is working in another session.

### When the assistant is not available

- When the assistant's program exits right after it starts, the work view says 助手现在不可用：助手启动之后立刻退出了。请把这个页面的地址告诉管理员。 ("the assistant exited right after it started; tell your administrator the address of this page") instead of showing what the program wrote to its error output, which could carry file paths and internal words. That text goes to the backend log and stays in `data.detail` of `executor_unavailable`. Other unexpected start errors say 助手现在不可用：助手没有启动起来。请把这个页面的地址告诉管理员。 ("the assistant did not start").
- When the task service cannot prepare the assistant's files before starting it (creating the archive directory, opening the archive files, or backing up and rewriting a session file it resumes; for example no write permission or a full disk), the work view says 助手现在不可用：启动助手之前，任务服务没能写入它要用的文件，系统原因：EACCES。请把这个页面的地址告诉管理员。 with the system's code, or 系统原因：未知 ("unknown") when there is none, instead of the system's English message; the path goes to the backend log only. The archive files opened so far are closed and the empty ones created by that start are removed.

### Conversation and work view

- The task status note at the top of a session opens with 这条会话开始时（time）的任务状况： ("the task at the start of this session") or, when a session is resumed, 接着这条会话继续时（time），上次之后交付物的变化： ("continuing this session, changes to the deliverable since last time"), instead of an opening written for the assistant that named the 执行者 ("executor") and the 扩展 ("extension"). In the note, 执行者在别的会话里做的 N 次 reads 助手在别的会话里做的 N 次 ("done by the assistant in other sessions"), and the line listing the assistant's acts still waiting for an answer is not shown. The assistant still reads the original text; the page gets the same wording live and after a reload.
- A page reloaded while a review is running shows 评审中 ("reviewing") and the greyed-out **Review** button at once, instead of waiting for the next item to be reviewed. When the assistant's program exits in the middle of a review, the work view clears 评审中 and enables the review buttons again without a reload, and after a reload the review that was cut off is no longer shown as running.

### Task service and API

- The snapshot has `review_in_progress`: the review started from the interface that is running now (`op_id`, `done`, `total`, `current`, as in `review_progress`), or null when there is none, the agent is not running, or its progress was written before the agent's current start.
- `step_count` of `work_ended` is computed from the session record, like that of `work_summary`. When a turn was stopped halfway through a message with several tool calls, the calls that never started were counted in the summary but not in `work_ended`.
- The API reference now documents `cleared` in the answer to a stop request (always empty, since no message is queued while the agent works) and says that database event numbers can skip, since a few kinds of records are not pushed.
- An absolute path in a startup profile (`system_prompt_file`, `platform_skill`, the `path` of an extension from the repository) is used as it is; before, it was joined to the repository root.

### Observatory

- The deliverable board follows the latest review of an item's revision and shows a wording kept after it as 已保留写法 ("wording kept"), drawn like a pass; before, a kept item was shown as 评审过，没有通过 ("reviewed, not passed"), and an item that once passed stayed passed after a later failed review. The rule fingerprint is still not taken into account.

### Issue items and sources

- Marking an issue resolved or kept by the user's decision needs a click from the user. `save_revision` refuses to set an issue item's status to 已解决 ("resolved") or 用户决定保留 ("kept by the user's decision") until the user has clicked 已解决 or 先不管，保留 ("leave it for now") on a Choose card that names the issue item, and the issue item and its related items have not changed since that click, whoever changed them; the latest click counts, and typed words do not count. The refusal says to send the card first. A new issue item can no longer be written with either status. Keeping an issue pending from the page is not affected.
- When the assistant updates an item, the item's existing sources are kept. Before, giving a source for a field replaced every source of that field, so adding an entry to a list such as 约束规则 ("constraint rules") dropped the material source of an entry that had not changed. Entries of a list are now recognised by their content, so a source follows its entry when entries are inserted, removed or reordered; before, it stayed at the same position and silently pointed at another entry, or the save was refused when the list became shorter. A source on an entry that was removed goes with it. A source on content the assistant rewrote stays, and the save result reminds the assistant to check it. To remove a source, the assistant relabels the item with sources only, and the save result lists what was removed.
- Your own edits on the page no longer add a source, and they keep the sources of what you did not touch. Before, changing a field replaced every source of that field with one 用户直接修改 ("your direct edit") source quoting the whole new value, so adding an entry to a list dropped the sources of the entries you had left alone. List entries are now recognised by their content in the same way as for the assistant: the sources of untouched entries stay and follow their entries when entries are inserted, removed or reordered, a source on a removed entry goes with it, and a source on a whole list stays. A sentence you rewrote, a plain field or one entry of a list, loses its earlier sources and gets no new one: what an item says counts as your own, its sources only mark which original passages it cites, and who changed what is shown by the revisions. An item may be left with no sources; its details then leave out the 来源 (sources) section, and the generated document writes （无） ("none") for its sources. The 用户直接修改 kind of source is gone: records of it from earlier revisions stay in the database, but they are not carried into new revisions and are left out of the page, the generated document, what the reviewer sees and what the assistant reads. When the assistant changes an item that has no other sources, it must give sources, as before.
- In the review rules, UC-R10 ("do not write in what the material does not have") is removed, since you may add content the material does not have; its number is not reused. The new rules UC-R15 (use cases) and EARS-R10 (non-functional requirements and constraints) check that a cited quote really supports the content it is cited for; content without a source is not checked by them. Both are optional rules, and the bundled task definition switches them off by default, since in a first trial with a real model they failed items that should have passed; you can switch them on for a task in the Review tab. UC-R14 now reads 用例里写到的数值、期限、判定条件要与材料原样一致，不四舍五入，不改比较方向；材料里有而这个用例没有写到的，不算违反这一条。 ("the numbers, periods and conditions a use case states match the material exactly, not rounded and with the comparison unchanged; a value the material has and the use case does not state is not a violation"). Before, it read 材料里的数值、期限、判定条件在约束规则里原样写出。 ("the numbers, periods and conditions of the material are written as they are in the constraint rules"), and the reviewer, which then saw one item at a time, failed use cases for not repeating numbers that other items already state. Tasks created earlier keep the rule files and the task definition copied when they were created.
- The reviewer's instructions say that content the material does not mention is not a violation of rules such as UC-R11, and that a point whose source is the user's words or a domain note was settled or confirmed by the user, so it does not break such rules even where the material leaves the matter open.
- The reviewer sees the task's other items as background, after the item's sources: related items in full (a document source in the same material paragraph, the same user message or domain note, the domain note the item cites, an issue item that refers to the item or that it refers to) and every other item as a one-line summary, with a cap of 10,000 characters. Its instructions say that content of the material already written in another item does not count against the item under review. Before, it saw one item at a time: when a fine was written as two constraints, one for the daily rate and one for the upper limit, the one with the daily rate failed for leaving out the upper limit, and when the two were merged again, the merged one failed for saying two things. A verdict does not follow the other items: when another item changes or is deleted later, earlier verdicts stay. This applies to tasks created earlier too, since the reviewer's program and instructions are shared.
- An item's details list only the unresolved issues that concern it. Resolved issues and issues kept by your decision are no longer shown there as dimmed cards with their outcome; they remain in the 问题 (issues) tab, and the revisions show how each was settled. The heading reads 挂在这条上的问题 N 个 ("N questions on this item") and counts only those; when none is left, the part is not shown, and a card you keep pending disappears once the change is saved. Opening an item from a resolved or kept issue in the 问题 tab still shows ‹ 回到问题列表 ("back to the question list") at the top, but no longer that issue's card, and the other unresolved issues are listed without folding.

### The earlier Python task service is removed

- The earlier Python task service (`server/`, `taskwright_server`) is removed from the repository; the TypeScript task service in `backend/` replaced it in 0.3. Installing, testing and building no longer need it: `make install`, the CI and the worktree setup install only the observatory, and `scripts/test-all.sh` no longer runs its tests. The side-by-side comparison with it (`backend/compare/` and its saved outputs) is removed too; what it checked is covered by the backend's own tests, among them new end-to-end cases with a real assistant.
- Direct operations no longer accept `unconfirm` (withdrawing a confirmation), which had no entry on the page; it is answered with 400 `bad_request`, like the earlier retired `confirm`. Withdrawals already in a task database are still read and shown.
- A review request no longer carries a force-review field; the task service no longer passes on `force`, which had no effect.
- The task service can be started with `--port 0`, which lets the system pick a free port; the log, the service info and the task locks carry the port actually used.
- The packages carry only the desktop launch profile; the development and test profiles are left out. The notes in the launch profiles no longer use internal program names.
- The AppImage build uses pinned releases of appimagetool and of the AppImage runtime, checked against their checksums, and hands the checked runtime to appimagetool, which no longer downloads it by itself.

### Known issues

- The assistant may still miss content in the materials, even in short ones. Statements in the materials that contradict each other may be written down as a settled rule, and the same rule may be written as two.
- The review rules have not been verified one by one, so a review verdict is for reference only, and you can overrule it with **保留这种写法** ("keep this wording"). No rule checks for now that a source the assistant gives matches the content it is given for: the two rules that do this are switched off by default and can be switched on in the Review tab.
- When you add a value by hand that the materials do not have, the review points it out once; click **保留这种写法** to keep it.
- A task created earlier uses the review rules copied when it was created, and an upgrade does not update them. After an upgrade, earlier review verdicts are not reviewed again automatically; an item is reviewed in the new way only after the item or the review rules change.
- The assistant's program goes online to look up its model catalog when it starts, and on a computer without internet access the default model is not recognised. The next version will let you configure the model in the interface and will not go online by default.
- When the package (AppImage) runs on a computer without FUSE, it leaves the files it unpacked in the system's temporary directory.
- While a review is running, the progress note in the top right corner covers the top line of the Review tab.
- The screenshots in the tutorial were taken from an earlier version. The Review tab and the item details look different now; where they differ, follow the text.
- The Windows executable can be built with the same scripts but has not been verified.
- Upgrades do not yet promise that existing tasks keep working. Back up the task directories before upgrading.

## [0.3.0-alpha] - 2026-09-28

In 0.3 the task service is rewritten in TypeScript, so the task service, the web pages and the assistant need only Node, and the product can be started from a single executable; the observatory and the simulator are still Python programs. Word materials are read by the assistant as Markdown, with a segment list and a location table beside them. Reviews, uploads and completing a task follow stricter rules.

### Completing a task

- Completing a task needs a click from the user; typed words such as 完成吧 ("finish it") do not count. When every completion condition is met at the end of the assistant's turn, the assistant asks with a Choose card that states the facts and what submitting means, with the options 已完成，提交交付物 ("finished, submit the deliverable") and 还没完成，继续修改 ("not finished, keep editing"). When the conditions become met through what the user does on the page while the assistant is not working, the work view shows a green bar above the items with the same question and one button, 已完成，提交交付物; it asks for confirmation and then completes the task without starting the assistant. The bar is hidden while the assistant works or while its card asking the same question is unanswered.
- The agreement holds as long as the deliverable has no new revision; reading items, reviews and kept wordings create no revision. The latest click counts. `complete_task` checks the completion conditions first and the agreement second, and a refusal says which is missing. From the page the task is completed through a new direct operation, `submit_deliverable` (`fields.revision_no`, the revision the page showed), with the user as the actor and a note in the conversation; a revision that is no longer the latest is refused. In the conversation a refused `complete_task` step reads 完成任务没有做成 ("completing the task did not succeed") instead of 完成任务被拒，完成条件还没满足 ("completing the task was refused, the completion conditions are not met yet"), since the call can now be refused although every condition is met.
- The hint 还有 N 条未读 ("N items unread") under a reply card appears only when unread items are the only condition left before the task can be completed; before, it also appeared while items still awaited review.

### Reviews

- An item is reviewed once per revision and rule set. The 仍要重评 ("review again") link and its confirmation are gone, and `force` no longer has any effect. An item is reviewed again after it changes or after the rules change. The greyed-out **Review this item** (评审这条) says why, and for an item that failed and was not kept it adds that the item can be changed and reviewed again, or its wording kept.
- One shared rule decides the review result everywhere: the item badge, the filters, the completion conditions, the Review tab, the task page, the generated document and what the assistant reads. For tasks that hold several reviews of one revision from 0.2, the latest review under the current rules counts, and a kept wording counts only if it was kept after that review. Stored reviews are not changed.
- A failed review whose wording you kept is no longer shown as failed, and it is not counted among the passed items either; for the completion conditions it still counts as passed, as in 0.2. The summary line above the item list counts it as 已保留写法 N ("wording kept"), the 评审不通过 filter lists only failed items that were not kept, a new filter 已保留写法 lists the kept ones, and the deliverable board on the task page shows 评审通过 N/M · 已保留写法 K.
- After the review rules change, a finding made under the earlier rules reads 按改之前的规则评出，不再算数 ("made under the earlier rules, no longer counts") in the Review tab, has no action links, and is left out of the tab's badge and of **Only open**. The generated document writes 未评审 for an item that has no review under the current rules.
- Reviews and kept wordings in the task data (`items[].reviews[]`, `items[].waivers[]` and the reviews in an item's revisions) carry `seq`, the number of the event they were recorded at. Reviews made now are recorded with `forced` false, and the `forced` list of `review_batch` is empty.
- Clicking **Review** (评审 N 条待评审的条目, "review the N items waiting for review") right after the assistant had replied often showed nothing until the first item had been reviewed, and a second click was refused. The button now greys out and 评审中 0/1 ("reviewing 0/1") appears as soon as the review starts.
- **Let the assistant fix this** (让助手照这条改) names the reviewer's suggestion first and the problem after it when the finding has a suggestion; before, it prefilled only the problem, which could read as the opposite of the suggested change.

### Word materials

- The text written beside each uploaded `.docx` for the assistant is now Markdown (`<name>.docx.md`) instead of plain text. Headings keep their level and Word's automatic numbering is written in front of them; list items use `-` or `1.`; tables are Markdown tables with one row per Word row, merged cells marked `（同左）` and `（同上）`, nested tables flattened into the outer cell; pictures are extracted to `<name>.docx.media/` and linked where they appear, on a line of their own when they stand in a heading; text-box text is written as a quote without a paragraph number and cannot be cited; the text inside equations is written in order as plain text. Every paragraph keeps its number, written `[pN]` in front of its text. The counting rule, the source form `inputs/a.docx#pN` and the verbatim check are unchanged.
- Word files in tasks created with 0.2 are still read: when a Word file has only the old `<name>.docx.txt`, the assistant, the excerpt check and the Materials tab read that file. Such files have no segment list on disk and no location table, so the Materials tab shows no sections for them and their source labels leave the chapter out. File names ending in `.docx.md` or `.docx.txt` are reserved.
- A segment list is written beside each Word material on upload (`<name>.docx.segments.json`): blocks at headings, each with its paragraph and line range. The list is recomputed when the `材料分段` parameters of the launch profile change. The assistant's skill tells it to read the list first, read long materials a few blocks at a time and save before reading on. The task status message states each Word material's paragraph and block count and, on a resumed session, how many paragraphs no item cites; `get_task_status` lists every block with the number of items citing it. The Materials tab shows the same per section under **按章节看引用** (sections and citations), greys sections no item cites, and scrolls to a section when it is clicked.
- The assistant's tool allowlist adds the built-in `grep` and `find`, so it can find paragraphs by words instead of reading from the top.
- A location table is written beside each Word material on upload (`<name>.docx.locations.json`): the headings by paragraph number, with the level and the heading text, the automatic number written as Word shows it (for example 第一章 总则). The chapter in a Word source label comes from this table; the chapter of a cited paragraph is the nearest heading at or before it, and a paragraph in a table cell that uses a heading style is not a chapter. The projection and the table take the heading text from the same code.
- Word headings that declare their level only through the style name are recognized. A paragraph's heading level comes from, in order: its own outline level; its style's outline level, looked up through the styles it is based on; the style name `heading N` or `标题 N`. Before, a file whose level-1 heading style carries no outline level (as LibreOffice writes it) lost all its level-1 headings, and the Materials tab put sources and citation counts under the wrong section.
- Derived files (projections, segment lists, location tables) are marked with `derived_from` in the materials API and are not listed or counted as materials in the pages. **View** on a Word file on the task page shows the file page by page in its original layout.
- When the Materials tab or **View** cannot draw a Word file, the page shows a fixed note instead of the rendering library's English error, and the hint about the original layout above the file is left out: 这份 Word 文件在这里显示不出来，但文件已经上传好了：助手仍然能读到它的内容，条目的来源仍然有效，不需要重新上传。 The library's error goes to the browser console. The source labels of such a file keep the file name and the chapter and leave out the page and the position on the page.
- Word files that could not be shown at all are now shown: a file with an equation whose brackets, bar or group character carried no properties, and a file whose automatic numbering is set in a paragraph style without a level.

### Uploading materials

- **Not backward compatible:** an upload whose name is taken by a material with other content is refused with `name_taken` (409) instead of being stored as `<name>-2.<ext>`. Names count as the same when they differ only in case, in Unicode normalization (NFC) or in white space at either end. Materials already stored under such names are left as they are.
- An upload whose bytes are the same as those of a material already in the task, whatever its name, is refused with `duplicate_content` (409). Both refusals give the existing material's path in `data.path`.
- `GET /api/v1/service` gives the upload rules: the size limit and its message (`upload.max_bytes`, `upload.too_large_text`), the extensions (`upload.extensions`), and the accepted types and the refusal written out for people (`upload.types_text`, `upload.unsupported_type_text`). The pages take the hints from there and refuse a file that is too large or of another type before sending it. Before, a file over 5 MB sent through the web development server showed 请求没有成功（HTTP 502）.

### Conversation and work view

- A turn the user stopped, or one that failed, says so. Under the summary line of such a turn an amber line reads 这一轮是你让助手停下的。 ("you stopped the assistant in this turn") with the revisions the turn saved and a tag that opens them, or 这一轮因为出错停下了，助手没有做完。 ("this turn stopped because of an error and the assistant did not finish"). The line stays after a reload; before, a stopped turn looked like a finished one and a failed turn disappeared from the conversation after a reload. A failed turn has its own notice, with the new `problem` code `failed`. `work_summary` carries `outcome` with the values of `work_ended`. The `outcome` of `work_ended` is decided by the turn's last assistant message, so a turn whose model call failed and was then retried successfully reports `replied` or `no_reply` instead of `failed`.
- The work summary no longer says a tool call finished when it has no result: a stopped save was shown as 写好并保存了修订 None：. A save or a completion that did not happen reads 保存修订没有做成 or 完成任务没有做成.
- Texts shown to people no longer write a missing value as None, in notices, in the generated document and in the revision log.
- Prefilled text is added after a draft already typed into the conversation input, on a new line, instead of replacing it.
- **Generate a document from this revision** (按此修订生成文档) on a revision card shows the revision it was clicked on; before, it showed the latest revision the first time it was used.
- The session menu in the work view reads the session list again when the assistant finishes a turn and when the menu is opened; before, it kept the last activity and message count from when the page was opened.
- The task page no longer shows **New session** (新建会话) once the task is completed or abandoned.
- When a message cannot be sent, its text goes back into the input box it came from if that box is still empty.

### When the assistant or the service is not available

- A direct operation on the page (saving or deleting an item, marking items read, undo, review and rule changes, keeping a wording) starts the assistant on demand and resumes the session first, as a message does. The work view no longer turns read-only when the assistant has exited: a note above the input box says it will restart on the next message. The page stays read-only only when the assistant cannot be started.
- Opening or reloading a session page while the assistant cannot be started shows its conversation, items and materials read-only, with the reason above the input box, instead of an error page. The snapshot is then answered with `executor.state` `failed_to_start` and the reason in `executor.text`, worded as in the `executor_state` event, instead of failing with `executor_unavailable`. Every reload tries to start the assistant again.
- Notices about the assistant's program no longer mention processes, commands or standard error, and they name pi only when the program cannot be found: 找不到助手的程序（pi），请检查安装。 ("the assistant's program (pi) cannot be found, check the installation"). When the system refuses to start it, the notice gives only the system's error code, for example 助手没有启动起来，系统原因：EACCES. The command and the system's own message go to the backend log and to the `detail` of the error.
- The note above the input box wraps long text inside the box. While the input box cannot be used, its placeholder says 现在不能在这里输入，原因见上方。 instead of repeating the note.
- The reconnecting notice says changes cannot be sent until the connection is back. After about a minute without a connection it becomes a lasting message that the service may have stopped, and the page retries every 30 seconds. A failed request says the service cannot be reached instead of mentioning the backend.
- The service tells open pages that it is stopping (`service_exiting`, with the run mode in `mode`) before it closes the event streams. Open work views then show that the service has exited or stopped, and stop reconnecting.
- Going back to an earlier session, or resuming one after the task service restarted, could put the assistant into a new, empty session without any error when the service was started with relative `--tasks` and `--runs` paths. The service now uses absolute paths, and after resuming or switching it checks that the assistant reports the requested session; if not, it sends nothing and answers `session_resume_failed`.

### Source checks

- A document source holds one continuous passage: for a Word file the excerpt must start in the cited paragraph and may run on into at most the next five. An excerpt that puts separate passages into one source is refused with a note to write one source per passage. Blank lines in an excerpt count as white space; before, passages separated by a blank line were saved as several sources, and such an excerpt is now refused.
- When an excerpt is not in the paragraph named by the source and occurs in several other paragraphs, the refusal lists the nearest ones with their table positions and asks the assistant to choose by context, instead of pointing to a single one. Pointing to one paragraph led the assistant to save sources that matched word for word but pointed to the wrong place.
- An excerpt taken from a text box in a Word file is refused with a note that text-box text cannot be cited.

### Task service in TypeScript

- `backend/`: the task service is rewritten in TypeScript and run directly by Node 24 with no third-party dependencies. `scripts/dev.sh` and `make dev` start it (`node backend/src/main.mts`). `--mode desktop|server` picks the default bind address; `GET /api/v1/service` reports the running mode, port and capabilities; a taken port falls back to the next free one.
- The earlier Python task service stays in `server/` for comparison and is no longer started by the scripts. Backend tests and `backend/compare/` compare with saved outputs of the Python service (`--against fixtures`). The launch profiles and the assistant's system prompt moved to `backend/profiles/` and `backend/prompts/`. The fake model endpoint used by tests has a TypeScript version in `backend/fake_model/`, and `observatory/archive-format.md` states the format of the archive files.
- `--web <directory>`: the task service serves the built web pages from that directory.
- When starting the assistant's program fails at once, the service closes the archive files of that start and leaves no empty ones behind.

### Packages

- `release/`: build scripts for a single executable (Linux and Windows) and a Linux AppImage. The packages carry the task service, the built web pages, the assistant's program and its extension, and the `rg` and `fd` programs that `grep` and `find` need. Starting a package opens the browser on the task list; starting it again while it runs only opens the browser. Data goes to `~/.local/share/taskwright/` on Linux and to `%LOCALAPPDATA%\Taskwright` on Windows, or to `TASKWRIGHT_DATA_DIR`.
- Desktop profile `desktop.json` for the packages. In desktop mode the task service uses the default provider and model from the assistant program's `settings.json` when both are set, checks at startup whether the model is registered or logged in, and reports the result in `GET /api/v1/service`. When no model service is set up the pages show a notice with a link to the deployment guide.
- In desktop mode the local-user menu has **Exit service** (退出服务), which asks for confirmation and then shows a service-stopped screen (`POST /api/v1/service/exit`; `capabilities.exit` in `GET /api/v1/service` is `true` only in desktop mode and for requests from this computer). This endpoint is meant for the 0.3 packages and may not stay.

### Observatory, simulator, scripts and documentation

- The observatory reads a `--runs` directory that holds the task archive directories again on every read, so tasks created after it started appear without a restart. Without `--workspaces` it picks the `tasks/` directory next to `runs/`, even while `runs/` holds no task yet.
- The simulator (`sim/`) no longer uses the Python task service. `python3 -m sim.run` starts the TypeScript task service, and the simulated user is started and driven by a Node driver (`sim/user_agent_driver.mts`) that uses the task service's session class. The judge checks the completion conditions through the observatory. Running the simulator needs Node.js, the assistant's program and a `python3` that can import the observatory package, but not the `server` package. When the simulated user cannot be started or its driver stops, `record.json` gives the stop reason 模拟用户不可用：<reason>.
- `scripts/tui.sh` opens the assistant program's own terminal interface for a task and replaces the Python `tui` client; the `chat` terminal client is no longer documented.
- `web/mock/`, the web mock server, is removed. The web development server proxies to the local task service, and `scripts/dev.sh --demo` starts the task service on the fake model with a demo task.
- `scripts/check-public.sh` also catches home paths written with a tilde and looks inside gzip-compressed files. `examples/library-lending/run.sh` runs from start to end again, and a backend test runs it.
- Documentation now matches the code in four places: withdrawing a confirmation does not make an item unread again; **Answer** (回答) on a question card stays available while the assistant works as long as its box is empty; a rule made required for the task can be switched off directly; the observatory's `--runs` takes the task service's `runs/` directory.

### Known issues

- Until the assistant's skill is updated, the assistant may try to complete the task without asking, or ask with a card that lacks the right option, and be refused once before it asks with the right card. Completing through the assistant can take an extra round; the green bar on the page is not affected.
- The Windows executable can be built with the same scripts but has not been verified.
- Upgrades do not yet promise that existing tasks keep working. Back up the task directories before upgrading.
- For a Word file that cannot be drawn, clicking a section under **按章节看引用** does not scroll, clicking a source label does nothing in the Materials tab, and the count of citing items next to the file name is not shown. The assistant's reading and the sources of the items are not affected.
- With the default profiles the assistant's program asks its vendor's site for its model catalog in the background each time it starts, with one request per built-in model provider (as of the version current at the time of writing). After it gets an answer for a provider it does not ask again for that provider for four hours. When the site cannot be reached, it asks again at the next start. The requests carry no task content. Setting `offline` under `flags` in the launch profile turns this off, and so does starting the task service or a package with the environment variable `PI_OFFLINE=1`.
- The earlier Python task service is still in the repository (`server/`), for comparison only, and will be removed in the next version. Its projection module is already removed, so it cannot project Word files.

## [0.2.0-alpha] - 2026-09-25

### Added

- Tool rejections are recorded in a `tool_rejection` table (tool, call id, unit of work, reason kind, fact and guidance, the first 2,000 characters of the input); the observatory shows them under the rejected call.
- Word materials: `.docx` files can be uploaded (up to 5 MB). The service writes a paragraph-numbered text beside each one (`<name>.docx.txt`) for the assistant; sources quoting a Word file name the paragraph (`inputs/a.docx#p37`), and `save_revision` checks the excerpt against that paragraph, or against it and at most five following paragraphs.
- The material pane shows Word files page by page in their original layout, with headers and footers; each Word source is labelled with its page, section and position on the page, derived from the paragraph number. Clicking a source highlights the quote, marks a quote that runs over several paragraphs, or says where it was not found.
- `GET …/materials/raw` returns a material file as uploaded.

- Review gate: each reviewed collection names a rule file (`docs/review-rules/*.json`) with numbered rules marked required or optional; the domain-knowledge documents quote the rules through generated regions (`scripts/render-rules.mjs`).
- The user starts a review from the interface ("Review N items waiting for review", "Review this item", "Review these N" in the completion panel). The review runs in the background and reports progress through two new events, `review_progress` and `review_finished`.
- Every finding cites a rule number. Findings under required rules are problems and fail the item; findings under optional rules are advice and do not. The verdict is computed from the rule levels, not taken from the reviewer's output.
- Findings are shown next to their fields in two colours, with the rule text on demand and a button that prefills a request to the assistant.
- The `request_review` tool is enabled for the assistant, for use only when the user asks for a review in the conversation.
- A Review tab in the side panel lists every review ("review N") with its counts, the findings of each item and whether each finding was fixed in a later revision, kept, or is still open.
- Keeping a wording that failed review, with an optional reason (`waive_review`, `unwaive_review`); a kept item counts as passed until it changes.
- Per-task rule switches: optional rules can be switched off or made required (`set_review_rules`). Each review records the rule fingerprint, and items go back to waiting for review when the rules change.
- The reviewer sees the full materials when they are short (up to 20,000 characters), otherwise the paragraphs its sources quote. Reviewer calls ask for temperature 0.
- Events `review_batch`, `review_waived`, `review_unwaived`, `review_rules_changed`.

- One service per task: a running service marks each task it serves with `service.lock` (port, process id, start time, host) and removes it on exit. Another service lists such a task as in use and refuses it (`task_occupied`); a lock left by a process that is gone is replaced.
- The service passes its task root to pi (`TASKWRIGHT_TASKS_ROOT`), and every write refuses a task database outside it.

### Changed

- `save_revision` is idempotent per tool-call id: a replayed call writes nothing and returns the first result.
- The basis of a suggested value is checked verbatim like a `save_revision` source, including Word paragraphs and domain notes.
- Reviewing an item whose content and rules have not changed since its last review needs an explicit "review again".
- When a review ends, the conversation shows one sentence with the counts; the findings are in the Review tab and in the task status.
- EARS-R2 and EARS-R3 state that a named system is a valid subject and that counting words such as "books" or "days" are units.
- "Every item passed review" is reported in three groups: items not reviewed yet, items that failed, and items that failed but whose wording you kept.
- `review_finding` gains `rule_id` and `level`, and `review` gains `batch_id`, `rules_hash`, `reviewer_version` and `forced`; older databases get the columns (and the new `review_waiver` table) when first opened for writing.

- Resuming a session whose file records another task directory (a copied or moved task) rewrites that record to the service's own task directory, keeping the original file as a backup, so writes never go back to the original task data.
- `save_revision` rejections have two layers: the fact (what was tried and why it is not allowed) and the guidance for the assistant. Work summaries show only the fact, for example "保存修订被拒：助手想改 TBD-001 的「种类」，但问题条目写下后只能改状态与处理结果。"
- The reply heading says 助手 (assistant) instead of 执行者.

### Removed

- The development switch `TASKWRIGHT_DEV_REVIEW_AS_MET`, and the stop after three failed reviews of the same revision.
- Open questions follow the items they concern: list rows show how many unresolved questions point at an item, the item detail lists those questions with an answer box and a keep-pending button, and following a question's link to an item offers a way back to the question list.

## [0.1.0-alpha] - 2026-09-24

First public release.

### Added

- Task type for writing a software requirements specification (`task-types/srs-authoring`).
- Agent built on pi, limited to eight tools; it changes the deliverable only through `save_revision`.
- A platform skill shared by all task types, separate from each task type's own skill.
- Direct operations in the interface: edit, delete, confirm, withdraw a confirmation, keep pending, undo a revision.
- One revision sequence per task; every item is identified by its id and a revision number.
- Web interface with a Revisions tab, field-level change marks since the last confirmation, and adjustable font size.
- One writer at a time and strict turn-taking between the user and the agent.
- Markdown documents generated from a chosen revision, with readable sources.
- HTTP/SSE task service, terminal client, read-only observatory, and a simulated user for test runs.
- Documentation in English and Chinese, and a GitHub Actions workflow for checks and tests.
