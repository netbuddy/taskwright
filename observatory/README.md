# 观测台：看清楚执行者在一条会话里做了什么

这是一个只读的本地网页应用。它自己不存任何数据，也不写任何数据。

## 它用的词，跟着 pi 走

界面上的层次与 pi 官方文档里的概念一一对应，每个词的定义、英文原句与出处都在观测台的
**「概念对照」**那一页上（页面地址 `#/concepts`）。四层是：

| 层 | pi 的名字 | 一句话解释 |
|---|---|---|
| 会话 | session | pi 记在一个文件里的一整条对话，有自己的会话编号。 |
| 一次运行 | agent run | 由一次提示（prompt）触发的一整段处理，从 `agent_start` 到 `agent_settled`。 |
| 轮 | turn | 一条助手响应，加上它引出的工具调用与结果。一次运行里可以有好几轮。 |
| 模型请求 | provider request | 往模型服务发一次请求、收一次响应。平时一轮一次，自动重试时一轮多次。 |
| 工具调用 | tool call | 模型请求执行一个工具，有自己的调用编号 `toolCallId`。 |

不属于 pi 的概念在界面上另有来源标记：**任务、字段、修订、里程碑**是领域概念（来自任务数据库），
**一次 pi 进程启动、归档名、后端补记、收到时刻索引**是后端概念（来自后端归档）。

有两点要留心。第一，**「用户消息」是 pi 的消息角色，不等于「人说的话」**：它可能是人经后端发来的，
也可能是扩展注入的，所以界面上每条用户消息都标出来源。第二，**轮号与模型请求这两样，
pi 的 RPC 事件流里拿不到**（`turn_start` 不带 `turnIndex`，也没有 `before_provider_request`
这一对事件）。轮号现在由 pi 进程里那个只读小扩展带出来，所以新归档里是 pi 给的；
旧归档取不到，观测台就按 `turn_start` 的先后自己数，并在那一轮旁边注明「不是 pi 给的」。
模型请求仍然是数「带响应编号 responseId 的助手消息」。

**轮的序数从 1 起给人读**（「第 1 轮」），旁边用小字注明 pi 的轮号（「pi 的轮号 turnIndex＝0」）——
pi 的轮号从 0 起，每次运行重新从 0 编。读取接口里两样都给：`给人读的序数` 与 `pi 给的轮号`
（取不到时为空），另有 `轮号是谁给的` 说明它的来路。

## 它读哪几处

| 它读什么 | 在哪里 | 里面有什么 |
|---|---|---|
| 任务数据库 | 每个任务目录下的 `task.sqlite`，一律以只读方式打开。 | 任务、每个字段的当前值与版本、每次变更的流水、事件流水。事件里带着 pi 给每次工具调用的调用编号。 |
| pi 原始事件流的归档 | 归档目录的 `pi-events/<归档名>-<年月日>-<时分秒>.jsonl`。 | 后端把 pi 标准输出里的每一行原样抄下来的记录。启动一次 pi 进程就有一个文件。 |
| 后端补记 | 与上面同名、扩展名换成 `.backend.jsonl` 的那个文件。 | pi 标准输出里根本没有的那几件事：启动命令与扩展解析结果、这次实际激活的工具清单、后端发过哪几条提示、自动应答过哪些界面请求、pi 的标准错误每一行、pi 退出时的退出码；每次启动时还有三样：pi 实际加载了哪些 skill、上下文文件（取不到 pi 实际加载的清单，如实写明原因）、知识仓库里每份文件的路径与内容摘要值。 |
| 收到时刻索引 | 与上面同名、扩展名换成 `.times.jsonl` 的那个文件。 | 它的第 N 行记的是后端读到归档第 N 行的时刻。pi 的事件本身不带时刻，每轮耗时与每次工具调用耗时都由它算出来。 |
| pi 自己的会话文件 | 归档目录的 `pi-sessions/<归档名>/<时刻>_<会话编号>.jsonl`。 | pi 记的整条会话，每条条目带一个条目编号。重启并接回原会话时 pi 接着往同一个文件里写。 |

另外它读任务目录里的任务定义文件与执行方法（skill）文件，给任务页显示原文、认出材料与指导文件；
完成条件交给 `check_completion.mts` 调用 agent 里的核对函数核对（要用 node，库以只读方式打开）。

第六处是 Langfuse（开源的大模型应用观测平台）。到 Langfuse 的链接分两级：

| 哪一级 | 要不要密钥 | 落在哪里 | 地址格式（在 Langfuse 3.162.0 上实地点过） |
|---|---|---|---|
| 第一级 | 不要 | 那条运行记录（trace，界面上写作 Pi Turn），对应 pi 的一次运行。 | `<服务地址>/project/<项目标识>/traces/<运行记录编号>` |
| 第二级 | 要 | 那条运行记录里的某一步：某一次模型请求（生成记录，写作 LLM Call）或某一次工具调用（工具记录）。 | `<服务地址>/project/<项目标识>/traces/<运行记录编号>?observation=<观测记录编号>` |

运行记录编号是 pi 进程里那个只读小扩展带出来的：Langfuse 官方扩展在每次运行开始时把它写进
环境变量 `LANGFUSE_PI_PARENT_TRACE_ID`，小扩展在每一轮开始时读出来报给后端。

第二级要观测台向 Langfuse 读一次：按观测记录的 `metadata.tool_id` 与 pi 的调用编号精确对上工具调用，
按 `metadata.assistant_index`（从 0 起）与这一轮在这次运行里排第几个对上模型请求。这件事上的规矩是：
**只发 GET 读取请求**，取回来的东西**只在内存里缓存、不落盘**，**密钥不进任何接口返回、页面与日志**；
Langfuse 不通或者密钥不对时**页面照常工作**，链接退回第一级，健康页如实显示不可达。

## 它遵守的几条规矩

1. **只读**。没有任何写入的路径，数据库一律用 `mode=ro` 打开。
2. **不伪造事实**。数据里没有的地方写「未知」「助手没有说话」「这类记录还没有」，
   并说清楚缺的是哪一条事实、建议由谁去补记。绝不用示意数据填。
3. **不自造词**。属于 pi 的概念一律用 pi 的名字与定义；不属于 pi 的标明它是领域概念还是后端概念。
4. **不写死具体名字**。页面与读取接口里没有任何任务名、字段名、工具名。
   字段的显示顺序取自任务定义；工具的中文显示名取自 `tool_names.json`，表里查不到就只显示英文标识。
5. **每个元素都能追回来源**。界面上到处标着事件序号、调用编号、会话文件条目编号、
   归档文件名与行号。
6. **以会话为单位组织**。任务不是这里登记的，而是拿会话里每一次工具调用的调用编号，
   到各个任务目录的库里去对，对上了才算这条会话写过那个任务。所以一条会话可能没有任务。
7. **交付物按整体看**。新格式的库按条目记版本，一次「保存修订」就是整份交付物的一次修订；
   旧格式的库按字段记版本，观测台用 `revisions.py` 这个适配层把它投影成整份交付物的一次次修订。
8. **判定规则不写死**。任务页按一份归类声明认出材料、执行方法与领域规矩文件：路径归类读任务定义，
   「需要注意」的阈值读 `stage_rules.json`，都登记在概念对照页。

## 怎么启动

```bash
python3 -m taskwright_observatory --runs <归档目录> --workspaces <任务目录所在目录> --port 8770
# 好几个归档目录一起看，--runs 写好几次
python3 -m taskwright_observatory --runs <归档目录一> --runs <归档目录二> --workspaces <任务目录所在目录>
# 产品后端按任务分目录存归档（runs/<任务目录名>/pi-events）：给 runs 这一层，全部任务一次收进来，任务目录默认取旁边的 tasks/
python3 -m taskwright_observatory --runs ./runs
```

- `--runs`：归档目录，下面应当有 `pi-events` 与 `pi-sessions` 两个子目录；可以写好几次，会话按开始时刻合在一起排。
  给的目录本身没有 `pi-events` 时，把它下面每个含有 `pi-events` 的直接子目录都当归档目录收进来。
  不给就取环境变量 `TASKWRIGHT_RUNS_DIR`。
  界面与文档里一律叫它「归档目录」。
- `--workspaces`：任务目录所在目录。它下面每个含有 `task.sqlite` 的子目录算一个任务目录；
  直接指向一个任务目录也行。不给时这样取：第一个 `--runs` 给的是 runs 这一层（子目录才是归档目录）而它旁边有
  `tasks/` 目录的，取那个 `tasks/`；其余情况取第一个归档目录的上一级。
- `--port`：监听端口，默认 8770。
- `--host`：监听地址，默认 `0.0.0.0`，也就是本机的每一张网卡都能连上。
- `--langfuse-base` 与 `--langfuse-project`：Langfuse 的服务地址与项目标识，用来拼链接。
  不给就分别取环境变量 `LANGFUSE_BASE_URL` 与 `TASKWRIGHT_LANGFUSE_PROJECT_ID`；都不给也能用，
  只是界面上不显示到 Langfuse 的链接。

**带密钥与不带密钥两种跑法。** 有了服务地址与项目标识，第一级链接就能用。要第二级链接，
再把环境变量 `TASKWRIGHT_LANGFUSE_ENV_FILE` 指到那个存着 Langfuse 密钥的文件上（那个文件在代码仓之外）：

```bash
# 不带密钥：只有第一级链接（直达那条运行记录）
python3 -m taskwright_observatory --runs <归档目录> --workspaces <任务目录所在目录>

# 带密钥：第二级链接也有（直达某一次模型请求或某一次工具调用）
export TASKWRIGHT_LANGFUSE_ENV_FILE=<存着 Langfuse 密钥的那个文件>
python3 -m taskwright_observatory --runs <归档目录> --workspaces <任务目录所在目录>
```

两种跑法在「系统健康」页上都看得出来：那里有一项写着现在能给到哪一级，
以及「未配密钥」「可达」「不可达」是哪一种。

起来之后用浏览器打开 `http://127.0.0.1:8770/`。**按 Ctrl+C 停掉它**；
它要是在后台跑的，先用 `pgrep -af observatory` 看一眼进程号，再 `kill <进程号>`。

数据每次都从磁盘重读，不过会先看一眼文件的修改时刻：没变就用上一次读好的。
跑完一条新会话之后，浏览器刷新一下就能看到，不用重启观测台。
改了观测台自己的 Python 代码要重启它；只改前端文件刷新浏览器就行。

## 五个页面

1. **会话列表**：一行是一条会话，或者一次没能启动起来的 pi 进程。行标题是「任务名 · 会话名 · 开始时刻」
   （会话名取自会话文件里最后一条 session_info 的名字，没有写「未命名会话」；没对上任务写「未对上任务」），
   小字里是任务编号、会话编号、归档名与归档文件；另给运行次数、轮数、模型请求次数、工具调用次数、被拒次数、
   有没有中途重启过 pi 进程、结局、对出来的任务，以及进入「会话详情」与「任务页」的入口。
   搜索框按任务名、会话名、任务编号、会话编号做包含匹配，输入即过滤；默认按开始时刻从新到旧排，
   「按任务分组」打开后按任务折叠。另可以按有没有对上任务、按结局筛选。
   会话文件不在归档里（取不到工作目录）时，按归档目录名去对任务目录名，对上了标「按归档目录名对上」。
   一次也没有运行过的会话只在这里挂上任务，任务页不收它，也不为它单独成段。
2. **任务**：顶部导航进来先是任务列表，点一个任务进它的任务页。一个任务可以跨好几条会话，
   任务页把它们按时间接起来。怎么读见下一节。
3. **会话详情**：与任务页是同一个组件，按会话取数据。没有创建任务的会话（例如闲聊）照样能看，
   看板处写「这条会话没有创建任务」。
4. **系统健康**：核对托着执行者跑起来的那一层是不是正常工作，与任务内容无关。
   范围可以切「全部会话」与某一条会话。取不到依据的项写「未知」并说明缺什么。
5. **概念对照**：观测台上每个词到底指什么、出处在哪里。pi 的每个概念都附官方定义的英文原句、
   中文翻译与出处；领域概念、后端概念、呈现用语、Langfuse 用词对应各一张表，另有一段说明材料、执行方法与领域规矩怎么认。

## 怎样读任务页（会话详情页同理）

流程的单位是**运行**（pi 的 agent run）：用户的一句话，加上助手为这句话做的全部轮（agent_start 到 agent_settled）。
页头标题下面一句统计，例如「17 次运行、48 轮、51 次工具调用、9 次保存修订，没有调用被工具拒绝」。
「需要注意」「交付物看板」「知识的使用」「知识仓库」「助手应答」「关键动作」「模型交互」「工具执行」「出口」「变化」
都是观测台的呈现用语，不是 pi 的概念，页底「这一页上的名词」与概念对照页上都写着。

- **流程表**：每次运行一行，写明序号、用户那句话、助手应答、开始时刻、轮数、工具调用次数、保存修订次数
  （「保存修订」被工具接受的次数）、被拒次数、耗时。用户那句话与助手应答都给完整的话，不截断，长了就在格子里换行。
  「助手应答」一列第一行是助手这次运行最后对用户说的话（没说话就写「没有对用户说话」），第二行小字是关键动作
  （例如「保存修订 2 次」「被拒 1 次」）；用户操作与任务现状两种行这一列留空。除序号与用户那句话以外的列
  可以在「显示哪些列」里隐藏；每一列都可以用鼠标左右拖动表头上的列边界改宽窄，双击边界恢复默认。
  隐藏了哪几列与各列多宽都记在浏览器本地，刷新后保留。用户在网页上的直接操作（改交付物、把条目标成看过，扩展写进会话的 taskwright-user-edit）
  与会话开头的任务现状各占一行；用户在回复卡片上点选项触发的运行标「由界面点击触发」。跨会话的任务按会话分段，段头写会话名。
- **展开一行**：先是用户那句话的全文，再逐轮显示助手读了什么、写了什么、说了什么。新格式的库里，每次保存先只显示一行，
  写明各集合新增、修改、删除了哪几个条目；点某个条目才在原地展开它的字段与来源（修改的是改前改后并排，文本逐字比、
  列表逐项比）。旧格式的字段改写内容很短，直接显示改前改后。
- **机器细节**：每一轮点「看这一轮的机器细节」，分模型交互（请求、应答）、工具执行（每次调用分调用、结果、变化三块）、出口，
  每次运行有一条可以点开的时间条。被工具拒绝的调用在「结果」之后多一块「拒绝记录」：工具被拒时自己在库里 tool_rejection 表记的一行，
  写明原因种类（输入不合规或缺前置步骤）、事实层与指引层；运行表里的「被拒」次数仍按 pi 的工具结果数，库里没有这一行的调用在「结果」里注明。点任何一块，抽屉里显示它的全部事实与到 Langfuse 的直达链接；按 Esc 或点关闭收起。
  流程上方三档开关「只看运行」「展开每次运行」「全部细节」一次把所有行收起、展开，或者连机器细节一起展开。
- **需要注意**只列由事实得出的异常，每一条能跳到那次运行里的那一轮；没有异常时不出现。
- **交付物看板**：完成条件逐条核对（调用 agent 的核对函数）；按集合列出条目、版本、来源条数、
  评审与确认两个状态格（没有记录是空心浅色格）。点一个条目，左边展开改过它的那几次运行并跳到那一块，抽屉里是它的各版；
  点流程里一次运行，看板上高亮它动过的条目。
- **知识的使用**：知识仓库里的文件逐个列出，写明这一次是助手按需读过（第几次运行第几轮，点一行跳到那次运行）、
  工具读过、启动时放进了系统提示、还是没有用到，并显示后端启动时记下的内容摘要值；旧归档没有这项补记时写
  「这条归档没有记下」。上面还写着 pi 实际加载了哪些 skill、上下文文件取不取得到。
- **自动重试与中途插话**：pi 自动重试的那一轮上有一条旁注；用户在运行中途说的话画在它落进的那一轮最前面，
  这次运行不因此断开。
- **流程末端**如实写「助手这次运行已经结束，它最后对用户说的话是：」加原文，不替它判断在等什么。

## 读取接口

这几个接口是按「以后产品前端也能直接用」设计的，返回里都带着来源信息。都只接受 GET。

| 地址 | 给出什么 |
|---|---|
| `/api/overview` | 归档目录、任务目录所在目录、会话数、工具中文名映射、Langfuse 链接底座。 |
| `/api/sessions` | 会话列表，每条带四层的数目、结局、对出来的任务、Langfuse 链接。 |
| `/api/sessions/<会话编号>` | 一条会话的每一次运行、每一轮、每次模型请求与工具调用、它在库里写下的事件、里程碑、界面请求。没有会话编号的那种（pi 没启动起来）用它的归档文件名当标识。 |
| `/api/taskpage/session/<会话编号>` | 会话详情页：按会话分段、按运行排的流程（每次运行的计数、用户的话与助手应答、关键动作与各轮，扩展消息按时刻插行），加页头统计句、看板、知识的使用、路径归类、需要注意、概括句与末端。见 `taskpage.py`。 |
| `/api/taskpage/task/<任务目录名>/<任务标识>` | 任务页：同一形状，按任务取数据，涉及的几条会话按时间接起来。 |
| `/api/tasklist` | 任务列表：每个任务在哪个任务目录、涉及哪几条会话。 |
| `/api/tasks` | 全部任务的读取结果（任务页内部也用它读旧格式的任务）。 |
| `/api/tasks/<任务目录名>/<任务标识>` | 一个任务：新格式给集合、条目与各版、修订清单；旧格式给字段顺序、每一次修订的整份快照与改动字段。 |
| `/api/calls/<调用编号>` | 这次调用出现在哪条会话的哪一步、在库里写下了哪些事件、产生了第几次修订。 |
| `/api/health?scope=all` 或 `?scope=<会话编号>` | 健康检查的每一项、门禁统计、当前范围的统计数。 |
| `/api/concepts` | 概念对照页的全部内容。 |
| `/api/session-options` | 健康页范围选择器用的会话清单。 |

## 怎样拿一个调用编号在三处互相印证

同一次工具调用，三处各有各的叫法：在 pi 的事件流与观测台上叫**调用编号**（`toolCallId`），
在任务目录的库里叫 **`call_id`**，在 Langfuse 的工具记录里叫 **`tool_id`**（在 Metadata 一栏里）。
三处应当逐字相同。走一遍：

1. **在观测台上**：进会话详情或任务页，切到「全部细节」，在那一轮「工具执行」里点「调用」那一块，抽屉里写着
   调用编号全文；点同一次调用的「变化」那一块，抽屉里写着这次调用写下的事件序号。
   也可以直接读 `/api/calls/<调用编号>`，它说出这次调用出现在哪条会话的哪一步、写下了哪些事件。
2. **到 Langfuse**：配了密钥时，点「调用」那一块，抽屉底下「在 Langfuse 里打开这一段」，
   页面会落在那条工具记录上，右边 Metadata 里的 `tool_id` 与观测台上那串逐字相同。
   没配密钥时那条链接只到这次运行那一级，并在旁边写明为什么，
   点过去落在那条运行记录上，再逐条工具记录看 `tool_id`。
   会话详情顶上还写着「到 Langfuse 里应当数到：运行记录几条、生成记录几条、工具记录几条」——
   运行记录对应运行次数，生成记录对应模型请求次数，工具记录对应工具调用次数，数目对得上
   就说明两边记的是同一条会话。
3. **到任务数据库**：

   ```bash
   python3 -m taskwright_observatory.dbshow <任务目录>
   ```

   新格式的库列出每次修订与它的调用编号；旧格式的库最近的事件里那几条 `DATA_CHANGED`，调用编号就是上面那几串；
   事件序号应当等于观测台上写的那个。

## 目录里各个文件做什么

| 文件 | 它做什么 |
|---|---|
| `__main__.py` | 启动入口：读命令行参数，把服务跑起来。 |
| `server.py` | 只用标准库的小型 HTTP 服务：读取接口返回 JSON，另外把 `web/` 下的网页文件发出去。 |
| `api.py` | 把归档目录与任务目录里读到的事实拼成界面要用的几份数据。只做拼接与关联，不做推断。 |
| `runs.py` | 读归档目录：归档、后端补记、收到时刻索引、pi 会话文件，摊成「一次 pi 进程启动 → 一条会话 → 一次运行 → 一轮 → 模型请求与工具调用」。 |
| `workspaces.py` | 只读读任务数据库。打开库一律经 `taskwright_observatory.taskdb.open_readonly`（带忙等待超时）。 |
| `revisions.py` | 适配层：把按字段记版本的流水投影成整份交付物的一次次修订。库表改版只动这一个文件。 |
| `health.py` | 系统健康的每一项检查。 |
| `langfuse.py` | 到 Langfuse 的两级链接。第二级要密钥，只发 GET、只在内存里缓存、密钥不外露。 |
| `concepts.py` | 概念对照那一页的底稿：每个 pi 概念的官方原句、中文翻译与出处，都在这里。 |
| `labels.py`、`tool_names.json` | 工具的中文显示名映射。表里查不到就只显示英文标识。 |
| `shared.py` | 时间写法、路径缩写这类小工具。 |
| `taskpage.py` | 任务页与会话详情页的数据：按运行排的流程、需要注意、页头统计句、概括句与末端、新旧库表的改动归一、交付物看板、知识的使用、跨会话分段。文件里还留着按轮归类的判定函数，本页已不再输出，留待后端改写时清理。 |
| `stage_rules.json` | 需要注意的阈值，以及按轮归类用的默认值（本页已不再输出，留待清理）。路径归类本身读任务定义。 |
| `check_completion.mts` | 用 node 调用 agent 里的完成条件核对函数，库以只读方式打开。 |
| `diffs.py` | 改前改后的文字比对与列表比对。 |
| `web/js/taskpage.js`、`web/taskpage.css` | 任务页与会话详情页共用的画法：按运行排的流程表（列可隐藏）、各轮与机器细节、看板、知识的使用、检视抽屉。样式都限定在页面根元素 `.tp` 之下。 |
| `web/` | 不经构建的静态网页：一个 HTML、一份 CSS、若干原生 JavaScript 模块。不引用任何外部资源。 |
| `tests/` | 单元测试与脱敏夹具：`fixtures/runs/` 是常规情形；`runs并行/` 一轮里并行的工具调用；`runs重试/` 自动重试；`runs插话/` 用户中途插话；`runs新库表/` 的调用编号与 `server/tests/build_current_db.mts` 写出的库一一对上。事件顺序都照 pi 源码里真实的发出顺序排。 |

跑测试：

```bash
python3 -m unittest discover -s taskwright_server -t .
```
