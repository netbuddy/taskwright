# 对话理解评测集的标注说明

`cases.jsonl` 里每一例的期望理解，都按这份说明标。每例的 `note` 写着这一例依据的是哪一条。功能的定义以平台 skill 第八节与 `agent/prompts/schemas/user_intent.schema.json` 为准；本文只写那里没有写明、标注时要统一的口径。

## 一、功能怎么选（三条口径）

1. **用户回答一个还没定下来的问题时给出取值，算告知（inform），不算纠正。**
   - 纠正的判据是「指出现有内容错了，并给出正确内容」。回答一个悬而未决的问题时，没有指出谁错。
   - 例：助手问「罚款怎样缴纳？」，用户说「手机支付」，算告知。助手请用户选「现在完成吗」，用户说「先别完成」，也算告知。
2. **要助手做一件事的话算请求（request），包括「删掉 X」「给 X 补上 Y」「X 改为 Y」。只有话里指出现有内容错了，才算纠正（correct）。**
   - 算请求的例子：「UC-001的参与者改为读者」「请修改 UC-002：补上后置条件……」。skill 的请求例子本来就有「删掉 X-004」。
   - 算纠正的例子：「TBD-001 的种类写错了，请把它的种类改成范围外」「UC-005 的参与者不全，还应该有图书馆工作人员，加上」。
3. **问助手自身的话算无关（other），不算询问。**
   - 询问的对象是材料、条目或任务现状。
   - 例：「你是用什么模型做的？」算无关，与 skill 里「问你是谁」同类。

## 二、其余统一的写法

- **一句话几件事写几项，按用户说的先后排。** 「都看过了，可以完成了吗？」写告知加询问两项。引出下文的话单独不成一项，例如「继续澄清：……」「现在补充：……」里的前半句。
- **要澄清（clarify）只用于助手说过的话。** 问的是助手上一次回复里的词，算要澄清，例如「「开发期开关」是什么意思？」。问的是材料里的说法或内容，算询问，例如「材料里有没有写开馆时间？」。
- **targets 只写上下文条目清单里有的条目。** 新增的条目还没有编号，不写。用户只针对某个字段时写上字段名；判分时，期望里写了字段的，实际也要写同一个字段。
- **解释概念、角色、背景，而没有对应条目的话，标告知，不带 targets。** 例如「借还台管理员是指坐在服务台办理借还的工作人员」。
- **responds_to 只指向用户回答了的那一条等回应行为，而且答的必须是那一条所问的事。** 用户说的是一件新的事时不写；用户没回答、转而要助手给几个做法时，也算回应那一条。一句话里只有一部分回答了它，只有那一项写。例：助手请用户选「要不要现在逐项澄清」，用户说「现在逐项澄清。寒暑假借期统一为 60 天。」，第一句是同意，写 responds_to；第二句给出取值，不是那一条所问的事，是不带 responds_to 的告知。
- **没有等回应的行为时，用户对助手正文的回应不算同意。** 用户明确指向助手正文里点名的条目时，targets 写那几个条目。例：助手正文里请用户打开 UC-001 与 UC-003，没有记等回应的行为，用户说「已看」，标告知，targets 写 UC-001、UC-003。
- **summary 先写对象，再写内容，不写动作动词。** 同时写 `keywords`：摘要里应当出现的对象关键词，一个关键词可以用「|」写几种说法。
- **纠正另写 `change`，取改为、追加、删去之一。** 这是摘要要写明的变更方式，报告里单独统计写明率。
