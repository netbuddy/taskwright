# 功能说明（Capabilities）

本文列出 Taskwright 当前版本（0.1.0-alpha）能做什么，分三部分：

1. [通用能力](#1-通用能力)：与任务类型无关，每种任务类型都有；
2. [任务类型「软件需求规格说明编制」](#2-任务类型软件需求规格说明编制)：目前随附的唯一一种任务类型；
3. [计划中，当前版本没有](#3-计划中当前版本没有)。

只有第 1、2 部分描述代码现在真正做得到的事。安装与运行见[部署](deployment.zh-CN.md)，使用方法见[用户手册](user-guide.zh-CN.md)。

## 1 通用能力

### 1.1 角色

- **用户**：网页界面或终端里的真人（也可以是 `sim/` 里的模拟用户）。
- **执行者**（executor）：运行在 pi 里的智能体，负责读材料、写条目、提问和回复。
- **确认判读者**（confirmation reader）：在工具内部单独发起的一次模型调用，自身不带工具、上下文干净，只判断用户的话是否接受了某个条目。它与执行者用同一个模型。

### 1.2 任务、会话与任务目录

- 一个**任务**（task）有一个任务类型、一个名称、一个可选的领域标签、它的材料和一份交付物。每个任务有自己的**任务目录**：里面是任务类型的起始文件、`inputs/` 下上传的材料，以及数据库 `task.sqlite`。
- 一个任务可以有多个**会话**（session，即多段对话），它们都在同一份交付物上工作。同一时刻只有一个会话处于活动状态：执行者在某个会话里工作时，发往另一个会话的消息会得到 `session_busy`。
- 对话保存在 pi 的会话文件里，不在任务数据库里。会话打开时，执行者会收到一条任务现状消息，列出材料清单和每个集合现有的条目数。
- 材料是纯文本的 `.md` 或 `.txt` 文件，单个不超过 5 MB，随时可以继续上传。

### 1.3 执行者的工具

启动配置（`server/taskwright_server/profiles/dev.json`）的工具白名单里恰好有八个工具。pi 的其他内置工具（例如 `bash`、`edit`、`write`）不加载，所以执行者不能执行命令、不能改文件，只能经 `save_revision` 改交付物。

| 工具 | 做什么 | 核对什么、什么情况下拒绝 |
|---|---|---|
| `read`（pi 内置） | 读一个文件，例如材料、任务定义或领域规矩文档。 | 只读。 |
| `ls`（pi 内置） | 列出一个目录的内容，例如 `inputs/`。 | 只读。 |
| `save_revision`（保存修订） | 把一批按条目的操作（新增、修改、删除）存成交付物的一次修订。条目编号由工具生成。 | 核对集合与字段是否存在、值的类型是否与声明一致、必填字段是否填了且没有被清空、每个新增条目是否至少有一条来源且种类、出处、摘录三项齐全、来源指向的字段是否存在、引用的条目是否存在。修改与删除必须写 `base_version`；条目已经被改到更新的一版时整批拒绝，并说明是谁改到了第几版。种类为「用户的话」的来源，工具会在本会话用户说过的话里逐字查找这段摘录并自己填写出处，找不到就拒绝。一个没有改动任何内容的修改操作会被拒绝。任务已完成或已放弃时拒绝。一批操作里只要有一个不对，整批**都不写入**，并逐条列出每一处问题。它不评判内容好坏。 |
| `reply`（回复） | 把执行者要对用户说的话发给用户。一次回复由零到多条告知（只写事实）、至多一个末位主行为（提问、请确认、给建议值、请选择、提议之一）和一段成文的话组成。 | 必须单独调用，作为这一轮的最后一步。核对形式：该有的部分齐全；主行为是五种之一；请选择至少有两个 key 不同的选项；给建议值必须带建议值和至少一条依据；提议的预览项格式正确。提问、请确认、给建议值、提议必须点名所涉及的条目及其**当前**版本号（对照数据库核对），标明 `scope: "general"` 的除外。连续被拒三次后，它只要求一段成文的话；第五次仍不合格时放行一条纯文字回复，并标为降级。它不写数据库。 |
| `get_item`（查看条目） | 查看一个条目：全部字段、全部来源、版本号、评审与确认状态；也可以指定查看更早的版本。 | 只读；条目或版本不存在时报错。 |
| `get_task_status`（查询任务状态） | 查看每个集合的条目、每条完成条件是否满足（不满足的列出条目）、未解决的待定事项和最近一次修订。 | 只读；与交付物看板用同一组核对。 |
| `record_confirmation`（登记用户确认） | 登记用户在对话里接受了某几个条目的当前版本。 | 条目不存在、版本不是当前版本、这一版之后用户还没说过话、任务已结束时拒绝。它把这一版之后用户说过的原话交给确认判读者；只有判读者判为接受、并给出逐字引用作为依据的条目才会登记。判读者的输出连续两次不合格，或者判读期间条目被改了，就什么都不登记。判读者的每次调用都记进数据库（提示、原始输出、模型、耗时、用量）。 |
| `complete_task`（完成任务） | 把任务标为已完成。 | 与 `get_task_status` 做同一组条件核对；有任何一条不满足就拒绝，并列出缺什么。完成之后所有写入工具都拒绝，任务变为只读。 |

### 1.4 用户在界面上的直接操作

以下操作不经过模型。它们在 pi 进程里运行，走与工具相同的写入函数，所以受同样的核对。

| 操作 | 效果 | 什么情况下被拒绝 |
|---|---|---|
| 改字段 | 把一个条目若干字段的新值存成新的一版。改到的字段来源换成一条「用户直接修改」，没改的字段沿用原来的来源。 | 你打开之后条目又被改过（会给你看最新版本，在它的基础上重改）、条目已删除，或者新值通不过与 `save_revision` 相同的核对。 |
| 删除条目 | 在一次新修订里把一个或几个条目标为已删除。 | 你打开之后条目又被改过，或者条目已经删除。 |
| 确认 | 登记你接受所显示的这些版本；可以同时通知执行者继续往下做。 | 某个版本已经不是当前版本。 |
| 撤回确认 | 登记你不再接受这些版本。 | 某个版本已经不是当前版本。 |
| 撤销一次修订 | 存一次新修订，把所选修订涉及的每个条目恢复成那次改动之前的样子（删掉的条目恢复，新增的条目删除）。不抹掉任何记录。 | 那次修订之后，其中某个条目又被改过。 |
| 标为先不管 | 把一条待定事项的状态改为「用户决定保留」。 | 条目所在集合没有含这个取值的状态字段。 |

任务完成或放弃之后，所有操作都会被拒绝。每次操作之后，执行者会在对话里看到一条说明，写明改了什么以及改后的字段值。

执行者回复卡片上的按钮（选某个选项、「我不知道，你按常识补」、「换一个」等）会作为你的一句话发给执行者，并附一条说明，标明你点的是哪张卡片的哪个选项。

### 1.5 来源

每个条目版本至少带一条来源；一条来源可以指整个条目、某个字段，或者列表型字段里的某一项。来源有四种：

| 种类 | 由谁写 | 出处 | 摘录 |
|---|---|---|---|
| 文档原文 | 执行者 | 材料的路径 | 材料里逐字摘录的原话 |
| 用户的话 | 执行者写摘录，工具填出处 | 用户说这句话的会话与消息 | 逐字摘录，工具对照对话核对 |
| 执行者补充 | 执行者 | 「执行者补充」 | 为什么这样补充或推断 |
| 用户直接修改 | 只能由系统写 | 那次界面操作的编号 | 新值的开头部分 |

### 1.6 完成条件

任务定义为每个集合列出必须满足的条件。代码认识四个条件名：至少一个条目；没有状态为未解决的条目；每个条目评审通过；每个条目用户确认。每一条都是对数据库事实的核对，不评判内容：「评审通过」指条目当前版本有一条合规的评审记录，「用户确认」指条目当前版本有一条接受的确认记录。所以改动一个条目之后，此前的确认就不再作数。集合为空时，「每个条目……」这类条件在门禁上算满足，但报告时不算作「已满足」。交付物看板、`get_task_status` 与 `complete_task` 用的是同一组核对。

### 1.7 文档

生成文档时，把你选中的条目版本按任务类型的 Markdown 模板渲染出来，不经过模型。未经评审或未经确认的版本也可以选入，并在文档里如实标出。结果可以预览或下载。

### 1.8 留痕不可改写

- 每次改动都生成新的一版，不覆盖也不抹掉任何内容。删除的条目保留它的各个版本；撤销是再加一次修订，而不是删掉一次修订。
- 每次写入（一次工具调用或一次直接操作）恰好记一条事件，事件与改动本身在同一个数据库事务里写入：要么都写进去，要么都不写。
- 每条事件都记着所在的会话、对应的工具调用，以及改动者是执行者还是用户。

## 2 任务类型「软件需求规格说明编制」

随附的任务类型 `srs-authoring`（在 `task-types/srs-authoring/`）把需求材料整理成一份软件需求规格说明。它的界面文字和规矩都是中文的。

### 2.1 条目集合与字段

| 集合 | 编号前缀 | 字段（加粗为必填） |
|---|---|---|
| 功能用例 | UC | **用例名称**、**用例功能**、**参与者**（列表）、前置条件（列表）、后置条件（列表）、约束规则（列表）、**基本流程**（列表）、扩展流程（列表） |
| 非功能需求 | NFR | **类别**、**句式类型**（EARS 六种句式之一）、**需求语句** |
| 约束 | CON | **类别**、**句式类型**、**需求语句** |
| 待定与范围外事项 | TBD | **事项**、**种类**（待澄清、范围外、后续迭代）、建议的处理、**状态**（未解决、已解决、用户决定保留）、处理结果、关联条目（条目引用） |

完成条件：功能用例至少一个；每个功能用例、非功能需求和约束都要评审通过并经用户确认；待定与范围外事项里不能留有状态为未解决的条目。

### 2.2 领域规矩

`docs/domain-knowledge/` 下的两份规矩文档规定条目怎样写，执行者动笔之前要先读完。

- **功能用例**（`use-case-writing.md`）：一个用例对应参与者的一个目的；用例的九项（用例名称、用例 ID、用例功能、参与者、前置条件、后置条件、约束规则、基本流程、扩展流程）各怎样写；不允许的写法（写界面细节、写材料里没有的功能、自行决定含糊之处、在规则里举例、用无法验证的词）。
- **非功能需求与约束**（`ears-writing.md`）：两类条目的区别；EARS（Easy Approach to Requirements Syntax，一种把需求写成固定句式的方法）的六种句式：普遍型、事件驱动型、状态驱动型、可选特性型、异常处理型、复合型；以及每一条都要满足的规矩（一条只说一件事、主语明确、可以验证、不用含糊的词、不举例、除非本身是约束否则不写实现手段、材料里的数值原样保留）。

### 2.3 执行者的工作方式

执行者的 skill（`.pi/skills/srs-authoring/SKILL.md`）规定了以下工作方式：

- **先读材料再动手。** 先列出材料目录、把每个文件读完全文再动笔；文件读不出或找不到时停下来问用户。
- **把材料分拣成四类**：功能用例、非功能需求、约束、待定与范围外事项；每次保存最多写四个条目。
- **含糊的地方不自己定。** 记成一条状态为「未解决」的待定事项，可以附上建议的处理，然后去问用户。
- **一次只问一件事**，先问最影响其他条目的那一件，问之前先说明这个问题从材料哪里来。是非题与几选一用「请选择」，只有开放问题才用「提问」。
- **用户答复之后**，修改受影响的条目并加一条「用户的话」来源，把待定事项改为已解决并在处理结果里写用户的决定。只有对话里的用户亲口说先不管，才算用户决定保留；材料里写着「以后再做」不算用户的决定。
- **用户的说法与材料对不上时**，先把材料原文摆出来问清以哪个为准，再改。
- **补充的内容必须标明。** 推断或按常识补上的内容带「执行者补充」来源，并在回话里向用户说明。
- **改条目之前**先看它的当前版本，在当前版本的基础上改。
- **改动之后请确认新版本。** 说清改了哪几个条目、各改了什么，并请用户确认新的版本。
- **用户明确接受才登记确认。** 「知道了」「你先写别的」不算接受；用户在界面上点的「确认」已经记下，不再登记。
- **完成前先问用户。** 完成条件全部满足之后，先问用户是否现在完成，用户同意才调用完成任务；工具拒绝时如实告诉用户还缺什么。
- **如实说明工具的缺失。** 某一步需要的工具现在没有（例如评审），就跳过这一步并告诉用户。

## 3 计划中，当前版本没有

以下能力在当前版本里**没有**。

- **评审者（合规评审）。** 按领域规矩逐条评审条目的评审者还在计划中。默认启动配置没有启用评审工具，所以没有条目能评审通过，「每个条目评审通过」这条完成条件无法满足。演练时可以设环境变量 `TASKWRIGHT_DEV_REVIEW_AS_MET=1`，把这一条当作已满足处理；完成记录里会写明是这个开关让它通过的。
- **Word（.docx）文档。** 目前只生成 Markdown 文档。
- **多种任务类型。** 目前只随附「软件需求规格说明编制」这一种。任务定义的格式是通用的，但没有附带其他任务类型。
- **需求池。** 条目属于各自的任务，不能在任务之间共享或复用。
- **身份认证与多用户。** 没有账号和权限，见[部署](deployment.zh-CN.md)。
