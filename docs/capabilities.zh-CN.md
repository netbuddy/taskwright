# 功能说明（Capabilities）

本文列出 Taskwright 当前版本（0.1.0-alpha）能做什么，分三部分：

1. [通用能力](#1-通用能力)：与任务类型无关，每种任务类型都有；
2. [任务类型「软件需求规格说明编制」](#2-任务类型软件需求规格说明编制)：目前随附的唯一一种任务类型；
3. [计划中，当前版本没有](#3-计划中当前版本没有)。

只有第 1、2 部分描述代码现在真正做得到的事。安装与运行见[部署](deployment.zh-CN.md)，使用方法见[用户手册](user-guide.zh-CN.md)。

## 1 通用能力

### 1.1 角色

- **用户**：网页界面或终端里的真人（也可以是 `sim/` 里的模拟用户）。
- **助手**（assistant，技术上也叫执行者 executor）：运行在 pi 里的智能体，负责读材料、写条目、提问和回复。
- **评审者**（reviewer）：按编了号的评审规则逐条核对条目（见 1.9 节）。它是系统发起的一次不带工具的模型调用，不能改条目。

用户接不接受一个条目，不由模型判断：打开条目详情就算看过，看过就算确认（见 1.4 节）。

### 1.2 任务、会话与任务目录

- 一个**任务**（task）有一个任务类型、一个名称、一个可选的领域标签、它的材料和一份交付物。每个任务有自己的**任务目录**：里面是任务类型的起始文件、`inputs/` 下上传的材料，以及数据库 `task.sqlite`。
- 一个任务可以有多个**会话**（session，即多段对话），它们都在同一份交付物上工作。同一时刻只有一个会话处于活动状态：助手在某个会话里工作时，发往另一个会话的消息会得到 `session_busy`。
- **一次只有一方在写。** 任一时刻只有用户或助手一方在改交付物。用户的一句话启动助手的一次运行；运行期间再来的说话与直接操作一律被拒绝，错误码 `session_busy`（没有排队），网页界面把发送键和所有写入按钮变灰。用户在网页界面里有未保存的编辑时，改为发送键与卡片按钮变灰。两个浏览器页签同时编辑同一条目时，后保存的那一边被拒绝，错误码 `stale_revision`，不做合并。
- 对话保存在 pi 的会话文件里，不在任务数据库里。会话打开时，助手会收到一条任务现状消息，列出材料清单和每个集合现有的条目数。
- 材料是纯文本的 `.md` 或 `.txt` 文件，单个不超过 5 MB，随时可以继续上传。

### 1.3 助手的工具

启动配置（`server/taskwright_server/profiles/dev.json`）的工具白名单里恰好有八个工具。pi 的其他内置工具（例如 `bash`、`edit`、`write`）不加载，所以助手不能执行命令、不能改文件，只能经 `save_revision` 改交付物。

| 工具 | 做什么 | 核对什么、什么情况下拒绝 |
|---|---|---|
| `read`（pi 内置） | 读一个文件，例如材料、任务定义或领域规矩文档。 | 只读。 |
| `ls`（pi 内置） | 列出一个目录的内容，例如 `inputs/`。 | 只读。 |
| `save_revision`（保存修订） | 把一批按条目的操作（新增、修改、删除）存成交付物的一次修订。条目编号由工具生成。 | 核对集合与字段是否存在、值的类型是否与声明一致、必填字段是否填了且没有被清空、每个新增条目是否至少有一条来源且种类、出处、摘录三项齐全、来源指向的字段是否存在、引用的条目是否存在。修改与删除必须写 `base_revision`，也就是条目当前所在的修订号；条目已经被改到更新的修订时整批拒绝，并说明是谁改到了哪次修订，附上它现在的内容。种类为「用户的话」的来源，工具会在本会话用户说过的话里逐字查找这段摘录并自己填写出处，找不到就拒绝。种类为「文档原文」的来源，摘录必须是出处所指材料文件里连续的一段；一条摘录里可以用空行隔开几段，工具按空行拆开、逐段查找，全部找到时在原位置存成几条来源（种类、出处、支持哪几处都相同）；有一段找不到、不用空行隔开就跳句拼接、改了字或出处读不到时拒绝，拒绝原因写明是第几段找不到。问题条目（状态字段的取值里有「用户决定保留」的集合，例如「问题」集合）写下之后，助手修改它只能改状态与处理结果，改别的字段被拒绝；新增不受限。一个没有改动任何内容的修改操作会被拒绝。任务已完成或已放弃时拒绝。一批操作里只要有一个不对，整批**都不写入**，并逐条列出每一处问题。它不评判内容好坏。 |
| `reply`（回复） | 把助手要对用户说的话发给用户。一次回复由零到多条告知（只写事实）、至多一个末位主行为（提问、请确认、给建议值、请选择、提议之一）和一段成文的话组成。 | 必须单独调用，作为这一轮的最后一步。核对形式：该有的部分齐全；主行为是五种之一；请选择至少有两个 key 不同的选项；给建议值必须带建议值和至少一条依据；提议的预览项格式正确。提问、请确认、给建议值、提议必须点名所涉及的条目及其**当前**所在的修订号（对照数据库核对），标明 `scope: "general"` 的除外。连续被拒三次后，它只要求一段成文的话；第五次仍不合格时放行一条纯文字回复，并标为降级。它不写数据库。 |
| `get_item`（查看条目） | 查看一个条目：全部字段、全部来源、当前所在的修订、它改动过的修订、评审与确认状态；也可以指定看它截至某次修订时的样子。 | 只读；条目不存在或任务还没有那次修订时报错。 |
| `get_task_status`（查询任务状态） | 查看每个集合的条目、每条完成条件是否满足（不满足的列出条目）、未解决的问题条目、**未读清单**（用户从没看过的条目，带标题）和最近一次修订。 | 只读；与交付物看板用同一组核对。 |
| `request_review`（请求评审） | 请评审者评审条目当前所在修订的内容；不写 `items` 就评全部待评审的条目。只在用户在对话里要求评审时使用；评审平时由用户在界面上发起（见 1.9 节）。 | 点名的条目不存在、已删除、不在给定的修订、所在集合不要求评审时拒绝；上一批评审还在进行时拒绝。结果逐条写「合规」或「不合规（问题 N 处，建议 M 条）」，每条发现带规则编号。 |
| `complete_task`（完成任务） | 把任务标为已完成。 | 与 `get_task_status` 做同一组条件核对；有任何一条不满足就拒绝。未读的条目单独写成一句，助手可以原样转告用户：「还有 N 条你从没看过：……」；其余没满足的条件列在后面。完成之后所有写入工具都拒绝，任务变为只读。 |

### 1.4 用户在界面上的直接操作

以下操作不经过模型。它们在 pi 进程里运行，走与工具相同的写入函数，所以受同样的核对。改动条目的操作各产生一次修订；标为已读不产生修订。

| 操作 | 效果 | 什么情况下被拒绝 |
|---|---|---|
| 改字段 | 把一个条目若干字段的新值存成一次新的修订。改到的字段来源换成一条「用户直接修改」，没改的字段沿用原来的来源。同时登记你已确认这个条目在这次新修订的内容。 | 你打开之后条目又被改过（例如另一个浏览器页签先保存了；会告诉你它现在所在的修订，请重新打开）、条目已删除，或者新值通不过与 `save_revision` 相同的核对。 |
| 删除条目 | 在一次新修订里把一个或几个条目标为已删除。 | 你打开之后条目又被改过，或者条目已经删除。 |
| 标为已读 | 记下你看过了这些条目当前所在修订的内容，看过就算确认。你打开条目详情时界面自动这样做；在请确认卡片上点「这几条都看过了」也是它，同时通知助手继续往下做；也可以在列表里勾选几条一起标为已读。条目在那次修订上已经记过的，不再写。 | 写的修订已经不是条目当前所在的修订。 |
| 撤回确认 | 记下你不再接受这些条目在那次修订的内容。网页界面上不再提供这个按钮，只保留接口；已读是按条目算的，撤回之后条目仍算看过。 | 写的修订已经不是条目当前所在的修订。 |
| 撤销一次修订 | 存一次新修订，把所选修订涉及的每个条目恢复成那次改动之前的样子（删掉的条目恢复，新增的条目删除）。不抹掉任何记录。网页界面按修订日志预先判断撤销不了的修订，把它的撤销按钮变灰并说明原因。 | 那次修订之后，其中某个条目又被改过或已删除。 |
| 标为先不管 | 在一次新修订里把一条问题条目的状态改为「用户决定保留」，同时登记你已确认它在这次修订的内容。 | 条目所在集合没有含这个取值的状态字段。 |
| 请求评审 | 评审全部待评审的条目（条目区顶上的「评审 N 条待评审的条目」）、一个条目（详情里的「评审这条」）或完成条件面板里列出的条目（「评审这 N 条」）。请求立即返回，评审在后台进行，见 1.9 节。不产生修订。 | 上一批评审还在进行、没有要评的条目，或点名的条目不在它当前所在的修订。 |

**看过就算确认。** 没有「确认」按钮。打开条目详情，就在条目当前所在的修订上记一条依据为「已读」的确认标记，条目状态从「未读」变成「已读 · 修订 N」（N 是你最后看过的那次修订）。只认「打开详情」这一个动作：列表里看到不算，也不计你看了多久。已读是按条目算的、只进不退：看过一次就一直是已读，助手之后再改它也不会翻回未读；它改过、你还没看的地方由「刚改」标签和详情里的琥珀色字段边框提示，不挡完成。再打开一次时，会在当时的修订上再记一条已读，导出文档时据此如实写你最后看过哪次修订。你不必在对话里说「可以」：助手不再按你说的话登记确认。

**你自己改的算已确认。** 你亲手写出来的内容就是你认可的内容：改字段或标为先不管成功时，会在产生修订的同一个事务里，为这个条目在新修订上登记一条你的确认，依据记「界面修改」。删除条目与撤销修订不会自动确认。详情底部右侧只显示状态，没有撤回已读的按钮。

任务完成或放弃之后、助手工作期间，所有操作（包括请求评审）都会被拒绝；只有一个例外：助手工作期间打开条目详情照样记为已读，因为它不改交付物。每次操作之后，助手会在对话里看到一条说明，写明改了什么、产生了哪次修订以及改后的字段值，例如「用户改了 UC-002 的「基本流程」，产生修订 5，UC-002 现在是修订 5。」

助手回复卡片上的按钮（选某个选项、「我不知道，你按常识补」、「换一个」等）会作为你的一句话发给助手，并附一条说明，标明你点的是哪张卡片的哪个选项。

**看得到改了什么。** 网页界面在三处显示改动。右侧栏的「修订」页签是修订日志，最新在上：谁改的、触发它的事（助手回应的是你的哪句话，或者你做的哪次直接操作）、碰到的每个条目以及改了哪些字段；在卡片上可以看一个条目的差异、撤销这次修订、按这次修订生成文档。助手保存过修订的回复带一枚小标签点名这几次修订，点它打开修订页签。条目详情里，自你上次确认的那次修订以来（从没确认过的，自新增的那次修订以来）助手改过的字段加框，差异按那次修订画；你自己改的字段不加框。打开详情就记为已读，所以框在你打开的那一刻定下来：详情开着时一直看得到，下次再打开就不再出现。助手最近一次运行改过的条目在列表里标「刚改」，从没打开过的（未读）条目加粗。条目区里灰掉的写入按钮，鼠标停在上面会说明原因（助手工作中、正在保存、看的是旧修订、任务已结束）。问题条目写下之后在网页上不能直接修改，只能「先不管，保留」或删除。

### 1.5 来源

条目在每次修订下的内容至少带一条来源；一条来源可以指整个条目、某个字段，或者列表型字段里的某一项。来源有四种：

| 种类 | 由谁写 | 出处 | 摘录 |
|---|---|---|---|
| 文档原文 | 助手 | 材料的路径 | 材料里逐字摘录的原话 |
| 用户的话 | 助手写摘录，工具填出处 | 用户说这句话的会话与消息 | 逐字摘录，工具对照对话核对 |
| 助手补充（库里存作「执行者补充」） | 助手 | 「执行者补充」 | 为什么这样补充或推断 |
| 用户直接修改 | 只能由系统写 | 那次界面操作的编号 | 新值的开头部分 |

直接修改产生的修订同时登记为用户已确认（见 1.4 节），所以带「用户直接修改」来源的内容一开始就是已读的，之后也不会翻回未读。

生成的文档里，这两种出处换成读者能看懂的写法：「用户的话」写成「会话「<会话名称>」里用户的第 N 句话」，「用户直接修改」写成「用户在界面上的第 N 次修改（<时刻>）」，N 按这些修改存入的先后编号。会话记录或那次操作找不到时，写「对话里用户说的话」或「用户在界面上的修改」，不把内部编号印进文档。

### 1.6 完成条件

任务定义为每个集合列出必须满足的条件。代码认识四个条件名：至少一个条目；没有状态为未解决的条目；每个条目评审通过；每个条目用户确认。每一条都是对数据库事实的核对，不评判内容：「评审通过」指条目在它当前所在的修订上有一条合规的评审记录（不满足时，说明里把还没评审的条目与评审不合规的条目分开写），「用户确认」指条目在任何一次修订上有过一条接受的确认标记（依据是已读、界面修改或早期的其他依据都算），也就是用户看过它、它不是未读。评审是挂在「条目加修订」上的标记，条目之后再改动时不会跟着移动，所以改动一个条目之后要重新评审；确认标记在库里同样挂在「条目加修订」上，但门禁只问有没有看过，改动之后不翻回未读。导出文档时，条目导出的修订比用户最后看过的修订新，依据写「用户最后看过修订 N，之后由助手改为修订 M」。集合为空时，「每个条目……」这类条件在门禁上算满足，但报告时不算作「已满足」。交付物看板、`get_task_status` 与 `complete_task` 用的是同一组核对。

### 1.7 文档

生成文档时，把交付物按某一次修订（缺省为最新）整体按任务类型的 Markdown 模板渲染出来，也可以只列出那次修订时交付物里的其中几个条目；不经过模型。每个条目写的是它在那次修订时的内容。用的模板是任务目录里的那份副本，由任务定义里的「文档模板」一项指定；它在建任务时从 `task-types/<任务类型>/` 复制过来，所以改代码仓里的模板只影响之后新建的任务。每个集合内的条目按编号排列。文档开头写明按哪次修订生成。未经评审或未经确认的条目也写进去，并在文档里如实标出：带标注的条目写明它的内容来自哪次修订、评审状态（未评审、评审通过或评审不通过，取那次修订上最近一次评审）和确认状态（在那次修订上：未确认，或已确认并写明依据：已读、用户修改，或较早的明确确认）。随附模板里的问题条目只写种类和状态，不带这些标注。结果可以预览或下载，任务完成之后也可以。修订号超过最新修订，或者列出的条目在那次修订时不在交付物里，会被拒绝。

### 1.8 留痕不可改写

- 每次改动都是一次新的修订，不覆盖也不抹掉任何内容。条目在任何一次修订下的内容都还读得到，删除的条目保留它之前的内容；撤销是再加一次修订，而不是删掉一次修订。
- 每次写入（一次工具调用或一次直接操作）恰好记一条事件，事件与改动本身在同一个数据库事务里写入：要么都写进去，要么都不写。唯一的例外是改字段与标为先不管：它们在同一个事务里记两条事件，一条是修订，一条是随之登记的确认。标为已读记一条 `ITEM_VIEWED` 事件；要标的条目都已是已读时什么都不记。
- 每条事件都记着所在的会话、对应的工具调用，以及改动者是助手还是用户。

### 1.9 评审

评审者按任务类型的评审规则核对条目。任务定义为每个要评审的集合写明一份规则文件（随附的任务类型里是 `docs/review-rules/use-case.json` 与 `ears.json`），每条规则有编号（例如 UC-R7）、级别、条文、反例与正例。**必选**规则决定评审通过与否，**可选**规则只给建议。任务定义可以关闭某些可选规则（「关闭」）或把它们升为必选（「升为必选」），界面上的开关还没有做。「问题」集合不评审。

- **谁发起。** 由你在界面上发起。助手不主动评审；只有你在对话里要求评审时，它才调用 `request_review`。
- **怎样评。** 每个条目由一次不带工具、不带对话的模型调用评审，一次最多并行 4 个，单个条目最多 60 秒，不合格重试一次。评审者的每条发现都必须引用清单里的规则编号；引用了清单里没有的编号、或者违反必选规则却没写改法的输出算不合格，重来一次。没有评完（超时、调用失败、两次输出不合格、评审期间条目被改）时不记合规与否。
- **结论由代码算。** 只要有一条违反必选规则的发现，条目就**不合规**；违反可选规则的发现只是建议。改法只写改哪个字段、往哪个方向改，不写改好的全文。
- **界面上看得到什么。** 条目区顶上写着待评审与评审不通过各几条；评审进行时显示进度条（「评审中 3/12」），评完显示一行结果。条目详情里，问题标红、建议标琥珀色，写在对应字段旁；点规则编号（「违反 UC-R9」）展开条文，「让助手照这条改」往输入框里预填一句请助手修改的话。条目的评审状态写作「评审通过」「评审通过（N 条建议）」「评审不通过 N 处」或「待评审」。
- **条目改了之后。** 评审是挂在「条目加修订」上的标记；条目改出新修订之后，要重新评审。

## 2 任务类型「软件需求规格说明编制」

随附的任务类型 `srs-authoring`（在 `task-types/srs-authoring/`）把需求材料整理成一份软件需求规格说明。它的界面文字和规矩都是中文的。

### 2.1 条目集合与字段

| 集合 | 编号前缀 | 字段（加粗为必填） |
|---|---|---|
| 功能用例 | UC | **用例名称**、**用例功能**、**参与者**（列表）、前置条件（列表）、后置条件（列表）、约束规则（列表）、**基本流程**（列表）、扩展流程（列表） |
| 非功能需求 | NFR | **类别**、**句式类型**（EARS 六种句式之一）、**需求语句** |
| 约束 | CON | **类别**、**句式类型**、**需求语句** |
| 问题 | TBD | **事项**、**种类**（待澄清、范围外、后续迭代）、建议的处理、**状态**（未解决、已解决、用户决定保留）、处理结果、关联条目（条目引用） |

完成条件：功能用例至少一个；每个功能用例、非功能需求和约束都要评审通过并经用户确认（也就是没有未读的）；「问题」集合里不能留有状态为未解决的条目。

### 2.2 领域规矩

`docs/domain-knowledge/` 下的两份规矩文档规定条目怎样写，助手动笔之前要先读完。

- **功能用例**（`use-case-writing.md`）：一个用例对应参与者的一个目的；用例的九项（用例名称、用例 ID、用例功能、参与者、前置条件、后置条件、约束规则、基本流程、扩展流程）各怎样写；不允许的写法（写界面细节、写材料里没有的功能、自行决定含糊之处、在规则里举例、用无法验证的词）。
- **非功能需求与约束**（`ears-writing.md`）：两类条目的区别；EARS（Easy Approach to Requirements Syntax，一种把需求写成固定句式的方法）的六种句式：普遍型、事件驱动型、状态驱动型、可选特性型、异常处理型、复合型；以及每一条都要满足的规矩（一条只说一件事、主语明确、可以验证、不用含糊的词、不举例、除非本身是约束否则不写实现手段、材料里的数值原样保留）。

两份文档里带编号的规则列表由 `docs/review-rules/` 下的规则文件生成（`node scripts/render-rules.mjs`），助手读的规则与评审者核对的规则是同一份文字。

### 2.3 助手的工作方式

助手加载两个 skill，系统提示要求它动手之前把两份都读完，先读平台 skill。**平台 skill**（代码仓里的 `agent/prompts/skills/taskwright-executor/SKILL.md`，所有任务类型共用，不复制进任务目录）写的是在 Taskwright 里怎样工作；**任务 skill**（任务目录里的 `.pi/skills/srs-authoring/SKILL.md`）只写这类任务特有的做法。

来自平台 skill 的：

- **认得系统消息。** 会话开头的任务现状消息（续接旧会话时改为上次之后的变化）、界面操作的通知、工具的拒绝，都是系统写的，不是用户说的话。看到界面操作的通知，就按它写的修订号工作（「X-001 现在是修订 N」）。改、删、先不管、撤销各产生一次修订，标为已读与撤回确认不产生修订。用户在界面上打开条目会直接记下，不发通知；哪些条目用户还没看过，看「查询任务状态」的未读清单。
- **先读材料再动手。** 先列出材料目录、把每个文件读完全文再动笔；文件读不出或找不到时停下来问用户。字段照任务定义填。
- **修订。** 交付物每保存一次就是一次修订，不论是助手存的还是用户在界面上改的，修订号在任务里从 1 起连续递增；条目没有单独的版本号，它最近一次在哪次修订里被新增或改过，就说它「现在是修订 N」。
- **改条目之前**先用 `get_item` 看它现在的内容与所在的修订，修改时把这个修订号填进 `base_revision`；工具说条目已经被改到更新的修订时，按工具附上的最新内容重来。
- **做完再回复。** 用户要你整理材料，就把材料里的内容都写成条目之后再回复，一次保存写不下就分几批，不要只写了一部分就停下来。
- **注明来源。** 每个条目至少一条来源；文档与用户的话逐字摘录；推断或按常识补上的内容带「助手补充」来源，并在回话里向用户说明。
- **经回复工具说话**，单独调用，作为这一轮的最后一步。一次只问一件事，问之前先说明这个问题从材料哪里来。是非题与几选一用「请选择」，只有开放问题才用「提问」。主行为点名条目时写条目当前所在的修订号。
- **改完只告知。** 说清改了哪几个条目、各改了什么，不必请用户确认。用户自己会去看：打开一个条目就算确认，看过一次就一直是已读。只有确实需要用户明确答复时（例如按常识补了一处关键内容）才用请确认。
- **没有要登记的。** 助手没有登记确认的工具；用户在对话里说「可以」时，请用户打开那几条看一眼。
- **完成前先看未读清单。** 先用查询任务状态看一遍。还有从没看过的，先告诉用户还有几条没看、是哪几条；其余条件都满足时，再问用户是否现在完成，用户同意才调用完成任务；工具拒绝时如实告诉用户还缺什么。
- **如实说明工具的缺失。** 完成条件里有某一项需要的工具现在没有，就如实告诉用户，不说已经做过。

来自任务 skill 的：

- **交付物**由四个集合组成；动笔之前读任务定义与两份领域规矩文档。
- **材料读完再动笔**，再把材料分拣成四类：功能用例、非功能需求、约束、问题。只约束某一个用例的规则写进这个用例的「约束规则」；对整个系统都成立的规则单列为约束条目。
- **含糊的地方不自己定。** 记成一条状态为「未解决」的问题条目，可以附上建议的处理，然后去问用户；一次只问一条，先问最影响其他条目的那一条。问题条目写下之后只改状态与处理结果。
- **用户要建议时**，给出对它牵涉的条目的具体改法（改哪条、哪个字段、改成什么），标明是推导出的候选、等用户采纳；该留到以后的，直接建议按「用户决定保留」了结。
- **用户采纳或答复之后**，先修改牵涉的条目并加一条「用户的话」来源，同一轮回复末尾用请确认问这个问题是否已解决；用户确认了，再把问题条目改为已解决并在处理结果里写明采纳的内容。只有对话里的用户亲口说先不管，才算用户决定保留；材料里写着「以后再做」不算用户的决定。
- **用户的说法与材料对不上时**，先把材料原文摆出来问清以哪个为准，再改。
- **一批最多四个条目**，问题条目放在最后单独一批保存，因为问题条目的关联条目只能填已经保存、拿到编号的条目。
- **整理完再报数。** 材料全部整理成条目之后（不是每保存一批就说一次），说明各集合各有几条，列出编号与名称；之后每次修改，说明改了哪几条。

## 3 计划中，当前版本没有

以下能力在当前版本里**没有**。

- **保留评审不通过的写法。** 还不能把评审不通过的条目连同理由标为你接受的写法；条目要改过再评审。
- **在界面上开关评审规则**，以及跨条目的评审（重复、冲突）。
- **Word（.docx）文档。** 目前只生成 Markdown 文档。
- **已生成文档的列表。** 网页界面的「文档」页签只提供生成入口，生成过的文档不保存、不列出。
- **网页界面里的停止按钮。** 目前只能经 HTTP 接口的 `stop` 控制请求中断助手（见[接口参考](api.zh-CN.md) 5.5 节）。
- **修订统一之前建的任务**在任务列表里标为不支持，打不开；不做迁移。
- **多种任务类型。** 目前只随附「软件需求规格说明编制」这一种。任务定义的格式是通用的，但没有附带其他任务类型。
- **需求池。** 条目属于各自的任务，不能在任务之间共享或复用。
- **身份认证与多用户。** 没有账号和权限，见[部署](deployment.zh-CN.md)。
