# 功能说明（Capabilities）

本文列出 Taskwright 当前版本（0.1.0-alpha）能做什么，分三部分：

1. [通用能力](#1-通用能力)：与任务类型无关，每种任务类型都有；
2. [任务类型「需求工程」](#2-任务类型需求工程)：目前随附的唯一一种任务类型；
3. [计划中，当前版本没有](#3-计划中当前版本没有)。

只有第 1、2 部分描述代码现在真正做得到的事。安装与运行见[部署](deployment.zh-CN.md)，使用方法见[用户手册](user-guide.zh-CN.md)。

## 1 通用能力

### 1.1 角色

- **用户**：网页界面或终端里的真人（也可以是 `sim/` 里的模拟用户）。
- **助手**（assistant，技术上也叫执行者 executor）：运行在 pi 里的智能体，负责读材料、写条目、提问和回复。
- **评审者**（reviewer）：按编了号的评审规则逐条核对条目（见 1.9 节）。它是系统发起的一次不带工具的模型调用，不能改条目。

用户接不接受一个条目，不由模型判断：打开条目详情就算看过，看过就算确认（见 1.4 节）。

### 1.2 任务、会话与任务目录

- 一个**任务**（task）有一个任务类型、一个名称、一个可选的领域标签、它的材料和一份交付物。每个任务有自己的**任务目录**：里面是任务类型的起始文件、`inputs/` 下上传的材料，以及数据库 `task.sqlite`。
- 一个任务可以有多个**会话**（session，即多段对话），它们都在同一份交付物上工作。同一时刻只有一个会话处于活动状态：助手在某个会话里工作时，发往另一个会话的消息会得到 `session_busy`。
- **一次只有一方在写。** 任一时刻只有用户或助手一方在改交付物。用户的一句话启动助手的一次运行；运行期间再来的说话与直接操作一律被拒绝，错误码 `session_busy`（没有排队），网页界面把发送键和所有写入按钮变灰。用户在网页界面里有未保存的编辑时，改为发送键与卡片按钮变灰。两个浏览器页签同时编辑同一条目时，后保存的那一边被拒绝，错误码 `stale_revision`，不做合并。
- 对话保存在 pi 的会话文件里，不在任务数据库里。会话打开时，助手会收到一条任务现状消息，列出材料清单和每个集合现有的条目数。
- 材料是纯文本的 `.md`、`.txt` 文件、Word 的 `.docx` 文件或 PDF 文件，单个不超过 5 MB，随时可以继续上传。PDF 上传时解析成给助手读的文字版（每块一行，带页与块；表格按行，不分格），整份没有可读文字的（扫描件）不收，只有部分页没有文字的收下并标出是哪几页。还没有进入对话的材料可以删除；材料上传之后任务里只要有会话活动过，就算进入了对话，不能再删除，所以条目引用过的材料始终都在。`.docx` 旁边会生成一份文字版（Markdown 格式），保留 Word 文件的标题、自动编号、列表、表格与公式里的字，图片写成链接，文本框里的字写成引用，每段前面写着段落号；助手读这份文字版，模型能读图时也看图片，引用时出处写 Word 文件加段落号。旁边还有一份分段清单：按标题把 Word 文件分成若干块，每块写着段落范围与行号，助手据此一次读几块，用 `grep` 找段落。另外还写一份位置表，按段落号记下 Word 文件的各个标题，标题文字与文字版里的相同，自动编号不论什么格式都写上；来源标签的章节取自它；助手不读它，材料清单也不列它。

### 1.3 助手的工具

启动配置（`backend/profiles/dev.json`）的工具白名单里恰好有十二个工具：pi 内置的 `read`、`ls`、`grep`、`find`，加上 Taskwright 自己的八个。pi 的其他内置工具（例如 `bash`、`edit`、`write`）不加载，所以助手不能执行命令、不能改文件，只能经 `save_revision` 改交付物、经 `save_diagram` 存图。

| 工具 | 做什么 | 核对什么、什么情况下拒绝 |
|---|---|---|
| `read`（pi 内置） | 读一个文件，例如材料、任务定义或领域规矩文档。 | 只读。读知识库目录下的文件而不写要读几行时，一次只读 120 行。 |
| `ls`（pi 内置） | 列出一个目录的内容，例如 `inputs/`。 | 只读。 |
| `grep`（pi 内置） | 在文件里搜一个词或一个模式，返回命中的行，带文件名与行号，例如找材料里哪几段说到某个术语。 | 只读。返回超过 40 行或 6144 字节时截短，并请助手换更具体的词或者分次搜。 |
| `find`（pi 内置） | 按文件名模式找文件，例如 `inputs/*.docx.md`。 | 只读。 |
| `save_revision`（保存修订） | 把一批按条目的操作（新增、修改、删除）存成交付物的一次修订。条目编号由工具生成。 | 核对集合与字段是否存在、值的类型是否与声明一致、必填字段是否填了且没有被清空、每个新增条目是否至少有一条来源且种类、出处、摘录三项齐全、来源指向的字段是否存在、引用的条目是否存在；同一批里排在前面的新增条目算作存在（编号按操作顺序接着集合的流水号推算），引用排在后面才新增的条目会被拒绝。修改与删除必须写 `base_revision`，也就是条目当前所在的修订号；条目已经被改到更新的修订时整批拒绝，并说明是谁改到了哪次修订，附上它现在的内容。种类为「用户的话」的来源，工具会在本会话用户说过的话里逐字查找这段摘录并自己填写出处，找不到就拒绝。种类为「文档原文」的来源，位置由写来源的一方声明，工具只核对：摘录必须是出处所指材料文件里连续的一段，Word 材料要从出处写的那一段开始，最多延续到其后相邻 5 段，摘录里的空行只当空白；不是连续的一段（例如把不相邻的几处放进一条来源）、改了字或出处读不到时拒绝，拒绝原因提示引了几处就写几条来源、每条各写段落号。工具不替它拆开，也不替它找后几处的位置。问题条目（状态字段的取值里有「用户决定保留」的集合，例如「问题」集合）写下之后，助手修改它只能改状态与处理结果，改别的字段被拒绝。助手把问题条目的状态改为「已解决」或「用户决定保留」之前，用户要在问这个问题是否已解决的请选择卡片上点过对应的一项（「已解决」或「先不管，保留」），而且点了之后这个问题条目与它的关联条目都没有再改过（不论是谁改的），以最近一次点击为准；用户打字说解决了不算，被拒时说明写明要先发卡片。新增问题条目时状态不能直接写成这两种。你在界面上的直接操作不受这条限制。修改条目时原来的来源默认保留：列表型字段按每一项的内容认它现在排在第几，来源跟着那一项走，所以在列表里插入、删除别的项或调换先后之后，来源仍指着原来那句话；列表里删掉的项，指到它的那一处去掉；被改写的内容（原地改了文字的一项，或者整个改了的字段）上的来源照旧留着，保存结果里提醒助手检查它是否还支持改后的内容。这次新给的来源接在后面，与原来同一句摘录的合成一条。助手要去掉某条来源，就做一次只给来源、不改字段的修改，重新标注这个条目的全部来源，保存结果里写明这次去掉了哪几条。保留下来的旧来源不再核对摘录。一个没有改动任何内容的修改操作会被拒绝。一批操作里只要有一个不对，整批**都不写入**，并逐条列出每一处问题。同一个工具调用编号的调用再来一次（模型重试，或 pi 重发这次调用）时什么都不写，工具交回第一次的结果，末尾加一句「这次调用之前已经保存过，没有重复写入」，任务在两次之间已经完成也一样；数据库里一个工具调用编号至多形成一次修订。没有工具调用编号的调用（模型服务没给编号时 pi 交来的是空编号）无法这样认出，每次照常保存。它不评判内容好坏。 |
| `save_diagram`（保存图） | 新画一张图、修改一张已有的图，或者删除一张图；一次一张。什么时候画由说明规定：整理建模阶段助手主动画五种图，别的时候在用户要求时画。图有图名、种类（系统边界图、用例图、对象关系图、状态图、时序图、流程图六选一）、Mermaid 文本、说明与来源；编号由工具生成（`D-001` 这样）。保存前由任务服务校验 Mermaid 文本的写法：不对就不保存，把第几行附近错在哪里交还助手；同一轮里连续三次不过，助手不再试、改为告诉用户；校验没有做成（例如任务服务联系不上）时同样不保存，并让助手告诉用户。修改与删除要写图的编号与它现在的修订号。 |
| `reply`（回复） | 把助手要对用户说的话发给用户。一次回复由告知（只写事实，可以点名说到的条目，界面画成条目链接）和一段成文的话组成；只有助手在等用户的一个具体回应时，才再加一个向用户要的回应（提问、请确认、给建议值、请选择、提议之一），它的文字是要用户回应的那句话，不是答案。 | 必须单独调用，作为这一轮的最后一步。核对形式：该有的部分齐全；向用户要的回应是五种之一；请选择至少有两个 key 不同的选项；给建议值必须带建议值和至少一条依据；提议的预览项格式正确。给建议值的每条依据与 `save_revision` 的来源同一套核对，被拒时的说法也相同：文档原文的摘录要逐字出现在材料里（Word 材料与来源一样写段落号），用户的话要逐字出现在本会话用户说过的话里（出处由工具填写），依据另一个条目时摘录要出现在那个条目当前的文字里；种类为「助手补充」的不核对摘录，只要求写了理由。有一条依据找不到，整条回复被拒。提问、请确认、给建议值、提议必须点名所涉及的条目及其**当前**所在的修订号（对照数据库核对），标明 `scope: "general"` 的除外。告知点名的条目按同样的规矩核对。卡片上的话只是把某条告知再说一遍（去掉空白与标点后相同或被它包含）时拒绝。连续被拒三次后，它只要求一段成文的话；第五次仍不合格时放行一条纯文字回复，并标为降级。它不写数据库。 |
| `get_item`（查看条目） | 写图的编号时看的是那张图：图名、种类、说明、Mermaid 文本、来源与它自己的修订号。查看一个条目：全部字段、全部来源、当前所在的修订、它改动过的修订、评审与确认状态；也可以指定看它截至某次修订时的样子。 | 只读；条目不存在或任务还没有那次修订时报错。 |
| `get_task_status`（查询任务状态） | 查看每个集合的条目、每条完成条件是否满足（不满足的列出条目）、未解决的问题条目、**未读清单**（用户从没看过的条目，带标题）、最近一次修订，以及每份材料被引用的情况：Word 材料按分段清单逐块写标题、段落与行号范围、被几个条目引用，以及还有几段没有被任何条目引用；文本材料写被几条来源引用。 | 只读；与交付物看板用同一组核对。 |
| `search_knowledge`（查找知识库） | 在任务选用的知识库里按意思与按字面两路找与一句话最相关的几个片段（不写是 3 个，最多 5 个），每个带所在的知识库与文档、位置、它在两路里各排第几、出处的写法与逐字的原文；用词不同也找得到，条号与原话按字面找得到。 | 只读。助手查知识库用这一个工具。两路由任务服务算（按意思那一路要调嵌入模型）。没有选嵌入模型、文档还没有换算好或者模型服务出错时不拒绝，退到只按字面找，开头一句写明。交给助手的原文是按片段的位置从文档里现读的（Markdown 与纯文本连空行逐字节相同，Word 文档每段一行、带段落号），助手照它抄摘录，不必再读文件；全部文字不超过 8192 字节，放不下时写明还有几条没有列出。联系不上任务服务时，它回一句说明，请助手再查一次，仍然不成就告诉用户并记一条问题条目。 |
| `request_review`（请求评审） | 请评审者评审条目当前所在修订的内容；不写 `items` 就评全部待评审的条目。只在用户在对话里要求评审时使用；评审平时由用户在界面上发起（见 1.9 节）。 | 点名的条目不存在、已删除、不在给定的修订、所在集合不要求评审时拒绝；上一批评审还在进行时拒绝。结果逐条写「合规」或「不合规（问题 N 处，建议 M 条）」，每条发现带规则编号。 |
| `publish_version`（发布版本） | 把交付物现在的样子发布为第 N 版：先请任务服务按这次修订生成文档、存下 Markdown 与 Word（Word 里的图写成 Mermaid 文本，助手手上没有画好的图片），再记下版本记录。参数 `note` 是可以不写的发布说明。发布之后任务照常可以修改。 | 只在评审确认与编写文档两个阶段可用。与 `get_task_status` 做同一组条件核对；有任何一条不满足就拒绝。未读的条目单独写成一句，助手可以原样转告用户：「还有 N 条你从没看过：……」；其余没满足的条件列在后面。条件都满足之后再核对用户同意了：最近一次对「这个任务是否已经完成」卡片的点击，点的要是 `key` 为 `complete` 的那一项（「已完成，发布版本」），而且点了之后交付物没有新的修订；打字说发布不算，已读、评审、保留写法不产生修订。不满足时拒绝，拒绝的事实都以「第 N 版没有发布」开头，后面是三种原因之一：用户还没有在卡片上点「已完成，发布版本」；用户在最近一张卡片上选的是别的项；用户点了之后交付物又有了新的修订、要重新问。指引请助手用这样的卡片问用户，两个选项是「已完成，发布版本」与「还没完成，继续修改」。条件还没满足时只报条件。任务服务没能写好存档时也拒绝，写明这是程序的问题、请用户稍后在页面上点「发布版本」再试。 |

**被拒的调用有记录。** `save_revision`、`reply`、`publish_version`、`request_review` 因为输入不合规、或者因为助手还没写下对用户这句话的理解而拒绝一次调用时，工具在任务数据库的 `tool_rejection` 表里记一行：哪个工具、调用编号、所属的那次工作、原因种类（输入不合规，或缺前置步骤）、拒绝文字的两层（事实，给人看；指引，给助手看），以及被拒输入的前 2000 个字符。不是输入问题的拒绝，例如没有可用的模型、上一批评审还没做完、数据库出错，不记。观测台把这一行显示在那次被拒的调用下面。

### 1.4 用户在界面上的直接操作

以下操作不经过模型。它们在 pi 进程里运行，走与工具相同的写入函数，所以受同样的核对。改动条目的操作各产生一次修订；标为已读不产生修订。

| 操作 | 效果 | 什么情况下被拒绝 |
|---|---|---|
| 改字段 | 把一个条目若干字段的新值存成一次新的修订。条目上的话都算你自己的，来源只标注引用了哪些原始片段，谁改的、怎样改的看修订。你改写了的内容（一个普通字段，或列表里原地改了文字的一项）原来的来源去掉，不加新的来源；你没动的内容来源保留：列表按每一项的内容认，插入、删除别的项或调换先后之后，来源跟着原来那一项走；删掉的项上的来源随之去掉；指整个列表的来源在你改了其中一项时留着。改完之后条目可以一条来源都没有。同时登记你已确认这个条目在这次新修订的内容。 | 你打开之后条目又被改过（例如另一个浏览器页签先保存了；会告诉你它现在所在的修订，请重新打开）、条目已删除，或者新值通不过与 `save_revision` 相同的核对。 |
| 删除条目 | 在一次新修订里把一个或几个条目标为已删除。 | 你打开之后条目又被改过，或者条目已经删除。 |
| 标为已读 | 记下你看过了这些条目当前所在修订的内容，看过就算确认。你打开条目详情时界面自动这样做；在请过目卡片上点「这几条都看过了」也是它，同时通知助手继续往下做；也可以在列表里勾选几条一起标为已读。条目在那次修订上已经记过的，不再写。 | 写的修订已经不是条目当前所在的修订。 |
| 撤销一次修订 | 存一次新修订，把所选修订涉及的每个条目恢复成那次改动之前的样子（删掉的条目恢复，新增的条目删除）。不抹掉任何记录。网页界面按修订日志预先判断撤销不了的修订，把它的撤销按钮变灰并说明原因。 | 那次修订之后，其中某个条目又被改过或已删除。 |
| 标为暂不处理（接口里的 `keep_pending`） | 在一次新修订里把一条问题条目的状态改为「用户决定保留」，同时登记你已确认它在这次修订的内容。 | 条目所在集合没有含这个取值的状态字段。 |
| 保留写法 | 保留一个评审不通过的条目现在的写法，理由可空；这条按你的决定算通过，条目再改动，评审要重做。 | 条目当前修订在当前规则下没有评审不合规的记录，或者已经保留过。 |
| 撤销保留 | 撤销保留，条目重新算作评审不通过。 | 条目当前修订上没有生效的保留。 |
| 开关评审规则 | 关掉或打开一个集合的某条可选规则，或把它升为必选；不产生修订。 | 规则是必选的、集合没有评审规则，或者与现在一样。 |
| 发布版本 | 在工作视图里发布一个版本：完成条件全部满足、最近一版之后交付物又改过（还没发布过也算）、助手不在工作时，条目区顶部出现一条绿色提示条「可以发布第 N 版了。」，按钮是「发布版本」；确认框里可以写发布说明。确认之后页面先把文档里的图画成图片，任务服务按页面看到的修订生成文档、存下 Markdown 与 Word，再与 `publish_version` 做同一组核对（这次点击就是你的同意，不看阶段），记下版本。任务照常可以修改；版本的发起方记为你，对话里追加一句说明，不引出助手的工作。助手问同一件事的卡片还没回应时，提示条不显示。 | 完成条件没有全部满足，或者交付物已经有了比页面看到的更新的修订。 |
| 删除任务 | 在任务列表里删除一个任务：任务目录与它的对话记录都删掉，没有回收站；确认框写明材料、条目与发布过的版本各几，可以先导出这个任务的数据包。服务日志记一行时刻、任务编号、任务名与请求来自哪里。 | 助手正在这个任务里工作。 |
| 请求评审 | 评审全部待评审的条目（条目区顶上的「评审 N 条待评审的条目」）、一个条目（详情里的「评审这条」）或完成条件面板里列出的条目（「评审这 N 条」）。请求立即返回，评审在后台进行，见 1.9 节。不产生修订。 | 上一批评审还在进行、没有要评的条目、点名的条目不在它当前所在的修订，或点名的条目在当前修订、当前规则下已经评过（同一次修订、同一套规则只评一次）。 |

**看过就算确认。** 没有「确认」按钮。打开条目详情，就在条目当前所在的修订上记一条依据为「已读」的确认标记，条目状态从「未读」变成「已读 · 修订 N」（N 是你最后看过的那次修订）。只认「打开详情」这一个动作：列表里看到不算，也不计你看了多久。已读是按条目算的、只进不退：看过一次就一直是已读，助手之后再改它也不会翻回未读；它改过、你还没看的地方由「刚改」标签和详情里的琥珀色字段边框提示，不挡发布。再打开一次时，会在当时的修订上再记一条已读，导出文档时据此如实写你最后看过哪次修订。你不必在对话里说「可以」：助手不再按你说的话登记确认。

**你自己改的算已确认。** 你亲手写出来的内容就是你认可的内容：改字段或标为暂不处理成功时，会在产生修订的同一个事务里，为这个条目在新修订上登记一条你的确认，依据记「界面修改」。删除条目与撤销修订不会自动确认。详情底部右侧只显示状态，没有撤回已读的按钮。

助手工作期间，所有操作（包括请求评审）都会被拒绝；只有一个例外：助手工作期间打开条目详情照样记为已读，因为它不改交付物。每次操作之后，助手会在对话里看到一条说明，写明改了什么、产生了哪次修订以及改后的字段值，例如「用户改了 UC-002 的「基本流程」，产生修订 5，UC-002 现在是修订 5。」

助手回复卡片上的按钮（选某个选项、「我不知道，你按常识补」、「换一个」等）会作为你的一句话发给助手，并附一条说明，标明你点的是哪张卡片的哪个选项。

**看得到改了什么。** 网页界面在三处显示改动。右侧栏的「修订」页签是修订日志，最新在上：谁改的、触发它的事（助手回应的是你的哪句话，或者你做的哪次直接操作）、碰到的每个条目以及改了哪些字段；在卡片上可以看一个条目的差异、撤销这次修订、按这次修订生成文档。助手保存过修订的回复带一枚小标签点名这几次修订，点它打开修订页签。条目详情里，自你上次确认的那次修订以来（从没确认过的，自新增的那次修订以来）助手改过的字段加框，差异按那次修订画；你自己改的字段不加框。打开详情就记为已读，所以框在你打开的那一刻定下来：详情开着时一直看得到，下次再打开就不再出现。助手最近一次运行改过的条目在列表里标「刚改」，从没打开过的（未读）条目加粗。条目区里灰掉的写入按钮，鼠标停在上面会说明原因（助手工作中、正在保存、看的是旧修订、任务已结束）。问题条目写下之后在网页上不能直接修改，只能「先不管，保留」或删除。

**问题跟着条目走。** 网页界面按每个问题条目的条目引用字段（关联条目）算出哪些问题牵涉哪个条目，不另外存关系。列表行上的**问题 N** 是牵涉这个条目的未解决问题数。条目详情里先列出这些未解决的问题（已解决和先不管的问题留在「问题」页签里）：每个都可以在那里直接回答，发给智能体的话是「回答 <问题编号>：<回答>」，算作你说的话；也可以照常标为先不管。从问题跳到条目之后，顶部保留一条回到「问题」页签那个问题的路。

### 1.5 来源

条目在每次修订下的内容至少带一条来源；一条来源可以指整个条目、某个字段，或者列表型字段里的某一项。来源说的是这个条目依据了什么，现在写入的有五种：

| 种类 | 由谁写 | 出处 | 摘录 |
|---|---|---|---|
| 文档原文 | 助手 | 材料的路径；Word 文件写路径加段落号，例如 `inputs/a.docx#p37`；PDF 文件写路径加页与块，例如 `inputs/a.pdf#p3-2`（摘录不跨页，核对前两边都做规范化：部首字符换成通用汉字、全角半角归一、去掉空白与连字符）。引用知识库里的文档时写 `knowledge/<知识库编号>/<文档名>`，Word 文档同样加段落号 | 材料里逐字摘录的原话（Word 文件要摘自那一段，或从那一段开始、跨到后面最多五段） |
| 用户的话 | 助手写摘录，工具填出处 | 用户说这句话的会话与消息 | 逐字摘录，工具对照对话核对 |
| 助手补充 | 助手 | 不用写，工具填「助手补充」 | 理由：为什么这样补充或推断；不写理由整批拒绝。理由里用直角引号逐字引出补进正文的那几个字，页面据此在正文里标出；引出的字不在这条来源支持的那几处正文里时整批拒绝（没有引号的不核对，问题条目不核对） |
| 条目 | 助手 | 同一个任务里另一个条目的编号，例如 `DN-002`、`UC-003`，哪个集合的都可以 | 逐字摘自那个条目当前内容里的一段 |
| 图 | 助手 | 同一个任务里一张图的编号，例如 `D-002`；图必须还在 | 可以是空的；写了就要逐字出现在那张图现在的 Mermaid 文本里。只有条目能依据图，图的来源里不能写这一种 |
| 用户直接修改（早期版本） | 早期版本由系统写，现在不再写 | 那次界面操作的编号 | 新值的开头部分；旧记录留在库里，页面、生成的文档、评审与助手都不再读出，修改条目时也不沿用 |

出自知识库文档的来源种类仍是「文档原文」，只是出处以 `knowledge/` 开头。助手只能引用这个任务选用的知识库里的文档，摘录照材料的规矩逐字核对；任务选用了哪些知识库、里面有哪些文档，写在每条会话开头的任务现状消息里：每份文档只列名字、种类、大小与出处的写法，不给路径，也不带正文。助手用 `search_knowledge` 去查，查到的片段就是逐字的原文，照它抄摘录，不整份读文档，也不把知识库里的文档整理成条目。逐字核对只放宽换行符与每行行尾的空白（材料来源也是这条规则）；Word 文档表格里的字，出处写摘录所在那一格里那一段的段落号。程序不拦助手用别的工具碰知识库的目录，只给返回定量：`grep` 一次最多 40 行、6144 字节，`read` 读知识库里的文件不写行数时只读 120 行。页面上这种来源的标签写「知识库」，出处写「知识库名 / 文档名」，点它在只读对话框里看那份文档的正文；文档已经不在知识库里时，来源照旧保留，出处旁写「这份文档已经不在知识库里」。生成的文档里写成「知识库，出处 知识库名 / 文档名」。

「条目」这种来源让一个条目依据任务里已经记下的另一个条目，例如用例依据总体分析里的一页主题（见 2.1 节），约束依据一个用例。被依据的是总体分析里已废弃的一页时拒绝，并指出改看哪一页。工具核对出处是一个还在、没有删除（也没有在同一批里删除）的条目，不是它自己，并且摘录逐字（包括标点）出现在那个条目当前内容的某段文字里，不是就整批拒绝；同一批里排在前面新增或修改的条目也可以引用，摘录对着它将要保存的内容核对。工具同时记下引用那一刻被依据的条目的修订号。之后那个条目又改了，读出来的这条来源就标为「依据已变」（它现在的修订号大于记下的修订号）；它被删除了就标为「已经删除」。这两个标记是读的时候现算的，不存库。条目被修改而这条来源原样沿用时，记下的修订号不变（助手改别的字段、用户在页面上改字段、撤销都一样）；助手重新写上这条来源，才换成最新的修订号，标记随之消失。反过来，每个条目读出来带着「被谁依据」：把它写成来源的别的条目（只数还在的条目当前修订下的来源）。生成的文档里写成「集合名 条目编号（「摘录」）」，例如「总体分析 OA-002（「摘录」）」。

**图。** 图是任务的另一种要素，不是集合里的条目：它没有字段，不评审，不算进完成条件；有业务说明的任务里，图画在生成的文档与整份 Word 文件中它所属的那一节或那一章，别的任务的文档里没有图，勾选条目的 Word 导出里也没有图；任务定义里不用声明，哪个任务都可以画。图的修订号是这张图自己的（新画是修订 1，之后每改一次、删除一次各加一），不占任务的修订序号，所以修订日志与撤销不涉及图。图的来源与条目的来源是同一套种类与逐字核对，有三处不同：图没有字段，来源不写支持哪几处；图依据条目时可以不写摘录；被依据的条目只认已经保存的。图里的一个节点画的是某个条目时，助手把条目编号写在这个节点的文字里（例如 `r1(["UC-001 借出图书"])`），读图的详情时程序据此从 Mermaid 文本里扫出「图里画了谁」。保存时程序核对两件：写进文本的条目编号必须是现有、没有删除的条目；画进图里的每个条目必须各有一条种类为「条目」的来源。这样被画的条目之后改了，图的那条来源就标为「依据已变」，条目的「被谁依据」里也列着这张图。用例图用流程图的写法画（参与者与用例写成圆角节点，系统边界写成子图，包含与扩展写在虚线上），不用 Mermaid 自带的用例图写法。新建任务时集合的编号前缀不能单写 `D`，免得与图的编号同形。用户可以在页面的「图表」页签里直接改一张图的 Mermaid 文本：经过同样的写法校验之后存成这张图的一次新修订，发起方是用户，不经过智能体。这样的改动不做上面那两件核对：不要求用户写来源，文本里写了任务里没有的编号时，「图里画了谁」把它标灰并说明。智能体从会话里的一行说明得知图改了，要看新的文本用 `get_item`。系统边界图也用流程图的写法画：系统写成子图，与它打交道的角色与外部系统写在子图之外；保存时另核对至少有一个子图与一个子图之外的节点。对象关系图用 Mermaid 的类图写法画，条目编号写在类的方括号文字里。条目可以把一张图写成来源（种类「图」）：保存时记下图当时的修订号，图之后改了，这条来源标为「依据已变」，图的详情里列出依据它的条目。用户打开看一张图时页面可以记一次「看过」（界面操作 `mark_diagram_viewed`，只记一条事件）：助手改过图之后要再看一次，「条目依据的图用户都看过」这盏灯据此判。

直接修改产生的修订同时登记为用户已确认（见 1.4 节），所以你改出来的内容一开始就是已读的，之后也不会翻回未读。

生成的文档里，「用户的话」的出处换成读者能看懂的写法「会话「<会话名称>」里用户的第 N 句话」；会话记录找不到时写「对话里用户说的话」，不把内部编号印进文档。早期版本写下的「用户直接修改」不写进文档；条目没有来源时，来源一项写「（无）」。

### 1.6 完成条件

任务定义为每个集合列出必须满足的条件。代码认识四个条件名：至少一个条目；没有状态为未解决的条目；每个条目评审通过；每个条目用户确认。每一条都是对数据库事实的核对，不评判内容：「评审通过」指条目在它当前所在的修订上有一条合规的评审记录（不满足时，说明里把还没评审的条目与评审不合规的条目分开写），「用户确认」指条目在任何一次修订上有过一条接受的确认标记（依据是已读、界面修改或早期的其他依据都算），也就是用户看过它、它不是未读。评审是挂在「条目加修订」上的标记，条目之后再改动时不会跟着移动，所以改动一个条目之后要重新评审；确认标记在库里同样挂在「条目加修订」上，但门禁只问有没有看过，改动之后不翻回未读。导出文档时，条目导出的修订比用户最后看过的修订新，依据写「用户最后看过修订 N，之后由助手改为修订 M」。集合为空时，「每个条目……」这类条件在门禁上算满足，但报告时不算作「已满足」。交付物看板、`get_task_status` 与 `publish_version` 用的是同一组核对。

完成条件之外另有提示，不挡发布版本。有「总体分析」集合的任务：在用而还没有贴标签的主题（「有 N 页主题还没有贴标签」；贴了标签的主题才会进文档，评审也只认贴了标签的主题）。`get_task_status` 与完成条件面板都列出这些提示。

### 1.7 文档

生成文档时，把交付物按某一次修订（缺省为最新）整体按任务类型的 Markdown 模板渲染出来，也可以只列出那次修订时交付物里的其中几个条目；不经过模型。每个条目写的是它在那次修订时的内容。用的模板是任务目录里的那份副本，由任务定义里的「文档模板」一项指定；它在建任务时从 `task-types/<任务类型>/` 复制过来，所以改代码仓里的模板只影响之后新建的任务。每个集合内的条目按编号排列。文档开头写明按哪次修订生成。未经评审或未经确认的条目也写进去，并在文档里如实标出：带标注的条目写明它的内容来自哪次修订、评审状态（未评审、评审通过或评审不通过，取那次修订上最近一次评审）和确认状态（在那次修订上：未确认，或已确认并写明依据：已读、用户修改，或较早的明确确认）。随附模板里的问题条目只写种类和状态，不带这些标注。随附模板的结构与页面上的业务说明相同：开头是任务名、生成说明与目录；前七章是业务说明，由程序排出来（`{{业务说明}}`），章与节号同页面的目录，图放在它说明的那一节，角色与用例对照表、规则表、目标与决定、决策记录与待澄清事项都是从页、问题条目与图算出来的；第 8 章起是需求条目的各个集合；最后是追溯附录（`{{追溯附录}}`），写每个需求条目依据了哪几节、哪几张图。没有贴标签的与已废弃的页不进文档；还没有了结的待澄清事项标【待澄清】，带「待定」的句子标【待定】；页与条目取那次修订时的内容，图取它现在的内容。任务目录里的模板副本没有 `{{业务说明}}` 这个占位、而任务有总体分析这个集合时（这一版之前建的任务），改用产品现在自带的模板，所以它们的文档也是这个结构。模板里另有 `{{目录}}`（整份文档二、三级标题的清单）与 `{{任务名}}`。模板可以按字段值筛选、按字段归组：`{{#每个 总体分析 标签=概念 状态=在用}}` 只取这个字段等于该值的条目，`状态!=已废弃` 取不等于的（列表型字段按「含有这一项」比；几个条件用空格隔开，同时成立才算），同样的条件也能写在 `{{#没有 …}}` 里；`{{#按 字段 归组 集合名 条件…}} … {{/按}}` 按这个字段的值每组渲染一遍，`{{组名}}` 是这一组的值（空值写「（未填）」），`{{#组内每个}} … {{/组内每个}}` 渲染组里的条目；组的先后按每组第一个条目的编号。`{{#按 字段 逐值归组 集合名 条件…}}` 按列表字段的每个值归组：一个条目有几个值就进几个组，没有值的不进任何组，组的先后照字段声明的取值，条件里可以写「组!=某个值」去掉某一组。条目里面，`{{#逐项 字段}} … {{/逐项}}` 把列表字段一项一项地写（`{{项}}` 是这一项，`{{序号}}` 从 1 起），`{{#有 字段}} … {{/有}}` 只在字段有内容时写中间那段，`{{字段|首段}}` 取文本的第一段，`{{字段|顿号}}` 把列表用顿号连成一句。结果随时可以预览或下载，发布版本之前、之后都可以。预览在页面上是排好版的样子，图当场画出来；下载有 Markdown 与 Word 两种，Word 文件与预览是同一批内容块，图由页面画成图片随请求交给任务服务嵌进去（任务服务自己画不了图；不经页面直接调接口时，图的位置写它的 Mermaid 文本）。把勾选的条目排成表导出 Word 是另一个入口，照旧。修订号超过最新修订，或者列出的条目在那次修订时不在交付物里，会被拒绝。

### 1.8 留痕不可改写

- 每次改动都是一次新的修订，不覆盖也不抹掉任何内容。条目在任何一次修订下的内容都还读得到，删除的条目保留它之前的内容；撤销是再加一次修订，而不是删掉一次修订。
- 每次写入（一次工具调用或一次直接操作）恰好记一条事件，事件与改动本身在同一个数据库事务里写入：要么都写进去，要么都不写。唯一的例外是改字段与标为先不管：它们在同一个事务里记两条事件，一条是修订，一条是随之登记的确认。标为已读记一条 `ITEM_VIEWED` 事件；要标的条目都已是已读时什么都不记。
- 每条事件都记着所在的会话、对应的工具调用，以及改动者是助手还是用户。

### 1.9 评审

评审者按任务类型的评审规则核对条目。任务定义为每个要评审的集合写明一份规则文件（随附的任务类型里是 `docs/review-rules/use-case.json` 与 `ears.json`），每条规则有编号（例如 UC-R7）、级别、条文、反例与正例。**必选**规则决定评审通过与否，**可选**规则只给建议。每个任务可以在评审页签的规则区关掉某些可选规则，或把它们升为必选（写进任务定义的「关闭」「升为必选」两项）；必选规则不能关。随附的任务类型里，核对「来源是否支持内容」的 UC-R15（功能用例）与 EARS-R10（非功能需求与约束）是可选规则，任务定义默认把它们关掉；需要时可以在评审页签的规则区为一个任务打开。「问题」与「总体分析」两个集合不评审。任务里有「总体分析」集合时，两份规则文件各另有一条可选规则（UC-R16、EARS-R11，缺省开着）：条目里出现的专门名词应当在总体分析里有一页主题。

- **谁发起。** 由你在界面上发起。助手不主动评审；只有你在对话里要求评审时，它才调用 `request_review`。
- **评审者看到什么。** 规则清单、字段声明、条目与它的来源；材料全部加起来不超过 20000 字时给材料全文，超过时只给这个条目的文档原文来源所在的自然段，并写明看到的不是全文。在来源之后，评审者还看到这个任务里没有删除的别的条目，取各自当前所在的修订，分两节：**【相关的条目】**写全部字段，相关指的是文档原文来源落在同一份材料的同一个自然段（Word 材料是同一个段落号）、引用了同一句用户的话、引用了这个条目或者被这个条目引用的问题条目；**【其余条目】**每个一行简述，全部字段的内容连起来不超过 120 个字时写全，超过时只写第一个字段。别的条目不给来源、修订号与评审结论。第一行写明别的条目共几个、其中相关的几个；两节合起来超过 10000 个字时，先从【其余条目】的末尾往前省，再省【相关的条目】，被省的那一节写明有几个没有列出。别的条目只是背景：评审者不对它们列发现；材料里的某项内容已经写在别的条目里的，不算正在评审的条目违反。UC-R11 这类「材料里定没定下来」的规则，以给它的材料为准，材料里没有提到、条目里补充的内容不算违反；那一处标的来源是用户的话或者总体分析的一页主题时，说明这件事已经由用户定下或确认，也不算违反；任务里有「总体分析」集合时，评审者在别的条目之后另看到 **【总体分析的主题】**一节：贴了标签、在用的主题的标题与别名，一行一页，最多 3000 个字，它只用来判断「专门名词有没有主题页」这条规则；UC-R15、EARS-R10 这类「来源是否支持内容」的规则打开时，只拿标了来源的那一处对照来源里引用的原话。评审者的调用要求温度 0；模型服务不接受这个参数时（默认模型就不接受），去掉它再调一次，并在模型调用记录里写明。
- **已知的限制。** 评审结论不跟着别的条目变：一个条目评审之后，别的条目改了或者删了（例如写着罚款上限的那一条约束被删掉），已有的结论不变，也不会自动重评。相关按自然段算，材料整段不分段时，几乎每个条目都与别的条目相关，都会给全部字段。
- **怎样评。** 每个条目由一次不带工具、不带对话的模型调用评审，一次最多并行 4 个，单个条目最多 60 秒，不合格重试一次。评审者的每条发现都必须引用清单里的规则编号；引用了清单里没有的编号、或者违反必选规则却没写改法的输出算不合格，重来一次。没有评完（超时、调用失败、两次输出不合格、评审期间条目被改）时不记合规与否。
- **结论由代码算。** 只要有一条违反必选规则的发现，条目就**不合规**；违反可选规则的发现只是建议。改法只写改哪个字段、往哪个方向改，不写改好的全文。
- **界面上看得到什么。** 条目区顶上写着待评审与评审不通过各几条；评审进行时页面右上角一条提示显示进度（「评审中 3/12」），评完换成结果。条目详情里，问题标红、建议标琥珀色，写在对应字段旁；点规则编号（「违反 UC-R9」）展开条文，「让助手照这条改」往输入框里预填一句请助手修改的话。条目的状态徽标写「评审不通过 N 处」「待评审」或「评审不通过 N 处 · 已保留」（未读排在评审不通过之后、待评审之前）；评审通过的不挂评审徽标，鼠标停在徽标上可以看到评审结论和建议条数。
- **条目或规则改了之后。** 评审是挂在「条目加修订」上的标记，并记下规则指纹（由规则文件与这个任务的开关算出的哈希）。条目改出新修订、或者规则改了之后，条目回到待评审；已有的评审记录不变。同一次修订、同一套规则只评一次，两样都没变时不能再评：「评审这条」是灰的，评审不通过的条目，提示里写着可以照发现修改之后再评，或者保留这种写法。早先版本的任务里，同一次修订、同一套规则下可能有几条评审记录（当时的「仍要重评」留下的）；这时各处（状态徽标、筛选、评审页签、完成条件、助手查到的状态、生成的文档）都以最后一条为准，保留也要在这最后一条之后做的才算数。
- **评审页签。** 右侧栏的评审页签按每个条目现在的评审结论来排，只认条目当前所在的修订、当前的规则。顶上一行写还有几个条目没有评审（规则改过之后写几个要重新评审），带一个评审它们的按钮；页面上发起的评审进行时写已经评完几个；还写有几处问题等你处理；什么都不缺时写全部条目都已经通过评审。下面是要处理的问题，按条目分组，每一处写位置、说明、改法，带「让助手照这条改」「保留这种写法」；再下面默认收起的是建议、已经没事的条目（评审通过的，与保留了写法的，后者带「撤销保留」）与评审记录（每次评审一行：时刻、评了几个、几个通过、几个有问题、几个没有评完，助手发起的注明）。更早修订上的、按改之前的规则评出的发现不在这里显示。页签上的角标是要处理的问题的处数，按每个评审不通过的条目结论所依据的那一次评审计。评审规则与开关在页签最下面一行点开的面板里。
- **保留写法。** 在评审不通过的条目的某一处问题上（评审页签里，或条目详情里某条发现旁），可以保留这个条目现在的写法，理由可写可不写；保留对这个条目的全部问题一起生效。这条按你的决定算通过；条目再改动，评审要重做。详情里标题旁的徽标写「评审不通过 N 处 · 已保留」；每条发现分两行，第一行是发现本身，第二行是去向（「未处理」「已在修订 N 改」「已保留 · 理由：……」）与操作「让助手照这条改」「保留这种写法」「撤销保留」。顶部的红色横幅只在还有未处理的问题时出现。生成的文档里写「评审不通过，用户保留（理由：……）」。只有你能保留。
- **助手看到什么。** 评审结束时对话区只追加一句计数和「看评审页签 ›」；助手经 `get_task_status` 读发现，它列出还没处理的发现（带规则编号和第几次评审），保留了写法的条目单独列一行。

## 2 任务类型「需求工程」

随附的任务类型「需求工程」（键 `requirements-engineering`，在 `task-types/requirements-engineering/`）覆盖需求工程的各项工作：从材料与对话里把需求弄清楚、写成业务说明与需求条目、评审确认，发布需求规格说明只是其中一项活动。这个任务类型在 0.6 之前叫「软件需求规格说明编制」（键 `srs-authoring`），格式 8 的任务升级时随之改名。它的界面文字和规矩都是中文的。

### 2.1 条目集合与字段

| 集合 | 编号前缀 | 字段（加粗为必填） |
|---|---|---|
| 功能用例 | UC | **用例名称**、**用例功能**、**参与者**（列表）、前置条件（列表）、后置条件（列表）、约束规则（列表）、**基本流程**（列表）、扩展流程（列表） |
| 非功能需求 | NFR | **类别**、**句式类型**（EARS 六种句式之一）、**需求语句** |
| 约束 | CON | **类别**、**句式类型**、**需求语句** |
| 问题 | TBD | **事项**、**种类**（待澄清、范围外、后续迭代）、建议的处理、**状态**（未解决、已解决、用户决定保留）、处理结果、关联条目（条目引用） |
| 总体分析 | OA | **标题**、别名（文本列表）、**它是什么**、例子（文本列表）、已经定下的（文本列表）、标签（概念、角色、流程、场景、目标、范围、假设、决定，可以选几个）、上级主题（本集合的一页）、**状态**（在用、已废弃）、改看（本集合的一页） |

总体分析是任务的中心：你和助手把这件事里的概念、角色、流程、场景、目标、假设与决定想清楚的全部痕迹，用这件事自己的话写成。一条就是一页**主题**：「它是什么」是一两段说明；「例子」每项一段话，有名字的人、具体的东西、具体的日子，以「反例：」开头的是这种不算的例子；「已经定下的」一句一条，每一条都要有自己的来源（保存时核对）；「标签」可以不贴，贴了标签的主题才会进文档、评审才认；「上级主题」只是目录里的位置；一页不再用时把状态改成已废弃，由另一页取代时在「改看」里写那一页。用例、需求与约束依据主题来写（来源种类「条目」）。

由这些内容另算出三样，都是读的时候现算、不存库：

- **待核实。** 一个条目（任何集合的）当前所在的修订上有助手补充的来源、而你还没有确认过，它就待核实。你打开看过（或点了确认）是确认整个条目；你亲手改，只确认你改到的那几处，只贴标签或只改上级主题不算。助手之后又改了它，它又待核实。
- **因依据而待核实。** 一个条目依据的那一页主题已废弃、待核实，或者你还没有看过时，它也要回头看；依据的是一张图、而你还没有看过这张图现在的内容时也一样。只看一层。
- **提到。** 贴了标签、在用的主题的标题与别名是词表；别的页与别的条目的文字里出现了这些词，就是提到了那一页，每页列出提到它的地方与原句。一个位置上取词表里最长的词，一句话里同一页只记一次。中文没有分词，太短的别名会在不相干的词里被认出来。

**在页面上叫业务说明。** 总体分析这个集合在页面上显示为「业务说明」，集合名与编号不变。页面把各页按标签排进固定的七章：概述与范围（范围、假设）、角色（角色）、业务流程（流程、场景）、业务对象（概念）、业务规则、业务目标（目标、决定）、决策记录与待澄清事项；贴了几个标签的页排进其中最靠前的一章，没有贴标签的列在「未归类」下面。章内按上级主题成树、同级按编号，依次编节号，已废弃的页不占节号。第 5 章与第 7 章没有自己的页，内容是规则表与按时间排的决定和待澄清事项。图画在它说明的地方：系统边界图、用例图、对象关系图在第 1、2、4 章的章首，流程图与状态图在把它写成来源的那一节里，别的图在它第一个来源页那一节的末尾；来源里一页主题都没有写的图另列在「未归入节的图」里。第 2 章章首的角色与用例对照表是从用例图的节点与连线算出来的，格子里是连线上写的字，没有写字的写「参与」。一张图在页面上画出来并且看得见，页面就替你记一次「看过」（界面操作 `mark_diagram_viewed`）。这样的任务没有图表页签；没有总体分析的任务照旧在图表页签里看图。

**任务、活动与流程。** 核读材料、澄清、整理建模、写条目、评审确认、编写文档是六项活动。把它们依次排起来就是「需求分析」这条流程，流程里的每一步叫一个阶段。每启动一次工作（需求分析，或者单独启动六项活动里的一项）就是一个**工作项**，带一条属于它的会话；从任务起点页或工作视图里的切换工作面板启动。一个任务可以同时有几个工作项，其中工作流程的至多一个。每条会话从建立起就属于一个工作项，或者不属于任何工作项（自由讨论的会话）：助手能写什么、拿到哪一段说明、哪个提议开着，都按这条会话的工作项算。自由讨论的会话里，助手能写的与澄清阶段相同（主题页与问题），不提议进入任何阶段。一个工作项可以先后有几条会话（换一条干净的会话接着做同一个工作项），它也没有终点：单独启动的活动照那项活动的规矩做、照它的灯看还差什么，做够了由助手在回复里汇报，工作项照旧留着；它不提议进入别的阶段，它的会话里进入、退回的卡片也不算数。不要的工作项由你删除，它的会话随之归档：默认不在会话清单里列出，打开之后按自由讨论办。启动什么工作只由你决定，助手没有启动工作的工具。每次启动、换站与删除都留一条记录（哪个工作项、谁、什么时候、为什么）。能不能启动一项活动只看任务里现有的内容——有没有材料、业务说明有没有内容、图是不是都看过、有没有需求条目、有没有已确认的条目——与之前做没做过哪一项、有没有工作项无关；这些前置条件写在每项活动的定义里。需求资产分六类：材料与证据、业务说明、分析模型、需求条目、评审与确认、文档与版本；每项活动的定义写明它读哪几类、写哪几类。

**工作分六个阶段。** 有总体分析的任务，在需求分析这条流程里工作分核读材料、澄清、整理建模、写条目、评审确认、编写文档六个阶段。阶段只由你移动，每次移动留一条记录（谁、什么时候、为什么）。往前：助手做完一段就发一张卡片说清下一段要做什么，你点「进入澄清」「进入整理建模」「开始写条目」「进入评审确认」或「进入编写文档」才算，点了助手随即开始做下一段；澄清与评审确认两段助手不主动提议，你问起或者它认为这一段齐了才提。往后：只有前面的结果大面积不能用时，助手发一张提议退回的卡片并写明原因，你点「退回某阶段」才退，点「留在本段」不退。助手自己不能移动阶段；它在回复里写阶段的做法已经停用，带了会被拒绝并指引改发卡片。阶段是需求分析那个工作项所在的站，不是任务的属性。需求分析在任务有材料时从核读材料开始，没有材料时从澄清开始。

**遇到没说清的地方就地记下，不退回。** 助手在任何阶段遇到一处局部不明白，记一条问题条目，在那一页、那张图或那个条目上写「待定」，接着做这一段；段末汇报与进入下一段的卡片里列出还没了结的问题。问题条目写明「是否阻断下游」：阻断下游的是没有它下一段做不出的，排在最前；不阻断的要写「何时回看」。问题改成已解决时要写「落实到」（答案写进了哪一页、哪个条目或哪张图），没有写会被拒绝。

**编写文档阶段补导语。** 这一段助手通读业务说明与已确认的条目，给有内容的章各补一页导语页（主题页上「导语所属章」写这一章的章名，一章至多一页在用的），给缺一句概括的节补一句，核对术语与各章说法；补写的内容来源种类是助手补充，等你过目。导语页不是节，不占节号，显示在章首页最上面；生成的文档里，概述与范围的导语在最前面，业务对象的在「术语与定义」开头，别的几章的在「总体描述」开头。助手请你过目的卡片上是「看过了，生成文档」与「需要修改」：点前者把卡片点名的页记为看过并打开生成的文档，不移动阶段，助手不因此工作。

**随时可用的七项。** 不管在哪个阶段，这七件事都可以做，不改变阶段，做完回到手上的事：提问与了结、修订、确认、记决定、复述、评审、工作进展。助手补的内容一律待核实，你确认之前不算定下。

**每个阶段助手能写什么由程序守着。** 总体分析的页与问题条目一直可以写；图在整理建模、写条目、评审确认三个阶段可以画；功能用例、非功能需求与约束的条目，以及请求评审，在写条目与评审确认两个阶段；评审确认阶段主题页只能改状态与改看；编写文档阶段只能写主题页与问题条目；发布版本在评审确认与编写文档两个阶段。助手在不许的阶段去写会被拒绝，拒绝里写明现在在哪个阶段、要先做什么、谁能移动。你在界面上的操作不受阶段限制。

**每个阶段还差什么。** 程序从任务现有的内容算出二十一条提示，分属六个阶段，例如「每份材料都被引用了」「每页流程都有一条以『例外：』开头的例子」「条目依据的主题你都看过」「没有还没了结的阻断下游的问题」「有内容的章都有导语」。它们只告诉你与助手这一段还差什么，不拦任何操作；助手查询任务状态时读得到现在这个阶段的几条。任务定义里没有相应字段的任务（这一版之前建的），与导语、阻断下游有关的几条显示为不适用。

**页面上的阶段条。** 阶段条只在调试模式下显示，位置在右侧栏「调试」页签的顶上，平常的页面上没有：六个阶段的名字，当前的标出来，已经过的填实；下面是现在这个阶段还差什么，每项一句，点了去差的那一页、那一条或那一份材料，已经齐的收成一句。阶段条只读，上面没有可以移动阶段的控件。助手提议进入下一个阶段的卡片标题是「进入下一阶段 · 请决定」，进入的那个选项是主按钮；提议退回的卡片标题是「退回前面的阶段 · 请决定」，请你过目的卡片标题是「补写的内容 · 请过目」；对话区在移动发生的地方各写一行（你点卡片进入下一段，或者照助手的提议退回前面的阶段）。业务说明（总体分析在页面上的名字）还没有一页主题时，页签里写明核读材料、澄清这两项活动把内容写进来，从头编制请在任务起点启动需求分析；这里没有把会话移到某个阶段的按钮。

**提议一直开着，工作进展随时可查。** 助手发出提议的卡片之后，这条提议一直开着，直到它的工作项换了站、助手发了新的提议、或者（请你过目的那一种）卡片点名的页你都看过了：输入框上方留一行「待决定」，带着生效的那个按钮，换一条同一个工作项的会话也在。提议有三种——进入下一段、退回前面的阶段、请你过目补写的页——这一行分别写「助手已提议进入某阶段」「助手已提议退回某阶段」「补写的 N 处待过目」。卡片上不生效的那一项分别固定写「继续本阶段」「留在本段」「需要修改」，点了只把卡片标为已选，助手不因此工作。每次运行开头给助手的任务现状说明与查询任务状态的结果里都带一行开着的提议，所以换了会话助手也知道提议开着：你说要进入时它请你点「待决定」一行，不重发卡片。做到哪里了由程序据任务记录算出一张「工作进展」卡（本会话在做什么：工作流程与所在的站、单项活动或者自由讨论；版本；任务的工作项；业务说明、模型、需求条目各自的数量与一句现状；这一段还差什么；待决定的提议），点输入框旁的「工作进展」、切换工作面板里的「查看工作进展」或者打 `/状况` 随时调出，新建的会话还没有人说过话时对话区开头也有它；它不经助手，卡上的「请助手汇报当前状况」才请助手讲；推荐的工作流程能启动时卡上另有启动它的按钮，「其他工作…」打开切换工作面板。任务起点页另有「待处理事项」一节，从条目、图、评审与各阶段的提示里汇总待澄清问题、待决定事项、待核实条目、未查看的模型与评审发现，每一项旁是启动相应活动或打开相应会话的按钮；澄清的输入页可以勾选要澄清的问题，勾选的编号写进范围说明。阶段的每次移动另记着它的所属流程，现在只有「需求分析」这一条。

**提问与选择的卡片没答就一直开着。** 用户在底部输入框说的话不会把卡片关掉；这句话是不是在回答某张开着的卡片，由助手按上下文判断并写进它对这句话的理解，页面据此把那张卡片显示为答过。在卡片自己的文本框里写的话带着这张卡片的标识，直接算作对它的回答。用户搁下的提问与请选择，助手不催；提议进入下一段之前，它照查询任务状态列出的「这一段还开着的提问与请选择」一次一张重发（回复里写明重发的是哪一张，原来那张不再等回应），仍没有答的记成问题条目，重发过一次的不再重发。这条规矩写在助手的说明里，工具只核对重发指向的卡片确实还开着，不核对助手有没有照做。

**助手的说明按阶段给。** 有阶段的任务，助手每次开始工作时拿到的说明由程序拼好放进系统提示：一份每个阶段都要用的说明，加上现在这个阶段的一段。这一段只写四件事：这一段做什么、不做什么、做到什么算够、怎样去下一段，另加一条「你的话落在这一段之外时」助手该怎么办（说明现在在哪一段、那件事怎样过去，需要你点的就发卡片；不照办越过阶段的要求，也不把你的话复述一遍求同意）。别的阶段的做法到了那个阶段才给，所以核读材料时助手手里没有「把材料都整理成条目」的要求。你在卡片上点了进入下一段，助手回应这次点击时拿到的就是下一段的说明。说明不再靠助手自己去读文件，也就不会只读到一半。这一段分两处写：做什么、不做什么、做到什么算够是这项活动自己的事；怎样去下一段、你的话落在这一段之外时怎么办，是它在需求分析这条流程里的那一步的事，在需求分析那个工作项的会话里才给。单独启动的活动的会话里，后一处换成固定的一段：做够了在回复里汇报，不提议进入别的活动。自由讨论的会话里，助手拿到的是澄清那项活动的说明，开头写明本会话不属于任何工作项，不带去下一段的部分。

**调试模式。** 服务带 `--debug` 启动时（缺省不带）多两样东西，给调说明文字的人用，请只在自己的电脑上开：设置页面多一栏「调试」，里面可以填一个提示词目录，目录里有哪一份说明文件就用它代替原来的那一份，改了文件之后对助手说下一句话就生效，不用重启；任务服务多一个接口，给出某个任务最近一次运行实际发给模型的系统提示，并标出每一段出自哪里。只认固定的十五个文件名，软链接不跟，一份文件最大 256 KB；产品只读这个目录。调试模式下工作视图的右侧栏另有一个「调试」页签，列出那份系统提示的各部分、阶段记录、现在这个阶段每盏灯的结果与它列出的编号、被拒的工具调用；任务页另有「导出为用户画像」，把这个任务里你说过的话整理成模拟器画像文件的草稿。

**先有你看过的主题，才能写条目。** 任务里要已经有至少一页在用的主题贴了标签、写了例子、你又看过，助手才能往功能用例、非功能需求与约束里新增条目；没有时保存被拒，并写明差的是什么。同一次保存里才新立的页不算；全部照抄材料、没有待核实内容的页，你没有看过也不算。

任务定义里的集合可以带一个可选的「界面」项，只影响显示：「右侧栏页签」（为 true 时在右侧栏另开一个页签）、「分组字段」（按哪个文本字段、枚举字段，或者写了取值的文本列表字段分组，条目行上也写成小标签）、「靠前的组」（这几组按给定顺序排最前，其余按每组第一个条目的编号排）、「说明」（写在这个集合页签下的一句白话）。随附的总体分析集合写的是 `{"右侧栏页签": true, "分组字段": "标签", "靠前的组": ["概念"], "说明": "用这件事自己的话写下的主题：它是什么、例子、已经定下的。条目依据它写。"}`。字段声明另有三样可选的写法：文本列表字段可以写「取值」（每一项只能从里面选，可以选几个）；条目引用字段可以写「只许本集合」（只能指向同一个集合里的条目）与「至多一个」（最多写一个编号），两样都写了的字段不许顺着它绕回自己。

完成条件：功能用例至少一个；每个功能用例、非功能需求和约束都要评审通过并经用户确认（也就是没有未读的）；「问题」集合里不能留有状态为未解决的条目；总体分析的每一页都要经用户确认。总体分析不评审。

### 2.2 领域规矩

`docs/domain-knowledge/` 下的两份规矩文档规定条目怎样写，助手动笔之前要先读完。

- **功能用例**（`use-case-writing.md`）：一个用例对应参与者的一个目的；用例的九项（用例名称、用例 ID、用例功能、参与者、前置条件、后置条件、约束规则、基本流程、扩展流程）各怎样写；不允许的写法（写界面细节、写材料里没有的功能、自行决定含糊之处、在规则里举例、用无法验证的词）。
- **非功能需求与约束**（`ears-writing.md`）：两类条目的区别；EARS（Easy Approach to Requirements Syntax，一种把需求写成固定句式的方法）的六种句式：普遍型、事件驱动型、状态驱动型、可选特性型、异常处理型、复合型；以及每一条都要满足的规矩（一条只说一件事、主语明确、可以验证、不用含糊的词、不举例、除非本身是约束否则不写实现手段、材料里的数值原样保留）。

两份文档里带编号的规则列表由 `docs/review-rules/` 下的规则文件生成（`node scripts/render-rules.mjs`），助手读的规则与评审者核对的规则是同一份文字。

### 2.3 助手的工作方式

助手的系统提示由扩展拼好，平台说明与任务 skill 的正文都已经在里面，不用再去读。**平台说明**（代码仓里的 `agent/prompts/stages/common.md`，所有任务类型共用，不复制进任务目录）写的是在 Taskwright 里怎样工作；**任务 skill**（任务目录里的 `.pi/skills/requirements-engineering/SKILL.md`）只写这类任务特有的做法。

来自平台说明的：

- **认得系统消息。** 会话开头的任务现状消息（续接旧会话时改为上次之后的变化）、界面操作的通知、工具的拒绝，都是系统写的，不是用户说的话。看到界面操作的通知，就按它写的修订号工作（「X-001 现在是修订 N」）。改、删、先不管、撤销各产生一次修订，标为已读与撤回确认不产生修订。用户在界面上打开条目会直接记下，不发通知；哪些条目用户还没看过，看「查询任务状态」的未读清单。
- **先读材料再动手。** 先列出材料目录；PDF 材料读它的文字版，分段清单按页；Word 材料先读分段清单，再按清单里的行号一次读连续几块，读完这几块就整理成条目并保存，再往下读（一次读得下的材料就一次读完）；其他文件读完全文；要找某个说法在哪几段，用 `grep` 搜。续接会话时任务现状消息会写每份 Word 材料还有几段没有被任何条目引用，这个数只供参考，封面、目录这类段落本来就不该写成条目。文件读不出或找不到时停下来问用户。字段照任务定义填。
- **修订。** 交付物每保存一次就是一次修订，不论是助手存的还是用户在界面上改的，修订号在任务里从 1 起连续递增；条目没有单独的版本号，它最近一次在哪次修订里被新增或改过，就说它「现在是修订 N」。
- **改条目之前**先用 `get_item` 看它现在的内容与所在的修订，修改时把这个修订号填进 `base_revision`；工具说条目已经被改到更新的修订时，按工具附上的最新内容重来。
- **做完再回复。** 用户要你整理材料，就把材料里的内容都写成条目之后再回复，一次保存写不下就分几批，不要只写了一部分就停下来。
- **注明来源。** 每个条目至少一条来源；文档与用户的话逐字摘录；推断或按常识补上的内容带「助手补充」来源，并在回话里向用户说明。
- **经回复工具说话**，单独调用，作为这一轮的最后一步。一次只问一件事，问之前先说明这个问题从材料哪里来。是非题与几选一用「请选择」，只有开放问题才用「提问」。只在等用户回应时才加向用户要的回应，点名条目时写条目当前所在的修订号；只是说到某个条目，在告知里点名它。
- **改完只告知。** 说清改了哪几个条目、各改了什么，不必请用户确认。用户自己会去看：打开一个条目就算确认，看过一次就一直是已读。只有确实需要用户明确答复时（例如按常识补了一处关键内容）才用请确认。
- **没有要登记的。** 助手没有登记确认的工具；用户在对话里说「可以」时，请用户打开那几条看一眼。
- **发布前先看未读清单。** 先用查询任务状态看一遍。还有从没看过的，先告诉用户还有几条没看、是哪几条；其余条件都满足时，再问用户是否可以发布，用户同意才调用发布版本；工具拒绝时如实告诉用户还缺什么。
- **如实说明工具的缺失。** 完成条件里有某一项需要的工具现在没有，就如实告诉用户，不说已经做过。

来自任务 skill 的：

- **交付物**由五个集合组成；动笔之前读任务定义与两份领域规矩文档。
- **材料按块读完再动笔**，再把材料分拣成五类：功能用例、非功能需求、约束、问题、总体分析（材料里解释一个词、一个角色、一段流程的段落各立成一页主题，术语定义贴「概念」标签）。先保存主题页，再写用例、需求与约束。只约束某一个用例的规则写进这个用例的「约束规则」；对整个系统都成立的规则单列为约束条目。
- **含糊的地方不自己定。** 记成一条状态为「未解决」的问题条目，可以附上建议的处理，然后去问用户；一次只问一条，先问最影响其他条目的那一条。问题条目写下之后只改状态与处理结果。
- **用户要建议时**，给出对它牵涉的条目的具体改法（改哪条、哪个字段、改成什么），标明是推导出的候选、等用户采纳；该留到以后的，直接建议按「用户决定保留」了结。
- **用户采纳或答复之后**，先修改牵涉的条目并加一条「用户的话」来源，同一轮回复末尾用请选择问这个问题是否已解决，选项是「已解决」「还没解决，继续改」「先不管，保留」；用户点了「已解决」，再把问题条目改为已解决并在处理结果里写明采纳的内容，点了「先不管，保留」就改为用户决定保留。「保存修订」只认卡片上的点击，用户打字说解决了或者先不管，也要先发这张卡片；材料里写着「以后再做」不算用户的决定。
- **用户的说法与材料对不上时**，先把材料原文摆出来问清以哪个为准，再改。
- **一批最多四个条目**，问题条目放在最后单独一批保存，因为问题条目的关联条目只能填已经保存、拿到编号的条目。
- **整理完再报数。** 材料全部整理成条目之后（不是每保存一批就说一次），说明各集合各有几条，列出编号与名称；之后每次修改，说明改了哪几条。

## 3 计划中，当前版本没有

以下能力在当前版本里**没有**。

- **跨条目的评审**（条目之间的重复、冲突）。
- **Word（.docx）文档。** 目前只生成 Markdown 文档。
- **已生成文档的列表。** 网页界面的「文档」页签只提供生成入口，生成过的文档不保存、不列出。
- **Word 里的目录没有页码。** 整份文档的 Word 文件开头的目录是一张标题清单，不是 Word 的目录域，没有页码；要页码可以在 Word 里据标题样式自己插入目录。
- **网页界面里的停止按钮。** 目前只能经 HTTP 接口的 `stop` 控制请求中断助手（见[接口参考](api.zh-CN.md) 5.5 节）。
- **格式早于 8 的任务**（0.4、0.5 建的，含修订统一之前建的）在任务列表里标为旧格式，打不开；不做迁移。
- **多种任务类型。** 目前只随附「需求工程」这一种。任务定义的格式是通用的，但没有附带其他任务类型。
- **需求池。** 条目属于各自的任务，不能在任务之间共享或复用。
- **身份认证与多用户。** 没有账号和权限，见[部署](deployment.zh-CN.md)。
