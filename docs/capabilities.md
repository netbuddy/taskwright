# Capabilities

This page lists what the current version (0.1.0-alpha) of Taskwright can do. It has three parts:

1. [General capabilities](#1-general-capabilities), which every task type gets;
2. [The software requirements specification task type](#2-task-type-software-requirements-specification), the one task type that ships today;
3. [Planned, not in the current version](#3-planned-not-in-the-current-version).

Only parts 1 and 2 describe things the code does now. How to install and run it is in [deployment.md](deployment.md); how to use it is in the [user guide](user-guide.md).

## 1 General capabilities

### 1.1 Roles

- The **user** is a person in the web interface or a terminal (or the simulated user in `sim/`).
- The **assistant** (technically the executor) is the agent running inside pi. It reads the materials, writes items, asks questions and replies.
- The **reviewer** checks items against numbered review rules (section 1.9). It is a model call without tools, made by the system; it cannot change items.

Whether the user accepts an item is not judged by a model: opening an item's details counts as having read it, and reading it counts as confirming it (section 1.4).

### 1.2 Tasks, sessions and the task directory

- A **task** has one task type, one name, an optional domain tag, its materials and one deliverable. Each task lives in its own **task directory**: the task type's starting files, the uploaded materials under `inputs/`, and the database `task.sqlite`.
- A task can have several **sessions** (conversations). All sessions of a task work on the same deliverable. Only one session is active at a time: while the assistant works in one session, messages to another return `session_busy`.
- **One writer at a time.** At any moment either the user or the assistant changes the deliverable, never both. One message from the user starts one run of the assistant; while it runs, further messages and direct operations are refused with `session_busy` (there is no queue), and the web interface greys out sending and every write button. While the user has an unsaved edit open in the web interface, sending and the buttons on cards are greyed out instead. If two browser tabs edit the same item, the second save is refused with `stale_revision`; nothing is merged.
- The conversation is kept in pi's session files, not in the task database. When a session opens, the assistant receives a status message that lists the materials and how many items each collection has.
- Materials are plain-text `.md` or `.txt` files or Word `.docx` files of up to 5 MB each; more can be uploaded at any time. For a `.docx` a Markdown text is generated beside it, with the headings, automatic numbering, lists and tables of the Word file, its pictures as links, text-box text as quotes, and a number in front of every paragraph; the assistant reads that text, looks at the pictures when the model can read images, and cites the Word file by paragraph number.

### 1.3 The assistant's tools

The startup profile (`server/taskwright_server/profiles/dev.json`) allows exactly eight tools. pi's other built-in tools (such as `bash`, `edit` and `write`) are not loaded, so the assistant cannot run commands or change files; it can change the deliverable only through `save_revision`.

| Tool | What it does | What it checks, and when it refuses |
|---|---|---|
| `read` (pi built-in) | Reads a file, for example a material, the task definition or a domain rules document. | Read-only. |
| `ls` (pi built-in) | Lists a directory, for example `inputs/`. | Read-only. |
| `save_revision` | Saves a batch of item operations (add, update, delete) as one revision of the deliverable. Item ids are generated by the tool. | Checks that the collection and fields exist, that values have the declared types, that required fields are filled and not cleared, that every new item has at least one source with kind, locator and excerpt, that each source points at existing fields, and that referenced items exist; an item added earlier in the same batch counts as existing (its id follows the collection's serial numbers in the order of the operations), while a reference to an item added later in the batch is refused. An update or delete must give `base_revision`, the item's current revision; if the item has moved on, the batch is refused and the reply says who changed it to which revision, with its current content. For a source of kind "user's words" the tool finds the quoted text verbatim in the user's messages of this session and fills in the locator itself; if the text is not found, it refuses. For a source of kind "document excerpt" the excerpt must be one continuous passage of the material file its locator names. An excerpt may hold several passages separated by blank lines: the tool splits it at the blank lines, looks up each passage on its own, and, if all are found, stores them as that many sources in the same place, with the same kind, locator and supported fields. An excerpt with a passage that is not found, that joins separate sentences without a blank line, changes a character, or points at a file that cannot be read is refused, and the refusal says which passage was not found. Once an issue item is written (an item of a collection whose status field offers "kept by the user's decision", such as the issues collection), the assistant may change only its status and outcome; other fields are refused, while adding new issue items is not limited. An update that changes nothing is refused. It refuses when the task is completed or abandoned. If any operation is wrong, **nothing** in the batch is written, and every problem is listed. A call that arrives again with the same tool-call id (a model retry, or pi sending the call again) writes nothing: the tool returns the first result followed by 这次调用之前已经保存过，没有重复写入 ("this call was saved before; nothing was written again"), even when the task has been completed since; the database holds at most one revision per tool-call id. A call without a tool-call id (pi passes an empty id when the model service gives none) cannot be recognised this way and is saved each time. It never judges content. |
| `reply` | Sends what the assistant says to the user. A reply has informs (plain facts; an inform may name the items it mentions, shown as item links) and a written text; only when the assistant waits for a specific response from the user does it add one act (ask, confirm, suggest, choose or propose) whose text is what the user should respond to, not the answer. | Must be called alone, as the last step of a turn. Checks the form: required parts present, one of the five act kinds, at least two distinct options for `choose`, a value and at least one basis for `suggest`, valid `preview` entries for `propose`. Each basis of a suggestion is checked like a `save_revision` source, with the same wording when it is refused: a document excerpt must appear verbatim in the material (a Word file with a paragraph number, as for sources), the user's words must appear verbatim in the session (the tool fills in the locator), a domain note excerpt must appear in the note's current text; a basis of kind "added by the agent" is not checked. A basis that cannot be found refuses the whole reply. Ask, confirm, suggest and propose must name the items they concern with their **current** revision numbers (checked against the database), unless they are marked `scope: "general"`. Items named in informs are checked the same way. An act whose text only repeats one of the informs (the same words, or contained in it, ignoring spaces and punctuation) is refused. After three rejections in a row it asks for plain text only; after the fifth it lets a plain-text reply through, marked as degraded. It writes nothing to the database. |
| `get_item` | Shows one item: every field, every source, its current revision, the revisions in which it changed, review and confirmation state; on request, the item as it was at an earlier revision. | Read-only; refuses an unknown item or a revision the task does not have yet. |
| `get_task_status` | Shows each collection's items, each completion condition and whether it holds (with the items that fail it), issue items, the **unread list** (items the user has never read, with their titles), and the latest revision. | Read-only; the same checks as the deliverable board. |
| `request_review` | Asks the reviewer to review items at their current revisions; without `items` it reviews every item waiting for review. Used only when the user asks for a review in the conversation; reviews are normally started from the interface (section 1.9). | Refuses an item that does not exist, is deleted, is not at the given revision, or is in a collection that is not reviewed, and refuses while another review is running. The result lists each item as compliant or not compliant (N problems, M pieces of advice), with every finding and its rule number. |
| `complete_task` | Marks the task as completed. | Runs the same condition checks as `get_task_status`; if any condition fails it refuses. Unread items are named in one sentence the assistant can pass on as is, 还有 N 条你从没看过：…… ("there are still N items you have never read: …"); other missing conditions are listed after it. After completion every write tool refuses and the task is read-only. |

**Refusals are recorded.** When `save_revision`, `reply`, `complete_task` or `request_review` refuses a call because of its input, or because the assistant has not yet written its understanding of the user's message, the tool writes one row to the `tool_rejection` table of the task database: the tool, the call id, the unit of work, the kind of reason (input, or a missing step), the refusal's two layers (the fact, for people, and the guidance, for the assistant) and the first 2,000 characters of the refused input. Refusals that are not about the input, such as no model being available, a review batch still running or a database error, are not recorded. The observatory shows the row under the refused call.

### 1.4 What the user can do directly

These operations in the web interface do not go through the model. They run inside pi through the same write functions as the tools, so the same checks apply. Each operation that changes items creates exactly one revision; marking as read does not.

| Operation | Effect | Refused when |
|---|---|---|
| Edit fields | Saves the new values of one item's fields as a new revision. The changed fields get a source of kind "direct user edit"; unchanged fields keep their sources. The item is also recorded as confirmed by you at that new revision. | The item changed since you opened it (for example another browser tab saved first; you are told which revision it is at now and reopen it), the item is deleted, or the values fail the same checks as `save_revision`. |
| Delete an item | Marks one or more items as deleted in a new revision. | The item changed since you opened it, or it is already deleted. |
| Mark as read | Records that you have read the items as they are at their current revisions; reading counts as confirming. The interface does this by itself when you open an item's details, and when you click 这几条都看过了 ("I've read these") on a confirm card, which also tells the assistant. You can also tick items in the list and mark them as read together. Marking an item that is already marked at that revision writes nothing. | A revision is no longer the item's current one. |
| Withdraw a confirmation | Records that you no longer accept that revision of the items. The web interface no longer offers this button; only the interface endpoint remains. Read is per item, so a withdrawn item still counts as read. | A revision is no longer the item's current one. |
| Undo a revision | Saves a new revision that puts every item the chosen revision touched back the way it was (a deleted item is restored, an added item is deleted). Nothing is erased. The web interface works out from the revision log which revisions cannot be undone, greys out their undo button and says why. | Any of those items changed again, or was deleted, after that revision. |
| Keep pending | Sets the status of an issue item to "kept by the user's decision" in a new revision, and records the issue as confirmed by you at that revision. | The item's collection has no status field with that value. |
| Keep a wording | Keeps the current wording of an item that failed review, with an optional reason; it counts as passed by your decision; if the item changes, it must be reviewed again. | The item has no failed review at its current revision under the current rules, or it is already kept. |
| Withdraw a kept wording | Withdraws the keep; the item counts as failed again. | Nothing is kept at the item's current revision. |
| Switch review rules | Switches an optional rule of a collection off or on, or makes it required; creates no revision. | The rule is required, the collection has no review rules, or nothing changes. |
| Request a review | Starts a review of every item waiting for review (评审 N 条待评审的条目, "review N items waiting for review"), of one item (评审这条, "review this item") or of the items listed in the completion panel (评审这 N 条). The request returns at once and the review runs in the background; see section 1.9. It creates no revision. | Another review is still running, there is nothing to review, a named item is not at its current revision, or a named item was already reviewed with the same content and rules (use 仍要重评, "review again"). |

**Reading counts as confirming.** There is no confirm button. Opening an item's details records a confirmation mark with the basis "read" on the item's current revision; the item's status changes from 未读 ("unread") to 已读 · 修订 N ("read · revision N", where N is the last revision you read). Only opening the details counts; seeing the item in the list does not, and nothing measures how long you look. Read is per item and one-way: once read, an item stays read even if the assistant changes it later; what it changed since you looked is pointed out by the "just changed" tag and the amber field frames in the details, and does not block completion. Opening the item again records another read mark at the revision you see, so a generated document can say truthfully which revision you last read. You do not need to say "OK" in the conversation: the assistant does not record confirmations from what you say.

**Your own edits count as confirmed.** Content you wrote yourself is content you accept: when editing fields or keeping an issue pending succeeds, the item is recorded as confirmed at the new revision in the same transaction as the revision, with the basis "interface edit". Deleting an item and undoing a revision do not confirm anything. The bottom right of an item's detail only shows its status; there is no button to withdraw a read.

All operations are refused once the task is completed or abandoned, and while the assistant is working (including requesting a review), with one exception: opening an item's details still marks it as read while the assistant works, because that does not change the deliverable. After each operation the assistant sees a note in the conversation that says exactly what changed, which revision it produced and the new field values, for example 用户改了 UC-002 的「基本流程」，产生修订 5，UC-002 现在是修订 5。 ("the user changed UC-002's basic flow, producing revision 5; UC-002 is now at revision 5").

Buttons on the assistant's cards (choose an option, "fill in from common sense", "another one", and so on) are sent to the assistant as your message, together with a note of which card and option you clicked.

**Seeing what changed.** The web interface shows changes in three places. The side panel's Revisions tab is a log of every revision, newest first: who made it, what triggered it (which of your messages the assistant was answering, or which direct operation you made), and each item it touched with the fields that changed; from a card you can show an item's changes, undo the revision, or generate a document from it. Each reply of the assistant that saved revisions carries a small tag naming them, which opens the Revisions tab. In an item's detail, the fields the assistant changed since the revision you last confirmed (or since the item was added, if you never confirmed it) are framed, and the differences are drawn against that revision; fields you changed yourself are not framed. Because opening the detail marks the item as read, the frames are fixed at the moment you open it: you see them for as long as the detail stays open, and they are gone the next time you open the item. Items changed by the assistant's most recent run are marked "just changed" in the list, and items you have never opened (unread) are shown in bold. Hovering over a greyed-out write button in the items area says why it is greyed out (the assistant is working, a save is in progress, you are looking at an old revision, or the task has ended). An issue item cannot be edited directly in the web interface once it is written; it can only be kept pending or deleted.

**Questions follow the items they concern.** The web interface derives, from each issue item's item-reference field (related items), which issues concern which item; nothing extra is stored. List rows show **问题 N**, the number of unresolved issues concerning the item. The item's details list those issues first; an unresolved one can be answered from there, which sends "回答 <issue id>：<answer>" to the assistant as your message, or kept pending with the usual direct operation. Following an issue's link to an item keeps a way back to that issue in the Issues tab.

### 1.5 Sources

The content of an item at each revision carries at least one source, and each source can point at the whole item, one field, or one entry of a list field. There are five kinds:

| Kind | Written by | Locator | Excerpt |
|---|---|---|---|
| Document excerpt | assistant | path of the material; for a Word file the path plus the paragraph number, such as `inputs/a.docx#p37` | a verbatim quote from the material (for a Word file, from that paragraph, or starting in it and running into at most five following paragraphs) |
| User's words | assistant; locator filled by the tool | the session and message where the user said it | a verbatim quote, checked against the conversation |
| Added by the assistant (stored as 执行者补充) | assistant | 执行者补充 | why it was added or inferred |
| Domain note (领域说明) | assistant | the id of a domain note of the same task, such as `DN-002` | a verbatim quote from that note's title or content |
| Direct user edit | the system only | the id of the interface operation | the start of the new value |

A domain note source lets an item rest on an explanation already recorded in the task's domain notes collection (section 2.1). The tool checks that the locator is an item of that collection that was saved before this batch (unlike item-reference fields, a note added earlier in the same batch cannot be cited yet, because its text is not saved) and is not deleted, also not in the same batch, and that the excerpt appears verbatim, punctuation included, in the note's title or content at its current revision; otherwise the batch is refused. A generated document writes it as 领域说明 DN-002（「excerpt」）.

A revision produced by a direct edit is also recorded as confirmed by the user (section 1.4), so content backed by a "direct user edit" source starts out read and never becomes unread again.

In a generated document these two locators are written so that a reader can follow them: a user's-words source as 会话「<session name>」里用户的第 N 句话 ("the user's N-th message in session <name>"), and a direct user edit as 用户在界面上的第 N 次修改（<time>） ("the user's N-th edit in the interface", numbered in the order the edits were saved). When the session record or the operation cannot be found, the document says 对话里用户说的话 or 用户在界面上的修改 instead of printing the internal id.

### 1.6 Completion conditions

The task definition lists, for each collection, which conditions must hold. The code knows four condition names: at least one item; no item with status "unresolved"; every item passed review; every item confirmed by the user. Each is a factual check of the database, never a judgement of content: "passed review" means there is a compliant review of the item at its current revision (when it fails, the explanation lists the items not reviewed yet and the items that failed separately), and "confirmed" means the item has an acceptance mark of any basis (read, interface edit, or an older basis) on any of its revisions, that is, the user has read it and it is not unread. Reviews are marks on "item plus revision" and do not move when the item changes later, so a changed item needs a new review; confirmation marks are stored on "item plus revision" too, but the gate only asks whether the item was ever read, so a change does not make it unread again. When a generated document shows an item at a revision newer than the one the user last read, its confirmation reads 用户最后看过修订 N，之后由助手改为修订 M ("the user last read revision N; the assistant has since changed it to revision M"). An empty collection counts as satisfied for the "every item …" conditions but is not reported as met. The same checks drive the deliverable board, `get_task_status` and `complete_task`.

Besides the conditions there is one hint, which never blocks completion: domain notes that are not linked to any item (有 N 条领域说明还没有和任何条目关联). A note counts as linked when a live item cites it as a source at its current revision, when a live item lists it in an item-reference field, or when the note's own item-reference field points at a live item. `get_task_status` and the completion panel show the hint.

### 1.7 Documents

Generating a document renders the whole deliverable as of one revision, the latest by default, through the task type's Markdown template; you can limit it to some of the items that were in the deliverable at that revision. No model is involved. Each item is shown as it was at that revision. The template is the copy in the task directory that the task definition's 文档模板 (document template) field names; it was copied from `task-types/<task type>/` when the task was created, so changing the template in the repository affects only tasks created afterwards. Within each collection, items appear in the order of their ids. The document says which revision it was generated from. Items that were not reviewed or not confirmed are included and marked as such: each marked item carries the revision its content comes from, its review state (not reviewed, passed review or failed review, from the latest review at that revision) and its confirmation state at that revision: not confirmed, or confirmed with its basis written out, 已读 (read), 用户修改 (user edit) or 明确确认 (explicit confirmation, for older confirmations). In the bundled template, issue items are listed with their kind and status but without these marks. The bundled template opens with 术语与定义 (terms and definitions: domain notes whose category is 术语) and 总体描述 (general description: the other domain notes, grouped by category) before the functional requirements; domain notes carry their revision and confirmation state. A template can select items by field value and group them by a field: `{{#每个 领域说明 类别=术语}}` keeps the items whose field equals the value, `类别!=术语` those whose field differs (a list field matches when it contains the value; several conditions separated by spaces must all hold), the same conditions work in `{{#没有 …}}`, and `{{#按 类别 归组 领域说明 类别!=术语}} … {{/按}}` renders its body once per value of the field, with `{{组名}}` for the value (（未填） when empty) and `{{#组内每个}} … {{/组内每个}}` for the items of that group; groups follow the id of their first item. You can preview or download the result, also after the task is completed. A revision number beyond the latest, or an item that was not in the deliverable at that revision, is refused.

### 1.8 A history that cannot be rewritten

- Every change is a new revision; nothing is overwritten or erased. An item's content at any revision can still be read, a deleted item keeps its earlier content, and undo adds a new revision instead of removing one.
- Every write (a tool call or a direct operation) records exactly one event, in the same database transaction as the change itself. Either both are written or neither is. The one exception is editing fields or keeping an issue pending, which records two events in that same transaction: the revision, and the confirmation that goes with it. Marking as read records an `ITEM_VIEWED` event, or none at all when every item was already read.
- Every event carries the session, the tool call and who made the change (assistant or user).

### 1.9 Review

A reviewer checks items against the task type's review rules. Each reviewed collection names a rule file in its task definition (`docs/review-rules/use-case.json` and `ears.json` in the bundled task type); every rule has a number (for example UC-R7), a level, the rule text, a counter-example and an example. **Required** rules decide the verdict; **optional** rules only give advice. Each task can switch optional rules off or make them required, in the rule area of the Review tab (the task definition keys `关闭` and `升为必选`); required rules cannot be switched off. The issues collection is not reviewed.

- **Who starts a review.** You do, from the interface. The assistant does not review on its own; it calls `request_review` only when you ask for a review in the conversation.
- **What the reviewer sees.** The rule list, the field declarations, the item and its sources, and the full materials when they are at most 20,000 characters in total; otherwise only the paragraphs its document sources quote, with a note that this is not the full text. Rules such as UC-R10 and UC-R11 ("not in the material", "left open in the material") are judged against that material. The reviewer call asks for temperature 0; when the model service rejects the parameter (the default model does), the call is repeated without it and the model call record says so.
- **How it runs.** Each item is reviewed by one model call without tools and without the conversation, at most four at a time and at most 60 seconds per item, with one retry. The reviewer must cite a rule number from the list for every finding; output that cites an unknown number, or a problem without a suggested fix, is rejected and retried. A review that does not finish (timeout, failed call, two rejected outputs, or the item changed meanwhile) records no verdict.
- **Verdict.** The code, not the model, computes it: any finding under a required rule makes the item **not compliant**; findings under optional rules are advice. Suggestions name what to change and in which direction; they never contain rewritten text.
- **In the interface.** The items area shows how many items wait for review and how many failed; while a review runs, a message at the top right of the page shows its progress (评审中 3/12) and turns into the result when it ends. In an item's details, problems are shown in red and advice in amber next to their fields; clicking the rule number (违反 UC-R9) shows the rule text, and 让助手照这条改 ("let the assistant fix this") prefills a request to the assistant. The item's status badge reads 评审不通过 N 处 (failed, N problems), 待评审 (waiting for review) or 评审不通过 N 处 · 已保留 (failed, kept by you), unless the item is unread, which is shown first after a failed review; a passed item shows no review badge, and hovering over the badge shows the review result, including the number of pieces of advice.
- **When the item or the rules change.** A review is a mark on "item plus revision", and it records the rule fingerprint (a hash of the rule file and the task's switches). After a new revision, or after the rules change, the item waits for review again; existing reviews stay as they are. Reviewing an item whose content and rules have not changed since its last review needs 仍要重评 ("review again"), which asks for confirmation; the new review is the one that counts.
- **Review tab.** The side panel lists every review as 第 N 次评审 ("review N") with its time, who started it (you, or the assistant because you asked in the conversation), how many items, how many passed and failed, and the counts of problems and advice. Opened, it shows each item's findings with their status: 未处理 (open), 已在修订 N 改 (fixed in revision N: the item passed review in a later revision) or 已保留 (kept, with your reason). 只看未处理 shows only open findings. The tab's badge is the number of open problems.
- **Keeping a wording.** Next to an item that failed review (in the Review tab or beside a finding in the item's details) you can keep its current wording, with an optional reason. The item then it counts as passed by your decision; if the item changes, it must be reviewed again. In the details, the item's badge reads 评审不通过 N 处 · 已保留 ("failed, N problems · kept"); each finding shows the finding on its first line and, on a second line, its status (未处理 open, 已在修订 N 改 fixed in revision N, 已保留 · 理由：… kept, with your reason) followed by the actions 让助手照这条改, 保留这种写法 and 撤销保留 ("withdraw"). The red banner at the top appears only while problems are open. Generated documents mark it 评审不通过，用户保留（理由：…）. Only you can do this.
- **What the assistant sees.** When a review ends, the conversation gets one sentence with the counts and a link to the Review tab; the assistant reads the findings through `get_task_status`, which lists the open findings with their rule numbers and the review they came from, and the kept items separately.

## 2 Task type: software requirements specification

The bundled task type `srs-authoring` (in `task-types/srs-authoring/`) turns requirements material into a software requirements specification. Its interface texts and rules are in Chinese.

### 2.1 Collections and fields

| Collection | Id prefix | Fields (required in bold) |
|---|---|---|
| Use cases | UC | **name**, **purpose**, **actors** (list), preconditions (list), postconditions (list), constraint rules (list), **basic flow** (list), extension flows (list) |
| Non-functional requirements | NFR | **category**, **sentence pattern** (one of the six EARS patterns), **requirement statement** |
| Constraints | CON | **category**, **sentence pattern**, **requirement statement** |
| Issues (问题) | TBD | **issue**, **kind** (to be clarified, out of scope, later iteration), suggested handling, **status** (unresolved, resolved, kept by the user's decision), outcome, related items (item references) |
| Domain notes (领域说明) | DN | **title**, **content**, **category** (free text such as term, role, current process, background, assumption, example), related items (item references) |

Domain notes hold explanations that are not requirements themselves: what a word means, who a role is, how the work is done today, why the system is wanted. Rules still go to constraints, scenarios and flows to use cases, and open decisions to issues; when a sentence is both an explanation and a rule, the domain note keeps only the explanation and the rule goes where rules go (the constraint rules of the one use case it constrains, or the constraints collection), the two linked both ways.

A collection in a task definition may carry an optional 界面 (display) entry that only changes how it is shown: 右侧栏页签 (true gives it its own side panel tab), 分组字段 (the text or enum field to group by, also shown as a tag on each row), 靠前的组 (groups listed first, in this order; the others follow the id of their first item) and 说明 (one plain sentence shown under its tab). The bundled domain notes collection uses `{"右侧栏页签": true, "分组字段": "类别", "靠前的组": ["术语"], "说明": "材料里或你说明过的背景、术语、角色，供条目引用。"}`. When you explain something in the conversation, the assistant records it as a domain note and says where it went, for example 我把「借还台管理员」记到领域说明了（DN-002）.

Completion conditions: use cases need at least one item, and every use case, non-functional requirement and constraint must pass review and be confirmed by the user (that is, none of them may be unread); no issue item may remain unresolved; every domain note must be confirmed by the user. Domain notes are not reviewed.

### 2.2 Domain rules

Two rule documents in `docs/domain-knowledge/` describe how to write items. The assistant reads them before writing.

- **Use cases** (`use-case-writing.md`): one use case is one actor's goal; the nine parts of a use case (name, id, purpose, actors, preconditions, postconditions, constraint rules, basic flow, extension flows) and how to write each; what is not allowed (interface details, functions not in the material, deciding unclear points, examples inside rules, unverifiable words).
- **Non-functional requirements and constraints** (`ears-writing.md`): the difference between the two; the six EARS (Easy Approach to Requirements Syntax) sentence patterns: ubiquitous, event-driven, state-driven, optional feature, unwanted behaviour, and complex; and the rules each statement must meet (one thing per statement, a clear subject, verifiable, no vague words, no examples, no implementation unless it is itself a constraint, numbers kept exactly as in the material).

The numbered rule lists in both documents are generated from the rule files in `docs/review-rules/` (`node scripts/render-rules.mjs`), so the rules the assistant reads and the rules the reviewer checks are the same text.

### 2.3 How the assistant works

The assistant loads two skills, and its system prompt tells it to read both before starting, the platform skill first. The **platform skill** (`agent/prompts/skills/taskwright-executor/SKILL.md` in the repository, shared by every task type and not copied into task directories) describes how to work in Taskwright. The **task skill** (`.pi/skills/srs-authoring/SKILL.md` in the task directory) describes only what is specific to this task type.

From the platform skill:

- **Know the system messages.** The status message at the start of a session (and the list of changes when an old session is resumed), the notes about operations in the interface, and tool refusals are written by the system, not said by the user. After a note about an interface operation, work from the revision number it gives ("X-001 is now at revision N"). Edits, deletions, keep-pending and undo each create a revision; marking as read does not. Opening an item in the interface is recorded without a note; to know which items the user has not read, look at the unread list of `get_task_status`.
- **Read before writing.** List the material directory and read every file in full before writing anything. If a file cannot be read or cannot be found, stop and ask. Fill fields as the task definition declares them.
- **Revisions.** Every save of the deliverable, by the assistant or by the user, is one revision, numbered from 1 within the task; an item has no version number of its own and "is at revision N" when N is the last revision that added or changed it.
- **Before changing an item**, look at its current content and revision with `get_item` and give that revision as `base_revision`; when the tool says the item has moved on, start again from the latest content it returns.
- **Finish the job before replying.** Asked to turn material into items, write all of it, in several saves if needed, before replying; do not stop halfway to ask for confirmation of what is written so far.
- **Mark sources.** Every item has at least one source; quote documents and the user verbatim; anything inferred or filled in from common sense gets an "added by the assistant" source and is pointed out to the user.
- **Reply through the reply tool**, alone and as the last step of a turn. Ask one thing at a time and explain first where the question comes from. Use "choose" for yes/no and multiple-choice questions and "ask" only for open questions. Name the items an act concerns with their current revisions.
- **After any change, only tell.** Say which items changed and how; do not ask the user to confirm them. The user reads them: opening an item counts as confirming it, and an item stays read once opened. Use the "confirm" act only when a clear answer from the user is really needed, for example after filling in a key detail from common sense.
- **There is nothing to record.** The assistant has no tool for recording confirmations; when the user says "that's fine" in the conversation, ask them to open the items instead.
- **Check the unread list before asking to complete.** Look at `get_task_status` first. If some items have never been read, tell the user how many and which ones; when everything else holds, ask whether to complete now; complete only after the user agrees, and report honestly if the tool refuses.
- **Be honest about tools.** If a completion condition needs a tool that is not available, say so instead of claiming it was done.

From the task skill:

- **The deliverable** consists of five collections; read the task definition and the two domain rule documents before writing.
- **Read all material first**, then sort it into use cases, non-functional requirements, constraints, issue items and domain notes (term definitions in the material become domain notes of category 术语). A rule that constrains one use case goes into that use case's constraint rules; a rule that holds for the whole system is a constraint item.
- **Do not decide what is unclear.** Record it as an issue item with status "unresolved", optionally with a suggested handling, and ask, one issue item at a time, the one that affects the most items first.
- **When the user asks for a suggestion**, give concrete changes to the items the issue concerns (which item, which field, what to write), marked as a derived candidate waiting for the user to accept; if the matter belongs to a later stage, suggest settling it as "kept by the user's decision". Once written, an issue item changes only in its status and outcome.
- **After the user accepts or answers**, first update the items concerned with a "user's words" source, then end the same reply with a confirm act asking whether the issue is settled; when the user confirms, mark the issue resolved and write what was accepted in its outcome. Only the user in the conversation can decide to leave an issue for later; a remark in the material that something is for later is not the user's decision.
- **When the user contradicts the material**, quote the material and ask which one holds before changing anything.
- **Save at most four items at a time**, and save issue items last, in a batch of their own, so that their related items already have ids.
- **Report once the material is done**: after all material has been turned into items (not after every batch), say how many items each collection has, with their ids and names; after later changes, say which items changed.

## 3 Planned, not in the current version

The following are **not** available in the current version.

- **Reviewing several items together** (duplicates, conflicts between items).
- **Word (.docx) documents.** Documents are generated as Markdown only.
- **A list of generated documents.** The Document tab of the web interface only offers to generate a document; generated documents are not stored or listed.
- **A stop button in the web interface.** The assistant can be interrupted only through the `stop` control request of the HTTP API ([api.md](api.md), section 5.5).
- **Tasks created before revisions replaced item versions** are listed as unsupported and cannot be opened; there is no migration.
- **More task types.** Only the software requirements specification task type ships. The task definition format is general, but no other task type is included.
- **A requirements pool** shared across tasks. Each task keeps its own items; items cannot be reused between tasks.
- **Authentication and multiple users.** There are no accounts or permissions; see [deployment.md](deployment.md).
