# Capabilities

This page lists what the current version (0.1.0-alpha) of Taskwright can do. It has three parts:

1. [General capabilities](#1-general-capabilities), which every task type gets;
2. [The software requirements specification task type](#2-task-type-software-requirements-specification), the one task type that ships today;
3. [Planned, not in the current version](#3-planned-not-in-the-current-version).

Only parts 1 and 2 describe things the code does now. How to install and run it is in [deployment.md](deployment.md); how to use it is in the [user guide](user-guide.md).

## 1 General capabilities

### 1.1 Roles

- The **user** is a person in the web interface or a terminal (or the simulated user in `sim/`).
- The **executor** is the agent running inside pi. It reads the materials, writes items, asks questions and replies.
- The **confirmation reader** is a separate model call made inside a tool, without tools of its own and with a clean context. It decides whether the user's words accept an item. It uses the same model as the executor.

### 1.2 Tasks, sessions and the task directory

- A **task** has one task type, one name, an optional domain tag, its materials and one deliverable. Each task lives in its own **task directory**: the task type's starting files, the uploaded materials under `inputs/`, and the database `task.sqlite`.
- A task can have several **sessions** (conversations). All sessions of a task work on the same deliverable. Only one session is active at a time: while the executor works in one session, messages to another return `session_busy`.
- The conversation is kept in pi's session files, not in the task database. When a session opens, the executor receives a status message that lists the materials and how many items each collection has.
- Materials are plain-text `.md` or `.txt` files of up to 5 MB each; more can be uploaded at any time.

### 1.3 The executor's tools

The startup profile (`server/taskwright_server/profiles/dev.json`) allows exactly eight tools. pi's other built-in tools (such as `bash`, `edit` and `write`) are not loaded, so the executor cannot run commands or change files; it can change the deliverable only through `save_revision`.

| Tool | What it does | What it checks, and when it refuses |
|---|---|---|
| `read` (pi built-in) | Reads a file, for example a material, the task definition or a domain rules document. | Read-only. |
| `ls` (pi built-in) | Lists a directory, for example `inputs/`. | Read-only. |
| `save_revision` | Saves a batch of item operations (add, update, delete) as one revision of the deliverable. Item ids are generated by the tool. | Checks that the collection and fields exist, that values have the declared types, that required fields are filled and not cleared, that every new item has at least one source with kind, locator and excerpt, that each source points at existing fields, and that referenced items exist. An update or delete must give `base_version`; if the item has moved on, the batch is refused and the reply says who changed it to which version. For a source of kind "user's words" the tool finds the quoted text verbatim in the user's messages of this session and fills in the locator itself; if the text is not found, it refuses. An update that changes nothing is refused. It refuses when the task is completed or abandoned. If any operation is wrong, **nothing** in the batch is written, and every problem is listed. It never judges content. |
| `reply` | Sends what the executor says to the user. A reply has zero or more informs (plain facts), at most one final act (ask, confirm, suggest, choose or propose) and a written text. | Must be called alone, as the last step of a turn. Checks the form: required parts present, one of the five act kinds, at least two distinct options for `choose`, a value and at least one basis for `suggest`, valid `preview` entries for `propose`. Ask, confirm, suggest and propose must name the items they concern with their **current** version numbers (checked against the database), unless they are marked `scope: "general"`. After three rejections in a row it asks for plain text only; after the fifth it lets a plain-text reply through, marked as degraded. It writes nothing to the database. |
| `get_item` | Shows one item: every field, every source, version number, review and confirmation state; any earlier version on request. | Read-only; refuses an unknown item or version. |
| `get_task_status` | Shows each collection's items, each completion condition and whether it holds (with the items that fail it), open issues, and the latest revision. | Read-only; the same checks as the deliverable board. |
| `record_confirmation` | Records that the user accepted the current versions of some items in the conversation. | Refuses if an item does not exist, the version is not current, the user has said nothing since that version, or the task is closed. It hands the user's words since that version to the confirmation reader; only items the reader judges as accepted, with a verbatim quote as evidence, are recorded. If the reader's output is invalid twice, or the item changed while it was being read, nothing is recorded. Every call of the reader is kept in the database (prompt, raw output, model, duration, usage). |
| `complete_task` | Marks the task as completed. | Runs the same condition checks as `get_task_status`; if any condition fails it refuses and lists what is missing. After completion every write tool refuses and the task is read-only. |

### 1.4 What the user can do directly

These operations in the web interface do not go through the model. They run inside pi through the same write functions as the tools, so the same checks apply.

| Operation | Effect | Refused when |
|---|---|---|
| Edit fields | Saves the new values of one item's fields as a new version. The changed fields get a source of kind "direct user edit"; unchanged fields keep their sources. | The item changed since you opened it (you get the latest version to redo the change against), the item is deleted, or the values fail the same checks as `save_revision`. |
| Delete an item | Marks one or more items as deleted in a new revision. | The item changed since you opened it, or it is already deleted. |
| Confirm | Records your acceptance of the shown versions. It can also tell the executor, which then continues. | A version is no longer current. |
| Withdraw a confirmation | Records that you no longer accept those versions. | A version is no longer current. |
| Undo a revision | Saves a new revision that puts every item the chosen revision touched back the way it was (a deleted item is restored, an added item is deleted). Nothing is erased. | Any of those items changed again after that revision. |
| Keep pending | Sets the status of an open issue to "kept by the user's decision". | The item's collection has no status field with that value. |

All operations are refused once the task is completed or abandoned. After each operation the executor sees a note in the conversation that says exactly what changed, with the new field values.

Buttons on the executor's cards (choose an option, "fill in from common sense", "another one", and so on) are sent to the executor as your message, together with a note of which card and option you clicked.

### 1.5 Sources

Every item version carries at least one source, and each source can point at the whole item, one field, or one entry of a list field. There are four kinds:

| Kind | Written by | Locator | Excerpt |
|---|---|---|---|
| Document excerpt | executor | path of the material | a verbatim quote from the material |
| User's words | executor; locator filled by the tool | the session and message where the user said it | a verbatim quote, checked against the conversation |
| Added by the executor | executor | "added by the executor" | why it was added or inferred |
| Direct user edit | the system only | the id of the interface operation | the start of the new value |

### 1.6 Completion conditions

The task definition lists, for each collection, which conditions must hold. The code knows four condition names: at least one item; no item with status "unresolved"; every item passed review; every item confirmed by the user. Each is a factual check of the database, never a judgement of content: "passed review" means there is a passing review of the item's current version, and "confirmed" means there is an acceptance of the current version. Editing an item therefore makes the earlier confirmation stale. An empty collection counts as satisfied for the "every item …" conditions but is not reported as met. The same checks drive the deliverable board, `get_task_status` and `complete_task`.

### 1.7 Documents

Generating a document renders the item versions you select through the task type's Markdown template. No model is involved. Versions that were not reviewed or not confirmed can be included and are marked as such. You can preview or download the result.

### 1.8 A history that cannot be rewritten

- Every change is a new version; nothing is overwritten or erased. A deleted item keeps its versions, and undo adds a new revision instead of removing one.
- Every write (a tool call or a direct operation) records exactly one event, in the same database transaction as the change itself. Either both are written or neither is.
- Every event carries the session, the tool call and who made the change (executor or user).

## 2 Task type: software requirements specification

The bundled task type `srs-authoring` (in `task-types/srs-authoring/`) turns requirements material into a software requirements specification. Its interface texts and rules are in Chinese.

### 2.1 Collections and fields

| Collection | Id prefix | Fields (required in bold) |
|---|---|---|
| Use cases | UC | **name**, **purpose**, **actors** (list), preconditions (list), postconditions (list), constraint rules (list), **basic flow** (list), extension flows (list) |
| Non-functional requirements | NFR | **category**, **sentence pattern** (one of the six EARS patterns), **requirement statement** |
| Constraints | CON | **category**, **sentence pattern**, **requirement statement** |
| Open and out-of-scope issues | TBD | **issue**, **kind** (to be clarified, out of scope, later iteration), suggested handling, **status** (unresolved, resolved, kept by the user's decision), outcome, related items (item references) |

Completion conditions: use cases need at least one item, and every use case, non-functional requirement and constraint must pass review and be confirmed by the user; no open issue may remain unresolved.

### 2.2 Domain rules

Two rule documents in `docs/domain-knowledge/` describe how to write items. The executor reads them before writing.

- **Use cases** (`use-case-writing.md`): one use case is one actor's goal; the nine parts of a use case (name, id, purpose, actors, preconditions, postconditions, constraint rules, basic flow, extension flows) and how to write each; what is not allowed (interface details, functions not in the material, deciding unclear points, examples inside rules, unverifiable words).
- **Non-functional requirements and constraints** (`ears-writing.md`): the difference between the two; the six EARS (Easy Approach to Requirements Syntax) sentence patterns: ubiquitous, event-driven, state-driven, optional feature, unwanted behaviour, and complex; and the rules each statement must meet (one thing per statement, a clear subject, verifiable, no vague words, no examples, no implementation unless it is itself a constraint, numbers kept exactly as in the material).

### 2.3 How the executor works

The executor's skill (`.pi/skills/srs-authoring/SKILL.md`) sets out these working rules:

- **Read before writing.** List the material directory and read every file in full before writing anything. If a file cannot be read or cannot be found, stop and ask.
- **Sort the material** into use cases, non-functional requirements, constraints, and open issues, and save at most four items per save.
- **Do not decide what is unclear.** Record it as an open issue with status "unresolved", optionally with a suggested handling, and ask.
- **Ask one thing at a time**, the one that affects the most items first, and explain first where the question comes from. Use "choose" for yes/no and multiple-choice questions and "ask" only for open questions.
- **After an answer**, update the affected items with a "user's words" source, mark the issue resolved and write the user's decision in its outcome. Only the user in the conversation can decide to leave an issue for later; a remark in the material that something is for later is not the user's decision.
- **When the user contradicts the material**, quote the material and ask which one holds before changing anything.
- **Mark additions.** Anything inferred or filled in from common sense gets an "added by the executor" source and is pointed out to the user.
- **Before changing an item**, look at its current version and change it against that version.
- **After any change**, say which items changed and how, and ask the user to confirm the new versions.
- **Record confirmation only on clear acceptance.** "OK, noted" or "do the others first" is not acceptance; a click on "confirm" in the interface is already recorded.
- **Ask before completing.** When all conditions hold, ask whether to complete now; complete only after the user agrees, and report honestly if the tool refuses.
- **Be honest about tools.** If a step needs a tool that is not available (for example review), skip it and say so.

## 3 Planned, not in the current version

The following are **not** available in the current version.

- **Reviewer (compliance review).** A reviewer that checks each item against the domain rules is planned. The default startup profile does not enable a review tool, so no item can pass review, and the "every item passed review" condition cannot be met. For trial runs, the environment variable `TASKWRIGHT_DEV_REVIEW_AS_MET=1` treats that condition as met; the completion record states that the switch was used.
- **Word (.docx) documents.** Documents are generated as Markdown only.
- **More task types.** Only the software requirements specification task type ships. The task definition format is general, but no other task type is included.
- **A requirements pool** shared across tasks. Each task keeps its own items; items cannot be reused between tasks.
- **Authentication and multiple users.** There are no accounts or permissions; see [deployment.md](deployment.md).
