# 架构（Architecture）

> 本文写给要改代码的贡献者。产品能做什么见[功能说明](capabilities.zh-CN.md)，怎样运行见[部署](deployment.zh-CN.md)。

## 组件（Components）

| 组件 | 语言 | 运行在哪里 | 读任务数据库 | 写任务数据库 |
|---|---|---|---|---|
| 智能体（Agent，`agent/`） | TypeScript | 在 pi 进程内部 | 是 | **是，且是唯一的写入方** |
| 任务服务（Task service，`backend/`） | TypeScript，由 Node.js 直接运行 | 自己的进程；为每个任务启动一个 pi 进程 | 只读 | 从不写（建任务经 agent 的 `createTask`） |
| 观测台（Observatory，`observatory/`） | Python | 自己的本地网页应用 | 只读 | 从不写 |
| 网页（Web，`web/`） | TypeScript、React | 浏览器 | 否，它只调接口 | 从不写 |
| 模拟用户（Simulator，`sim/`） | TypeScript 工具、Python 驱动程序，以及启动模拟用户的 Node 驱动程序 | 另一个 pi 进程 | 只读（用于判定） | 从不写 |

**任务服务怎样与 pi 通信。** 任务服务以 RPC 方式启动 pi，与它按行收发 JSON，一行一个对象：命令与对话框的应答写进 pi 的标准输入，事件与回应从它的标准输出读出（`backend/src/pi_session.ts`）。读的时候只在换行符处断行，这是 pi 的 RPC 文档的要求，所以 JSON 字符串里的 U+2028、U+2029 两个字符不会把一行切断。启动 pi 与收发这些行的一层是可以替换的接口（`backend/src/transport.ts`），现在只有一种实现：子进程（`backend/src/transport_rpc.ts`）。命令与回应的对应、事件、归档与对话框的应答在它上面一层，由 `PiSession` 处理。有一处例外：列 Codex 订阅的模型目录时，`backend/src/model_config.ts` 会另起一次 pi 的进程让它印出模型清单，不经过这个接口；以后改用 pi 的命令接口读目录。

**知识库放在哪里。** 任务整理时参考的资料放在任务目录之外，在 `--knowledge` 给的知识库根目录下（缺省是用户数据目录下的 `knowledge/`，与 `tasks/`、`runs/` 并列）：`libraries.json`，每个知识库一份 `documents.json` 与放文档本体的 `files/`（`backend/src/knowledge.ts`；目录结构见接口文档第 11 节）。这些文件由任务服务自己读写，不在任何任务数据库里。任务选用了哪些知识库记在任务目录的 `knowledge.json` 里，同样由任务服务写。任务服务启动智能体时，经环境变量 `TASKWRIGHT_KNOWLEDGE_ROOT` 把知识库根目录交给它；智能体一侧只读知识库（`agent/src/lib/knowledge.ts`）：在任务现状消息里列出任务选用的知识库与文档，核对出处以 `knowledge/` 开头的来源（接口文档第 11 节）。智能体不写知识库。

**数据的版本与任务登记。** 数据分两类库。每个任务的内容在它自己的任务库里（任务目录下的 `task.sqlite`），只有助手一侧的工具写它，任务服务只读。任务库在自己的 `user_version` 里记格式版本；改任务库结构的唯一入口是一张按版本号排的升级步骤表（`agent/src/lib/schema.ts` 的 `UPGRADE_STEPS`），助手写库、服务启动时的数据升级、命令行的数据升级都走它。不属于任何一个任务的数据在服务级库里（数据目录下的 `service.sqlite`）：现在是数据目录的格式版本与任务登记表；它的每一句 SQL 都只写在一个数据模块里（`backend/src/service_db.ts`），别的代码只调取存函数。任务目录里另有 `task.json`，记这个任务是哪个产品版本建的、最近一次由哪个版本升级。旧版本的程序遇到更新的数据一律拒绝打开。升级怎样做见部署说明第 8.1 节（`backend/src/data_upgrade.ts`）。

**三种代码。**

| 种类 | 所在目录 | 它可以做什么 |
|---|---|---|
| 工具（tools）与扩展命令（extension commands） | `agent/src/tools`、`agent/src/hooks` | 校验并写任务数据库，始终经过 `agent/src/lib` 里的核心函数，一次写入对应一个事务、一条事件。 |
| 后端 | `backend/`、`observatory/` | 启动并看护 pi，转发用户说的话，转发事件，只读方式读数据库。从不解释或评判内容。 |
| 前端 | `web/` | 发送请求；只有对应的事件到达时才改变屏幕上的内容。 |

## 角色（Roles）

| 角色 | 是谁 | 做什么 |
|---|---|---|
| 用户 | 网页界面或终端里的一个真人，或模拟用户 | 提供材料，回答问题，编辑并确认条目。 |
| 执行者（Executor） | pi 内部的智能体，遵循平台说明与任务类型的 skill | 读材料，写带来源的条目，就不清楚的地方发问，通过回复工具作答。 |
| 判读类角色（Judges） | 在工具内部发起的模型调用，自身不带任何工具 | 评审者（reviewer）按所在集合编了号的评审规则核对一个条目，同一个任务里别的条目作为背景一并交给它（相关的给全部字段，其余的给一行简述），由用户在界面上发起，结论由代码按发现所依据规则的级别算出。用户接不接受一个条目不由模型判断：打开条目看过就算确认。 |

## 数据流（Data flow）

1. 用户创建一个任务（任务类型、名称、材料）。服务端把该任务类型的起始文件复制进一个新的任务目录，智能体的命令行入口创建数据库与任务记录。
2. 打开一个会话会在该目录里启动 pi。一个扩展会追加一条任务状态消息，列出这个任务已有哪些材料。
3. 用户说的话送到 pi。执行者调用工具；每次保存都成为交付物的一次修订（改到的条目在这次修订下的内容），外加 `event` 表里的一行记录。
4. 服务端在写工具执行完毕、扩展命令回报之后、以及 pi 运行期间每 2 秒轮询一次这三个时机察觉新事件，在一个简短的只读事务里读出它们，连同对话事件与进度事件一起，通过 SSE 推给浏览器。
5. 网页界面里的直接操作（编辑、确认、撤销……）都经由 pi 内部的扩展命令完成，因此走的是与工具完全相同的写入路径。
6. 生成文档，是把交付物按某一次修订（也可以只取其中几个条目）通过任务类型的模板渲染成 Markdown：业务说明的七章由程序照页面同一套章节规则排出来（`backend/src/render_chapters.ts`，章与节号、图的放置、角色与用例对照表用的是页面也在用的共用函数），需求条目照模板写。这份 Markdown 再由一个共用的分块函数（`agent/src/lib/document_blocks.ts`）切成标题、段落、列表、表格、图几种块：页面的预览照块排版，整份文档的 Word 文件也照同一批块写，所以两处内容相同。这一步不涉及模型。

**用一句话概括事件流：** 每条数据库事件都有一个单调递增的序号，浏览器把每个序号只应用一次，检测到序号有缺口时就请求一份新快照；对话事件与进度事件不带编号，刷新页面后会依据快照重新构建。

**有阶段的任务的系统提示怎样来。** 任务定义里有「总体分析」集合的任务有阶段。这样的任务，助手一侧的扩展在每次运行开始之前（pi 的 `before_agent_start` 事件，`agent/src/hooks/stage_prompt.ts`）读任务库里最近一条阶段记录，把系统提示整份换成拼好的一份：`agent/prompts/stages/` 下的 `system.md`、`common.md` 与现在这个阶段的那一份（文件名是阶段的键：`reading.md`、`clarifying.md`、`modeling.md`、`writing.md`、`reviewing.md`），加上任务目录里任务 skill 的正文与它旁边 `stages/` 目录里这个阶段的那一份（可以没有），最后接回 pi 自己加的工作目录。pi 的 skill 清单不接回去。替换只管这一次运行，所以换阶段在下一次运行生效；扩展在进程里记着上一份，阶段与各文件的修改时刻、大小都没有变就原样交回。每次运行它经状态栏报一行（哪个阶段、重拼还是沿用、说明文字与各部分的摘要值），后端记成补记里的「系统提示」一条。拿不到阶段或者拼装出错时，扩展不换，这次运行用启动参数给的 `agent/prompts/stages/system.md`。

**活动的说明与节点的出口分开放。** `agent/prompts/stages/` 下六个阶段的文件只写活动自己：做什么、不做什么、做到什么算够。一项活动做完了提议什么、往回提议什么、用户说的话不属于这一段时怎样办，是它在一条流程里的那个节点的事，写在流程的定义里（`agent/prompts/flows/analysis.md`，需求分析，每个节点一节）。会话属于需求分析的工作项时，系统提示里活动的说明后面接它所在那个节点的一节（拼出来的文字与 0.5.0 相同）；会话属于单独启动的活动的工作项时接一段固定的文字（做够了在回复里汇报，不提议别的活动）；自由讨论的会话用一段固定的开头接澄清那项活动的说明，不带出口。启动记录里除了 `agent/prompts/stages/` 的文件，也登记 `agent/prompts/flows/` 的文件的字节数与摘要值。

**活动与流程的定义开头有一段头。** 每项活动的文件与每条流程的文件开头两行 `---` 之间是一段结构化的头，一行一栏：活动写键、名称、方式（批处理、逐项对话、仅限用户发起）、目的、读哪几类需求资产、写哪几类、前置条件与一句例子；流程写键、名称、目的、适用情形、各站、输入、前置条件与一段示例。需求资产分六类（材料与证据、业务说明、分析模型、需求条目、评审与确认、文档与版本），前置条件都是数据条件，取值是封闭的，读的时候校验，缺栏或取值不认就报错（`agent/src/lib/activity_def.ts`）。任务状况里六类资产的现状、活动目录、一项活动现在能不能启动，都从头与任务库现有的内容算出来（`agent/src/lib/activity_catalog.ts`）；拼系统提示时头去掉，只用其后的正文。`stages/publish.md`（发布）与 `flows/change.md`（需求变更）现在只有头。

## 配置放在哪里

| 什么 | 在哪里 | 谁写 |
|---|---|---|
| pi 怎样启动：工具、扩展、技能、缺省的模型 | `backend/profiles/` 下的启动配置 | 代码仓；运行时只读 |
| 模型服务及其密钥 | pi 配置目录里的 `models.json` 与 `auth.json`，与用户在命令行里用的 pi 共用 | 用户手工写、pi（`/login`）写，任务服务写它自己登记的那几项（`backend/src/model_config.ts`，照 pi 的办法加锁、先备份、先写临时文件再改名；见[接口参考](api.zh-CN.md)第 10 节） |
| 用哪个语言模型、哪个嵌入模型，嵌入模型的查询前缀，任务服务登记过哪些模型服务 | 产品自己的设置文件：用户数据目录下的 `settings.json`（`TASKWRIGHT_SETTINGS_FILE` 可以改它的位置），每个 pi 配置目录一份 | 任务服务（`backend/src/product_settings.ts`）；里面不存密钥 |

pi 启动时用哪个模型由 `backend/src/launch.ts` 的 `resolveModel` 决定：先看设置里选定的语言模型；没有时照 0.3，桌面包看 pi 的 `settings.json`；再没有时用启动配置里的。设置里选定了模型时，执行者在每次启动、新建会话、切换会话之后核对 pi 用的模型，不同就用 `set_model` 换过去（`backend/src/executor.ts` 的 `ensureModel`）。

## 数据库表（`task.sqlite`，每个任务目录一份）

| 表 | 一行代表 |
|---|---|
| `task` | 这个任务：任务定义的路径与快照、名称、领域标签、创建者。任务没有状态：早先的状态一列与结束时刻还留在表里，格式 8 起不读不写。 |
| `version_record` | 发布过的一版：版本号（从 1 起）、发布的时刻与发起方、发布时交付物的修订号、发布说明、这一版文档在任务目录 `versions/v{N}/` 下的 Markdown 与 Word 存档、文档里有几张图与其中几张在 Word 里是图片。从 0.5.0「已完成」的任务升级来的第 1 版没有存档。 |
| `revision` | 一批变更（一次保存修订调用，或一次直接操作）；同一任务里一个工具调用编号至多形成一次修订。 |
| `item` | 一个条目的身份信息：它的编号（例如 `UC-001`）、所属集合，以及新增或删除它的那些修订。 |
| `item_version` | 一个条目在某次修订下的字段内容；条目只在新增、修改或恢复它的那些修订下有一行。 |
| `item_source` | 某个来源在某次修订下的条目里支撑的一处内容：产出方是哪种要素（条目，或者图）、种类（文档原文、用户的话、助手补充、条目、图；早期版本还写过用户直接修改，现在不再写，旧记录保留）、locator、逐字摘录（助手补充时是理由）、字段与列表下标；种类是条目或图时另记引用那一刻对方的修订号。早期版本的库（种类叫执行者补充、领域说明，没有这两列）在写入一侧下一次打开时重建这张表迁成现在的样子，读取一侧在那之前按现在的名字读。 |
| `diagram` | 一张图的身份信息：它的编号（例如 `D-001`）、流水号，以及它在自己的哪次修订里删除。图是与条目并列的另一种要素，不评审，不算进完成条件。 |
| `diagram_version` | 一张图在它自己的某次修订下的内容：图名、种类（系统边界图、用例图、对象关系图、状态图、时序图、流程图；库里不检查种类，有哪几种由代码判）、Mermaid 文本、说明，以及这次修订由助手还是用户做的。图的修订号从 1 起，与任务的修订号分开。 |
| `review` | 评审者对条目在某次修订下的内容给出的一次判定；逐条发现（带规则编号与级别）在 `review_finding` 里。 |
| `judgement` | 一条确认标记（表名沿用早期的叫法）：它的依据，已读（用户打开了条目）、界面修改，或界面点击（撤回）；较早的库里还可能有按用户的话登记的。 |
| `judgement_item` | 一条标记接受（已读或已确认）或不接受（撤回）了哪些条目，各自在哪次修订下的内容。 |
| `event` | 发生过的一件事，带着 pi 会话编号、工具调用编号与发起者（执行者或用户）。每次写入都恰好新增一行。 |
| `model_call` | 判读类角色发起的一次模型调用：提示词（prompt）、原始输出、模型、耗时、用量。这是一条过程记录，不是领域事实。 |
| `dialogue_act` | 会话里用户或助手的一项对话行为（dialogue act），例如请求、纠正、询问，助手的告知、提问、请确认；编号写成 rN-M，rN 是这条会话里第几句用户的话。 |
| `tool_rejection` | 助手被工具拒绝的一次调用：哪个工具、调用编号、所属的那次工作、原因种类（输入不合规，或缺前置步骤）、拒绝文字的事实与指引两层、被拒输入的前 2000 个字符。这是一条过程记录，不是领域事实，不写事件。 |
| `activity_record` | 任务的工作项，一个一行：一次启动——启动一条工作流程，或者一项单项活动。记现在做的是哪一项活动、流程的工作项在哪一站与所属流程（单项活动的这两列为空）、谁在什么时候为什么启动，以及用户启动时写的范围说明。工作项没有终点：它一直留着，不要了由用户删除，删除时这一行删掉（事件表里记 `WORK_ITEM_DELETED`）。流程换站只改这一行并记 `ACTIVITY_NODE_ENTERED`，不另开一行；启动记 `ACTIVITY_STARTED`。一个任务可以同时有几个工作项，其中流程的至多一个。记录号自增、不重用。任务库格式版本 5 加的表，取代格式版本 2 到 4 的阶段记录表 `stage_record`；格式版本 7 之前一行是一项活动的一段（流程里每到一站一行），升级时同一流程的各行并成一个工作项，流程的键由早先的 `initial`（需求分析）改写成 `analysis`（需求分析）。早先记下的 `STAGE_MOVED` 与成对的结束、开始事件留在事件表里，照样被认作移动。活动的取值只在代码里判，库不检查，所以加一项活动不用改表。 |
| `work_item_session` | 哪条会话属于哪个工作项：一条会话在建立时属于一个工作项，或者不属于任何工作项（自由讨论的会话，这张表里没有它），之后不改；一个工作项可以先后有几条会话。助手在一条会话里能写什么看这条会话的工作项。工作项被删除时它的会话归档：写上归档的时刻，记录号照旧留着，说明它曾属于那个已经删除的工作项（记录号不重用）；守门按归档的时刻判断，会话文件不动。格式版本 7 加的表。 |

**助手对用户每句话的理解怎样记下。** 用户每说一句话，助手都要写一份理解：在它的文字输出里写一个 JSON 对象，格式是 `agent/prompts/schemas/user_intent.schema.json`（平台说明里对格式的说明也从这个文件生成）。扩展扫这一轮每条助手消息的全部文字段，取出其中的 JSON 片段（围栏里的与裸写的都算），逐个与登记的 schema 匹配（登记表在 `agent/src/lib/registered_outputs.ts`，今天只登记了理解一种）。结果记为四种事件：

| 事件 | 什么时候记 | 算不算失败 |
|---|---|---|
| `USER_INTENT_RECORDED` | 片段符合 schema，事实核对也通过了（它回应的那项行为存在且还没被回应，它提到的条目存在，摘要说的不是系统那句「请用 reply 工具把要对用户说的话发出来」的提醒）；各项行为写进 `dialogue_act` | 不算 |
| `USER_INTENT_INVALID` | 片段符合 schema，但事实核对没通过 | 不算，助手重写即可 |
| `USER_INTENT_MISSING` | 这一轮已经结束（pi 的 `agent_settled`：自动重试与排队的续跑都做完之后），这句话仍没有合格的理解 | 算，而且只有它算 |
| `STRUCTURED_OUTPUT_UNMATCHED` | 一条消息里有哪种登记格式都不匹配、或解析不了的片段（例如漏进文字的工具参数），逐个列出片段与错误 | 不算，只是诊断 |

这一轮还没有合格的理解时，保存修订、发布版本、回复三个工具拒绝执行。用户在卡片上点选、点「这几条都看过了」或「先不管」之后界面替用户发的那句话，按操作本身记下，助手不为它写理解。

数据库使用 SQLite 的预写式日志模式（WAL mode），忙等超时（busy timeout）设为 5 秒：读取不会阻塞写入，写入会排队等待。

## 代码遵守的三条规则

1. 写入只发生在智能体的工具与扩展命令里，且都经过同一套核心函数。
2. 校验只检查结构：集合、字段、类型、必填项、来源。不用内容关键词表做判断；评判内容是模型角色的职责。
3. 界面只展示事件流所说「已经发生的事」，不展示「预期会发生的事」。
